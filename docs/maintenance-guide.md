# AgenticOps 维护指引

不熟悉本文术语时，先查看[术语表](glossary.md)。

## 旧版空工位的一次性恢复

正常升级遵循[更新与回退](usage/update-and-rollback.md)。当指定旧版清理器无法处理自身缓存且绑定产品根已切换时，可由维护人员使用 `internal/station_recovery.py`；它不安装到安装目录，不解析活动任务，也不修改旧 epoch 或复用历史授权。

此工具仅支持产品提交 `25d0b2c66298b5c00eb961d2929116846e113681` 生成的 epoch 2、任务索引为空的 TapData 工位。其它版本、有任务、未知状态、改动接线或不可信目录均停止，不扩大为通用兼容工具。先停止该工位 Agent 和应用写入，再生成清单：

```sh
python3 internal/station_recovery.py plan --station <绝对工位路径> --product-root <绝对产品根> --backup <工位外同文件系统的新备份目录>
python3 internal/station_recovery.py apply --backup <备份目录> --confirmed-digest <核验并确认的摘要> --writers-stopped
```

plan 固化工位身份、旧状态和接线指纹。apply 取得工位、旧状态及缓存锁，逐项回读后原子移出受管接线，最后整体移出已核验的旧状态目录。文件保存在备份中，不递归删除原材料；源码、配置、归档、其它用户文件及数据库不在处置范围内。秘密可能存在于旧配置，备份仅当前用户可访问，不提交或上传。符号链接按原目标字符串保存，备份不作为可直接运行的旧工位。

中断后使用原摘要重试，通过原位置或备份位置的唯一匹配恢复；不覆盖已有备份或新工位。结果 exported 只表示导出成功，不表示新工位已可用。确认旧绑定已移出后，单独使用新版本原生 init/doctor 重建；若保留材料非空，按正常规则确认并使用 --reuse-materials。恢复旧现场需单独核验和授权，不能把备份直接覆盖到新工位。

## 1. 从零开始

准备 Git、Python 3.9+ 和 uv：

```sh
git clone --branch develop --single-branch git@github.com:tapstate/agentic-ops.git
cd agentic-ops
./agenticops setup
```

克隆前先完成 [Git SSH 授权指引](security/git-ssh-access.md)，并确认账号有本仓库访问权。示例显式以 `develop` 作为维护基线；`setup` 会仅 fast-forward 同步该分支、安装本仓库维护依赖并接入受信 Git Hook。工作区有修改时会停止，不会覆盖修改。业务源码由独立工位的 source 管理，不写入产品根。

工位接管时按完整源码 Profile 准备独立仓库；无权限或已有目录不洁净时停止对应准备。产品管理 bare 下载缓存以加速准备，但不共享工位 Git 元数据或管理跨工位源码租约；缓存不是任务事实源，详见[工位源码与材料](usage/station-materials.md)。

`setup` 用于首次初始化产品源码目录。之后在 `develop` 更新当前源码目录：

```sh
./agenticops update
```

`update` 只执行 fast-forward，不自动切换分支、处理分叉、覆盖修改或推送本地提交。本地领先远端时会继续同步维护依赖和源码 Git Hook，并明确报告领先提交数。

## 2. 初始化测试工位

维护源码目录、候选安装目录与项目工位必须分开。公开入口只允许已安装 Product Root 绑定业务工位，不允许可变源码目录直接绑定。以下示例从当前源码仓库的已提交 `develop` 创建本地候选安装，再初始化新的 TapData 测试工位；不推送，不触碰已有安装或工位：

```sh
source_root="$(pwd -P)"
test_root="$(mktemp -d "${TMPDIR:-/tmp}/agenticops-test.XXXXXX")"
candidate_root="$test_root/product"
station="$test_root/station"
./agenticops install --install-home "$candidate_root" --repository "$source_root" --branch develop
"$candidate_root/agenticops" station init --station "$station" --project tapdata
"$candidate_root/agenticops" station doctor --station "$station"
```

Git 克隆只包含该分支已提交内容，不包含当前未提交修改；先核对源码候选提交与安装 HEAD。未提交候选的安装范围必须另外精确记录，不能把上面的克隆结果称为已包含工作树。正式固定验收由[验证](#5-验证)的既有入口准备隔离候选，不要为运行测试擅自提交或推送。

`station` 不得是产品源码、安装目录或其子目录；测试父目录也应在二者之外。省略 `--agent` 会接入候选安装提供的全部 Agent；只接入部分 Agent 时重复传入 `--agent <Agent ID>`。示例只初始化和诊断，不接管 Jira；实际接管测试按已有测试绑定及授权执行，结束后保留现场供审查，退出和 purge 另按正常边界处理。

## 3. 维护与运行是一套代码

源码目录可以直接运行同一套 Gate、Policy、Workflow、Project、Adapter 模块和维护测试，不维护第二套 Runtime。业务工位则运行其绑定的候选安装快照，不会随着源码工作树编辑而热更新。需要复测新候选时准备新的安装快照和测试工位；已有安装的升级遵循[更新与回退](usage/update-and-rollback.md)，不能复制源码覆盖活动安装。

工位中的同版本可再生接线可能需要刷新，命令必须从其绑定安装运行：

```sh
<绑定安装目录>/agenticops station doctor --station <项目工位>
<绑定安装目录>/agenticops station repair --station <项目工位>
```

已启动的 Agent 可能仍持有启动时加载的指引，绑定安装或接线更新后应重启 Agent。通过 `agenticops station start` 启动时会尝试刷新接线；发现旧托管 Hook 时保留现场并要求同 epoch 的显式迁移，跨 epoch 不能用 refresh/repair 续接。源码仓库 Git Hook 独立保留，不是使用者的工具拦截链。更新、回退和首次初始化由 `.local/lifecycle.lock/` 串行执行；发布、Hotfix 或固定验收运行期间不要更新源码。

源码目录产生的所有非 Git 状态统一进入：

```text
.local/
├── product.json              # source、仓库、develop 和最近生命周期同步提交
├── lifecycle.lock/           # 生命周期操作期间的临时互斥锁
├── venv/internal/            # 本仓库维护依赖
├── cache/                    # 缓存
├── story-gate/               # 故事审批、证据和运行记录
└── release/                  # 发布运行记录
```

`.local/` 不提交，也不是规则事实源。

## 4. 变更归属

先从实际受阻或易出错的场景检查现有要求：是成果标准缺失、判定错误，还是辅助工具失败。优先修正现有判定、去除重复步骤或复用原生能力；只有现有机制不能解决问题时，才新增规则、配置或状态，并在现有方案中说明收益、适用边界和维护代价，不另建登记或审批流程。例如，源码清理应依据 Git 跟踪事实和已确认的处置范围，不因 Java 包目录名为 `target` 就增加 Maven 输出目录登记。

评审时用代表性场景比较改动前后的操作负担和结果：正常路径是否减少人工判断或重复操作，脚本中断后能否在原权限内接力，结果不合格时能否明确缺项并补齐。相关行为纳入受影响用例；文档更新和脚本成功本身不证明流程改善，未做真实场景验证的结论应明确限制。权限、保全和外部未知结果的边界不能因简化流程而取消。验证入口与执行时机沿用下节，不新增一套检查流程。

- 标准协议：`contracts/`
- 公司通用门禁：`policies/`
- 平台无关判定：`gate/`
- 确定性状态：`workflow/`
- 项目差异：`projects/<project>/`
- Agent/工具协议差异：`adapters/`
- 安装与接线：`bootstrap/`
- 产品维护协作指引：`skills/`（不含 `shared/`）；它们只供维护 Agent 使用，不安装或接线到业务工位。共享需求设计入口为 `skills/shared/ao-requirement/`，维护根和项目工位共用方法，按目标项目读取约束。Skill 的分类、事实源、发现接线和迁移要求见 [Skill 维护规范](skill-maintenance.md)。

新增 Agent 只增加 `adapters/agents/<id>/` 的 Manifest v3、必要的指引模板和测试（不提供通用工具 Hook）；不要修改公共入口建立平台枚举。新增产品项目只增加 `projects/<project>/`。每个 Jira Project Profile 必须配置 `jira.takeover_watermark`：逻辑键固定为 `agenticops_version`，配置实际 `customfield_<ID>`、字符串字段名、启用的 Jira 事务类型 ID 和 `overwrite` 写入方式；`workflow/project_rules.py` 会拒绝缺失或无效配置，不能绕过接管门禁。工作项、进度和验收写入 Jira，不在仓库新增执行计划。

`python3 workflow/project_rules.py` 的 `render`、`branch` 和 `workflow` 子命令必须通过 `--project <project>` 显式指定项目。无工位的 Python 调用同样提供 `project`，不再默认 TapData；工位调用使用 `station` 的现有绑定。缺少项目时停止读取或生成，旧脚本应补齐参数，不能用默认业务项目代替缺失输入。

准入清单生成使用 `admission.json` 中各 `task_classes.<class>.doc` 的路径，新任务类型无需修改通用渲染器。路径必须为 `projects/<project>/admission/<英文小写连字符名称>.md`，不允许越界、符号链接或多个任务类型覆盖同一文件。生成器先检查全部目标并渲染正文，再开始写入；`render --check` 只检测漂移，不创建目录。既有 TapData 文档路径和正文保持不变。

### 从 Jira 接续维护任务

维护者通过 AO 项目问题列表统一处理所有项目研发从工位提交的问题，按[问题反馈流程](usage/problem-feedback.md#4-维护受理与修复反馈)受理、分诊及交付修复结果，复用同一工作项。`ao-feedback` 负责研发侧总结和上报，不承担维护任务接管或处理；原场景复测和反馈责任由该合同集中定义，不另建维护台账。

使用共享 [ao-task-resume](../skills/shared/ao-task-resume/SKILL.md) 接续 AgenticOps 源码维护任务。核验 Jira 当前目标、负责人、范围与决定，检查本地仓库身份、分支、HEAD、未提交修改以及 GitHub PR/CI；从现有 Story Gate 读取与当前候选匹配的验收材料。缺失材料先核实，只询问影响正确性或授权的缺项。

复用仍适用的设计、代码和验证，按本仓库当前授权及验收合同继续。维护任务不要求业务工位、current/op 或新建 Workflow run，也不调用业务 takeover；外部写入结果未知时先回读原操作，停止依赖步骤并继续独立准备。记录沿用原 Jira 和 Git/PR，不新增任务状态机；接续请求不自动授权提交、推送或发布。

### 确定性执行与 AI 接续原则

本节是脚本与 LLM 分工、异常接续及功能闭环验收的唯一开发规范，适用于新增和修改功能；不是新运行框架，也不表示所有现役入口已具备完整接续能力。数据管理见[数据生命周期开发规范](development-data-lifecycle.md)，具体操作见工位合同，反馈提交规则见[问题反馈流程](usage/problem-feedback.md)。

任务接管协调的分工：程序核验任务身份、记录格式、报告时间、引用关系及回读结果，保护本地原子写入；Agent 通过原生 Jira 工具读写，解释冲突、核实停写并取得必要人工决定。具体规则唯一见[工位合同](architecture/single-task-station.md#jira-任务级接管协调与授权)，不得让各功能各自实现计时或用 LLM 推测替代确定性核验。当前协调入口消费原生回读，不自动联网感知远端变化；旧安装不会随指引更新获得该能力。

程序负责明确、必须可靠执行的规则和状态变化；LLM 负责理解、判断、补齐和处理变化。程序失败后提供可接续现场，LLM 在原授权内继续。同版本程序正常闭环不得依赖 LLM 修补自产合法状态。程序不要求每一步调用 LLM，已知且可确定处理的错误应在所属功能内解决。

| 职责 | 脚本固化 | LLM 处理 |
|---|---|---|
| 输入与判定 | 格式、必填项、路径和对象身份、稳定的明确约束 | 理解需求与差异，从可信来源补齐，未知语义交研发决定 |
| 执行与状态 | 原子写入、互斥、受控状态转换，以及值得复用的稳定操作 | 组织原生工具完成研发工作，选择非固定步骤与替代路径 |
| 验证 | 比较明确预期与实际结果，核验证据对象和绑定 | 分析业务结果与失败原因，不能凭判断伪造验证通过 |
| 恢复 | 已知中断回读、幂等重试、保护已完成成果 | 排障和修补外部数据、配置、环境，处理程序未覆盖的变化 |
| 记录 | 必要操作身份、执行事实与回执 | 总结进度、影响、缺项和反馈材料 |

固化前判断输入/输出/失败条件是否明确、是否重复或涉及必要一致性保护，以及维护收益是否超过成本。必要确定性保护不能因 LLM 能执行而取消；单纯包装原生命令却引入第二套状态的脚本应优先删减。平台已有权限、预算和执行控制不在本应用重复实现，LLM 不承担必须由程序核验的规则。

#### 异常输出与接续

失败输出通过现有结果和操作记录说明：目标及具体对象；已完成、未完成和结果未知部分；原操作标识及必要现场/证据位置；已确认原因与未知项；可重试步骤、所需输入或决定。按实际复杂度提供必要信息，简单无副作用功能不必新增操作记录。仅退出码和堆栈不足以交接，但不要求统一错误数据库、持久问题队列或新协议；输出不得泄露秘密。

接续顺序为读取现场、回读实际结果、分类处理受影响部分、核验成果、沿受支持入口继续。原授权仍有效时复用，缺少决定时只问缺项并继续无依赖工作。

| 失败类别 | 接续边界 |
|---|---|
| 输入、配置或环境缺项 | AI 核实补齐，未知语义由研发决定，复查后重试 |
| 已知临时故障 | 按功能适用条件有限重试，复用原操作身份；无进展不循环 |
| 外部写入结果未知 | 先回读，短暂查不到不证明未写入，不能直接重发 |
| 辅助脚本缺陷 | 原授权内有安全替代路径时，使用原生工具完成剩余工作，仍按相同成果标准核验 |
| 程序内部状态或合同缺陷 | 保全现场并整理反馈；不手改控制状态、删除锁、伪造回执或 PASS；无安全路径只暂停受影响动作 |
| 权限不足、范围扩大或不可逆决定 | 停止受影响动作及依赖步骤，说明具体对象和所需决定，继续已授权的独立准备 |

替代工具不能绕过策略或门禁。功能应能通过受支持入口核实真实外部成果，而不是仅接受某脚本的成功退出码；不为此新增万能状态导入或任意跳阶段接口。现役入口尚不能接纳结果时保持待核验、记录缺口，不把目标规范当成手改状态许可。业务接续不等于产品缺陷修复，临时接力不能成为永久依赖。

#### 问题反馈

应用缺陷、错误指引、缺失恢复路径和反复非预期故障应整理反馈；普通缺项补齐不要求每次建单。用户主动反馈的使用障碍或未定位问题仍应受理，不能要求先证明产品缺陷。沿[问题反馈流程](usage/problem-feedback.md)及现役 ao-feedback 处理授权、查重、脱敏、提交和回读，不复制账号分派及 Jira 操作规则。排障本身不授权外部提交；已有明确反馈授权继续有效，无授权时先整理并说明待提交。

反馈说明预期与实际、版本、必要复现证据、影响、接力方式和最终结果，区分任务已继续与产品问题已修复。反馈服务失败保留可用草稿及待办，不阻断无依赖业务、不新建持久待发队列、不无限重试反馈。维护修复沿既有任务流程，不要求业务 Agent 为继续工作先修应用。

#### 功能逻辑闭环验收

在既有功能设计和验收中说明进入条件、数据与副作用、成功依据、中断恢复、退出收尾和再次使用；按实际影响适用，不新增审批表或要求只读函数具备资源清理接口。数据及资源具体要求只在数据生命周期规范维护。

| 场景 | 验收结果 |
|---|---|
| 同版本正常链路 | 功能 A 生成的合法材料能被后续功能 B 读取、采用和退出，不依赖 AI 修补程序自产状态 |
| 中断与重复调用 | 回读已完成部分，不重复副作用，恢复材料不丢失 |
| 创建失败与退出 | 未创建完成也能收尾，不以部署健康或业务任务完成解锁退出 |
| 归档、恢复、清理与再次使用 | 按对应合同验证跨功能衔接，归档后可继续、清理后可接管；目标能力未实现则明确缺口 |
| 异常接续 | 输出可定位对象和下一步；替代执行成果可核验，无安全路径只暂停依赖步骤，不伪造成功 |
| 原授权失效或事实未知 | 正确停止相关动作，保留现场；不借换工具绕过规则 |
| 接力与反馈失败 | 业务结果与产品缺陷分别记录；反馈不可用不循环、不扩大阻塞 |

复用既有测试并重点验证功能衔接，不以独立函数返回成功证明闭环。确定性约束使用可执行验证；代表性 Agent 接续验证指引是否足以完成处理，两者不互相替代。按变更影响选择用例，不要求每个功能覆盖全部矩阵；正式验收沿第 5 节现有入口。正常场景经常需 AI 改数据、解锁或修状态时判定程序闭环缺陷，不能计为恢复能力通过。新规范不追认现役能力，也不提前撤除尚无替代实现的保护。

### 外部依赖检查与修补继续

本节是上述原则在升级和外部输入差异中的应用，当前操作限制见[更新与回退](usage/update-and-rollback.md#目标设计与当前实现)，状态采用边界见[工位合同](architecture/single-task-station.md#修补后继续现有任务的目标设计)。外部依赖包括当前调用之外形成的旧任务数据、受管文件、配置、进程与服务事实；不是把程序自身缺陷统称外部问题。

正常入口只检查本次必要条件，满足后执行；不满足时返回具体差异，由 AI 依据当前合同修补，再沿原入口复查继续。条件检查不隐式修补或推进；会获取远端材料的探测须说明副作用，不能称纯只读。无关缺项不阻塞独立工作，状态字段转换不证明原操作已完成。

当前条件、采用和恢复判定由所属功能维护，复用已有校验；不要求识别每个历史版本、增加函数包装或独立诊断命令。不新增兼容中心、迁移状态机、兼容队列、逐版本脚本或平行台账。任务控制数据经受支持入口采用；普通只读功能不因此增加候选事务。

在闭环验收基础上，按影响补充：更新后仍有效的输入直接继续；旧格式或缺项可定位并修补；结构合法但事实不符拒绝采用；采用中断及并发变化不覆盖新现场；未知语义交研发补齐。现有全局保护只在对应检查、保全、采用和恢复已实现并验证后替换。

### 生命周期协作规范

功能开发统一遵循[数据生命周期开发规范](development-data-lifecycle.md)，该文集中维护数据分类、用途、写入位置、保全恢复、清理与环境收尾责任，不在本节重复维护矩阵。新增或修改功能同时评审生成和退出闭环；操作行为见[工位目标合同](architecture/single-task-station.md#任务生命周期目标合同)，场景见[PROD-003](user-stories/v1/prod-003-multi-repository-task.md#目标用户故事)。现役操作和目标设计分别验收，不凭规范绕过当前授权、epoch 或源码保护。

## 5. 验证

运行代码及 Skill 变更整理为明确候选后，使用普通提交/PR 候选按影响范围生成正式门禁证据：

```sh
internal/acceptance.sh affected --change-source staged
```

此入口薄转发至 `story-gate verify`，复用 `internal/test_selection.py` 根据全部候选路径选择关联测试，至少运行 Resources。共享 Workflow、Gate/Policy、契约、安装与 Adapter、门禁/发布、Project 配置与 Skill、共享测试夹具及未知影响回到完整四项；已知测试文件运行自身测试，项目脚本运行声明的关联消费者，普通文档运行资源检查。选择器只减少已可靠界定的范围，不以单个修改文件代表完整影响。已提交范围使用 `affected --change-source range --base <base> --head <head>`，且当前实际 HEAD 必须等于指定 head。staged 前后要求工作树与索引一致，无非忽略的未跟踪输入；不会自动暂存、stash 或清理用户文件。

显式需要完整候选验收时使用 `full --change-source staged` 或 `full --change-source range --base <base> --head <head>`；完整证据可以满足同候选的局部最低要求。`affected --change-source worktree`、不带 `--change-source` 的 `full`、`quick` 或组合检查只用于诊断，不产生门禁证据。`quick` 包含完整 Runtime，并不承诺快速。开发中按需运行受影响用例，候选确定后再正式验收，不要先执行诊断 full 再重复正式四项。

```sh
internal/acceptance.sh runtime install
internal/acceptance.sh --list
```

维护审查可使用 `python3 skills/ao-review-change/scripts/review-context.py --change-source staged` 读取精确候选摘要。`acceptance_evidence` 在 Story Gate 已核验匹配证据时返回 `run_id`、验收范围和实际检查结果，便于记录 Jira 验收引用；没有有效证据时为 null。它不读取原始日志，不签发批准，也不替代代码审查。

诊断日志写入 `.local/acceptance/<run-id>/`；正式日志写入 `.local/story-gate/runs/<impact-id>/<run-id>/`，最新自包含摘要位于 `.local/story-gate/evidence/`。同一精确候选从暂存到 commit/range、推送可以消费匹配证据；基线、完整树、变更范围、选择器内容或行为相关环境变化则重验；门禁回读时重新推导最低范围，局部证据不得满足更宽的要求。显式再次调用 verify 始终重新执行，不做跨候选缓存。重验开始即使旧通过和审批失效，失败、取消、超时保留本次非通过记录。机器崩溃残留锁需人工确认没有在途进程后处理，不自动抢锁。

正式检查不设置总耗时硬上限。任一检查超过 600 秒时输出一次 `check_slow` 事件，提供已用时间、日志位置、当前检查的日志起点和日志未增长时间，检查继续执行。Agent 应查看日志与逐组、逐用例耗时，区分持续推进、外部等待和疑似停滞；不能仅凭超过阈值或日志静默断言卡死。向用户说明已核实慢因、待验证推测、优化收益与代价，再由用户决定是否优化或主动取消，不自动扩大修改范围。用户取消仍回收检查进程组并保留非通过记录；真实失败仍阻塞验收。性能调优使用同机同配置三次中位数，不把时间阈值作为普通 CI 硬门禁。

规则测试直接构造经现有契约校验的任务状态，在源码观察等外部边界使用固定输入，保留真实判定、摘要计算和本地状态读写；不得把被测的门禁、归档验证或恢复判定 mock 成成功。只验证规则的用例应断言不执行 Git，避免隐含依赖完整接管夹具。Git 命令与输出语义由边界测试覆盖；源码保存与重置、索引和引用变化、gitlink、归档前现场漂移及中断恢复继续使用独立真实临时仓库。固定 Runtime 同时运行规则测试和真实交互测试，保留代表性的正常、失败恢复和多仓完整流程，不以抽样正常路径代替安全回归。线上 Jira/GitHub 联调与业务验收单独记录，mock 通过不能证明真实服务交互已验收。

证据 v6 的环境字段只包含实际工具版本、两个维护依赖文件的摘要和测试行为开关，不记录绝对路径或敏感环境变量。正式候选验收拒绝启用可选 Maven 集成开关；有需要时单独运行诊断并附上真实集成证据。OPA 缺失或可选 Maven 用例未启用必须明确披露，不声称真实集成已验收。Git 读取和检查子进程清除外部 `GIT_*` 上下文覆盖，候选不能使用 assume-unchanged 或 skip-worktree 隐藏工作树变化。原始日志目录和文件分别限制为 0700 和 0600。发布校验器核验历史开发记录后，仍须在自身隔离环境独立完整验收；同一发布的有效证据可跨准备、审查提交、发布和恢复复用，不重复运行四项。发布证据与开发证据分开，绑定仓库、版本或 Jira、目标基线、候选完整树、验证器和测试合同、工具依赖环境及四项结果；任一绑定变化或记录损坏不得复用。显式 `release.sh verify` 开始即撤销旧发布通过结果，失败或取消不能恢复旧通过；旧审计缺少这些字段时需补一次发布验证。v3/v4/v5 记录仅保留查阅，不满足 v6 选择与绑定合同；首次升级走受保护 main 的独立人工 PR，不要求旧 release submit-review 接受 v6 格式，不双写旧证据。不要使用 `--no-verify`。

## 6. 发布与 Hotfix

发布前比较候选与目标 `main` 的 `contracts/station-state-compatibility.json` 中 `station_state_epoch`，选择发布方式：

- 未跨 epoch：默认使用 Hotfix，尽量不创建新版本标签。确有独立版本发布需要时，在 Jira 说明理由，并取得针对该候选的正式发布与 Tag 授权。
- 跨 epoch：必须使用正式发布流程并创建新版本标签，不得以无标签 Hotfix 代替。Tag 绑定实际 Merge commit；工位升级仍遵循[更新与回退](usage/update-and-rollback.md)的原版本退出、归档、purge 与重建要求。

epoch 只表示工位状态兼容性，不得为创建标签而提升 epoch，也不得为使用 Hotfix 而保留本应提升的 epoch。上述选择不豁免既有验证、发布授权或信任根变更的独立人工审查要求。

正式版本发布分为本地候选准备、独立人工审查和远端交付，复用同一固定候选与发布证据，不新增发布状态机：

| 阶段 | 入口与检查 | 边界 |
|---|---|---|
| 本地候选准备 | `release.sh prepare --version vX.Y`：核验 develop、固定 main 基线、版本占用、epoch、可信故事材料，独立完整验收并创建本地 release 分支 | 会读取远端引用及 fetch；不要求 Auto-merge 或 main 保护，不推送、不修改仓库设置。`delivery_checks=pending` 表示尚未核验交付条件 |
| 独立人工审查 | 候选用 `release.sh submit-for-review --version vX.Y --confirm-release` 提交固定分支 PR，复用验证及绑定检查 | 默认 hard，也接受显式 soft；该确认仅授权推送候选和创建审查 PR，不授权合并或 Tag。保护尚未就绪可以先审查，不能因此合并 |
| 远端交付 | 普通候选用 `publish`；独立人工 Merge commit 合并后用 `inspect`、`recover` | hard 交付核验 main 保护、当前 Head 的独立人工批准、候选/基线/合并树与有效证据，并要求对应交付授权。只有 `publish` 的自动合并路径要求 Auto-merge；人工审查及恢复不依赖它 |

普通候选也可选择同一人工审查路径，不因关闭 Auto-merge 自阻塞。信任根仍禁止自动发布；人工合并前必须由维护者核验受保护 main、独立审查及 GitHub 必需检查。`recover` 在 Tag 前再次核验保护与当前候选批准，不能用“已合并”代替独立审查。规则集检查接受不同名称、至少一人批准及更严格 Code Owner 要求；当前支持单个有效、无绕过、无排除且明确覆盖 main（或默认/全部分支）的规则集，不推断传统保护或多个规则集组合等价。规则要求 Merge commit、禁止删除及强推、撤销过期审批、最新推送由他人批准及讨论解决。

软门禁交付仅为普通候选保留显式 `--allow-soft-gate`，不表示独立审查只能走 soft，也不能豁免信任根交付所需的 main 保护。发布命令不再接受 `--configure-workflow` 代为配置仓库；治理配置应单独审查和授权。版本及候选在合并前固定，发布版本使用 `v1.x`；同 epoch 的正式版本准备还须提供 `--jira <编号> --same-epoch-reason <已在 Jira 记录的理由>`。发布从固定实现快照执行，测试只读取固定 Git 候选，不自动提交、stash 或清理用户工作区；发布实现自身有未提交修改时停止，先审查实现。`publish`、合并和 Tag 需要针对实际候选范围的明确授权。上述分阶段行为为当前源码能力，旧安装仍按其版本执行，不因本文自行绕过旧入口。

Hotfix 只能使用：

```sh
internal/release/hotfix.sh <JIRA-KEY>
```

明确调用该 Hotfix 入口是快速修复授权。同 epoch 普通变更在固定验收后原子更新 `main` 与 `develop`；同 epoch 信任根变更仍由此入口编排独立人工 PR，禁止自动直推 `main`，合并后重新调用同一命令完成无标签收尾。跨 epoch 拒绝 Hotfix，必须使用正式版本流程。冲突、分叉或回读不明时停止受影响动作。源码版本由 `python3 internal/version.py` 输出为 `<分支>-<标签>-<提交数>-<提交编号>`。

详细边界见[项目目标](strategy/project-goals.md)和 [v1 架构](architecture/agenticops-v1-architecture.md)。

### 发布验证复用与合并后收尾

`prepare` 先核验候选已包含固定 `main` 基线、版本占用及历史故事审查材料，再在隔离环境独立执行四项；结果保存于 `.local/release/`，测试原始日志保留在其中的私有运行目录。`submit-for-review`、`publish` 和 `recover` 只消费同一有效发布证据。`inspect` 和不带确认参数的 `recover` 不执行测试；缺证据时明确要求补验，不因查询或生成确认参数重复测试。

需要显式重验时使用 `internal/release/release.sh verify --version vX.Y`；已合并候选附加 `--merged-pr <PR编号>`。恢复使用 `inspect --version vX.Y --merged-pr <PR编号>` 核对事实，再按输出执行 `recover`；确认参数绑定版本、PR、候选及实际合并和 Tag 状态，有效授权不因分步命令重复索取。Hotfix 没有有效证据时在自身入口补一次独立验收，不使用正式版本 Tag。

合并前核验固定 Head、目标基线及审查；实际 Merge commit 必须恰有两个父提交，分别对应已确认基线与候选，完整代码树必须与已测候选一致，且仍在 `main` 历史中。基线或合并结果漂移时停止 Tag 并重新评估范围、验收和授权，不用旧候选通过或仅祖先关系代替实际结果校验。版本号事先确定，annotated Tag 在合并后指向实际 Merge commit；已有正确 Tag 可幂等复用，错误 Tag 不移动、不覆盖。源分支删除不影响按 PR 和提交事实恢复。

正常与恢复使用同一收尾逻辑：回读实际合并及 Tag，再尝试同步该发布 Merge commit 到 `develop`，不顺带同步后续 `main` 提交。响应分别给出 `delivery_status` 和 `develop_sync_status`；有并行开发提交时保留代码并报告 `pending_integration`，工作区脏或不能安全快进本地分支时报告 `local_pending`，外部结果不明报告 `unknown`。已交付但同步待办使用 `completed_with_pending_sync`，不能把待办隐去；同步问题不撤销正确 Tag，也不触发重新发布。任何推送结果不明确先回读，不盲目重写远端；Tag 成功后审计失败，重试只补未完成收尾。

本地锁只约束同一记录目录内的操作，不是跨 clone 的服务端锁或防篡改机制。远端引用、PR 和检查仍是事实源；并发变化必须靠精确对象核验及写后回读处理。该优化本身修改发布信任根，首次交付仍需独立人工审查，不能用新候选放宽旧门禁。

### 提交信息构造

- 提交标题使用第一个 `git commit -m "<title>"` 参数。
- 正文每个自然段必须使用独立的 `-m "<paragraph>"` 参数，Git 会自动以空行分隔各段。
- 禁止在任何 `-m` 参数中传入字面 `\n`、`\\n`、`echo -e`、`printf`，或依赖下游二次解析来形成多段正文。
- 正文确实需要复杂格式时，使用 `git commit -F <message-file>`；文件内容必须包含真实换行。
- 发起提交前，Agent 必须逐段检查提交参数中的标题、变更、原因、验证和风险；任何参数含字面 `\n` 时停止并改正。

推荐模板：

```sh
git commit \
  -m "fix(station): AO-108 中文主题" \
  -m "变更：……" \
  -m "原因：……" \
  -m "验证：……" \
  -m "风险：……"
```

## 7. 维护 Agent 协作与模型适配

截至 2026-10-14，OpenAI 的 [GPT-6 系列指引](https://developers.openai.com/api/docs/guides/latest-model)将 GPT-6.1 Sol 定位为兼顾速度、成本与复杂编码的选择；关于指令敏感、澄清和测试范围的提示主要基于 Astra 观察，需在实际模型与工作负载中验证。[官方提示词审计建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)强调精确触发、按需阅读和明确完成边界。这些是模型与平台能力说明，不是 AgenticOps 的权限保证。

产品维护据此采用根 `AGENTS.md` 的协作约定：沿用有效授权、先完成可审查准备、只在真实决策处暂停；技能编写检查见 [Skill 维护规范](skill-maintenance.md)。初始化技能区分明确更新与意图不清的重建，接管测试技能区分必填绑定与可选回复，避免把重复确认当作安全措施。

异步工具、执行中补充要求和推理强度调整以当前 Agent 实际暴露的接口为准；不能因为模型支持就假定 CLI、桌面端或 Adapter 已支持。没有异步能力时按顺序执行并报告阻塞，不新增 Runtime 模拟平台调度，也不自行修改用户模型配置。等待期间可做独立只读分析；恢复后先核验原操作及当前目标，再消费结果。子代理只用于已要求的独立工作，接管测试仍使用一个执行子代理，不扩大并发写入范围。

指引调整的人工场景核对包括：明确更新既有工位时直接 repair；缺工作目录时只问该目录；已有绑定不符时停止覆盖；用户中途收窄目标时停止受影响步骤；外部写结果未知时先回读并继续不依赖该结果的准备；正文修正且主题结构未变时不改总纲；维护任务接续不索要业务工位，业务接续仍核验绑定；方案第五轮仍有问题时输出当前方案与未决问题交由用户决策；测试通过且候选未变时不重复运行。静态核对与固定验收只能证明指令和资源合同，不能宣称 Astra 行为、真实 Jira 接管或多平台端到端已验证。


## epoch 25 空 runtime 身份恢复

epoch 25 目录身份修复版本可直接清理同 epoch 工位，以下工具仅供仍需在原安装完成清理的受控恢复，不是同 epoch 更新的前置要求。仅当研发明确批准旧版本恢复例外时，维护工具 `internal/station_identity_recovery.py` 可处理未修改的安装提交 `16b76424c2f20ec737d29d23aec830a4ecdd1eaf`。它加载该原安装的 Workflow，要求当前任务未归档、无未完成操作、无登记写入者或未知外部结果，且仅登记一个空 runtime、父子 inode 均不变、仅设备号变化；不解释其它版本，不进入产品安装目录。

先用 `--product-root <原安装> --station <工位> --request <工位外私有新文件>` 生成旧新登记及绑定摘要；审阅后以相同参数追加 `--confirm-digest <摘要> --decision-ref <用户决定来源> --writers-stopped` 执行。恢复只原子更新原格式目录登记并保留外部请求和回执；中断复用相同请求，任务或目录变化则停止。此恢复不授权删除或升级；仍由原版本重新生成清理清单、保全归档、清理及 purge，成功后才切换新版。

## 脚本控制台输出规范

Bootstrap 的人读输出采用 `[AgenticOps][操作][状态] 消息`，操作使用中文名称，状态为“进行”“完成”“警告”或“失败”。先输出有意义的阶段，再给一次最终结果；普通字段使用两空格缩进，下一步给可复制的命令，包含路径时按 Shell 规则引用。帮助文本保持用法格式，JSON、只读数据回执与 Agent 子进程输出保持原协议，不添加人读前缀。

阶段、警告与失败写 stderr；成功摘要与下一步写 stdout。阶段描述实际执行的工作，不伪造下载百分比，不在循环中重复刷屏。底层工具的普通成功进度优先通过原生 quiet 选项关闭；警告、错误与必要诊断保留，不使用全局丢弃 stderr 的方式隐藏问题。失败时报告当前阶段及原退出码，不输出完成摘要，不自动删除可能用于恢复的产物，也不记录命令参数中的凭证。

规范覆盖 `agenticops` 的 Bootstrap 生命周期入口（install/setup/update/rollback、工位 init/doctor/repair/start 与注册管理操作）。安装脚本支持 stdin 独立执行，输出直接使用 Shell 原生能力，避免依赖尚未下载的公共日志文件；Workflow、Gate、项目工具、内部验收/发布事件按各自既有协议输出，不机械增加人读前缀。运行条件失败不使用 argparse 的参数错误出口；真正的参数错误仍展示用法。不新增日志框架、第三方依赖、日志配置或持久日志目录。该规范只管理展示，不改变生命周期锁、安装状态、工位 epoch 或验收判断。

初始化调用渲染器时，使用内部 `--quiet` 选项省略接线成功明细；repair/start 调用渲染器同样省略成功明细；repair 在全部步骤成功后汇总，start 输出启动阶段后将控制权交给 Agent；独立渲染保留缩进字段。静默选项必须保留需要用户行动的警告和全部失败诊断。doctor 检出产品版本漂移时提供含实际工位路径的 repair 命令，按 Shell 引用；修复仍由用户显式执行，不能将检查自动变成写入。插件首次使用的说明收敛为一条提示，详细规则由[必需 MCP 配置](usage/mcp-setup.md)维护。
