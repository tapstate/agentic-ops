# 单任务工位设计合同

本文同时区分产品目标与当前源码。当前候选提供 `clean --scope task|station` 两个清理范围，归档独立，功能校验模式不以 epoch 差异要求退出；旧模式目标按第 10 节处理；源码候选不代表现有安装已经更新，也不代表真实业务环境验收已经完成。实际采用须核验安装提交与机器兼容清单。

通用异常接续与闭环验收引用[开发原则](../maintenance-guide.md#确定性执行与-ai-接续原则)，本合同只维护任务状态和生命周期操作边界。原生工具完成的成果仍须经支持的入口核验；目标规范不授权手改状态或回执。

## 任务生命周期目标合同

数据分类、作用、存放及功能管理责任唯一见[数据生命周期开发规范](../development-data-lifecycle.md)；本节只定义用户操作和接管行为。验收见[PROD-003](../user-stories/v1/prod-003-multi-repository-task.md#目标用户故事)。

### 接管归档与恢复

新任务接管从 Jira 获取需求及方案，准备独立源码和必要输入，建立本地状态。处理期间在正常协作节点持续保存已确认方案、决定与进度。同工位继续沿有效 run/op，不要求先归档或因会话丢失重新创建任务。

目标归档是建立可跨工位接续的持久保存点，不等于完成、释放或清理，也不打包整个工位。核实 Jira 上的方案、实际进度、剩余事项、阻塞和待回读外部操作，确认需保留代码已提交并推送对应远端分支，记录完整引用；必要证据和唯一数据按数据规范保全。用户可明确放弃未保全成果，只保留已确认方案，但须说明哪些进度需要重做。推送遵守既有授权，不能把提出方案当成执行授权。

多次归档有新增成果时保存新接续点并保留历史，无变化时回读复用，重试先查已成功写入结果。最新归档未完整成功时不能替代上次有效接续点，须披露新增部分的持久化缺口；局部失败不妨碍无依赖工作。Jira 与 Git 不具备跨服务原子提交，不假设两者同时成功。归档后新增变更在清理前重新保全或明确放弃，不能仅检查“归档过”。不新增归档数据库或平行进度台账。

新工位从最新有效接续点核实 Jira/Git/PR/CI 成果，尽可能恢复实际进度，以当前受支持入口建立状态，补齐缺项；不直接映射阶段或继承旧锁、占用、授权凭据和 PASS。历史决定与验证只在适用条件仍成立时复用。配置与环境由 Agent 和研发补齐，唯一数据不能凭空恢复。归档不证明原执行者已停止；目标交接统一遵循下述 Jira 任务级接管协调，当前本地实现另见“执行接管（当前源码）”。

### 两个清理操作

| 操作 | 作用 | 完成状态 |
|---|---|---|
| 清理任务 | 保全或放弃成果后，释放任务独占资源，删除 source、任务运行数据及本地任务状态，解除任务和 Agent 占用 | 保留用户配置及工位基础接线，可以接管新任务 |
| 清理工位 | 复用清理任务，再删除工位内用户配置、秘密材料及使用期间产生的其他数据 | 恢复当前版本初始工位状态，保留安装、初始接线及登记；不等于注销或卸载 |

两个操作不删除 Jira 历史、远端分支、PR、中央持久档案、共享缓存和外部共享服务。清理工位允许用户明确放弃工位内全部积累，但不沿链接或配置引用扩大到外部对象。空闲工位及未完成接管也可清理残留。工作中的缓存清理或环境重建由功能自身承担，不新增第三种生命周期清理入口；release 不再作为目标独立概念。

源码采用保全后删除工位独立 source 副本，不逐仓复杂重置。检查暂存/未暂存/未跟踪修改、未推送提交、本地独有分支、stash、被忽略的配置或唯一数据、多仓及嵌套仓库/关联工作树；仅对可能丢失的成果请研发决定推送、另存或放弃。已核实保全不重复确认，删除本地分支副本不授权删除远端引用。配置须先归置 config；外部工作树、挂载与路径身份不明时不直接递归删除。停止写入后复查新增变更，归档不能替代实际保全核验。共享源码池复用但不随清理删除，性能须按数据规范实测。

执行顺序为取得执行控制、确认成果处置、停止并释放独占资源、删除数据、核验结果。用户清理不必等待闲置阈值，但须协调原执行者与在途操作；8 小时超时不授权直接删除。必要恢复记录最后清除。中断沿原操作回读并继续，不扩大删除范围、不重复已完成副作用；已解绑不代表清理完成，必要残留如实报告。配置损坏仅阻止依赖其身份的动作；清理不要求部署健康、完成任务或先升级。

### Jira 任务级接管协调与授权

当前源码候选已提供下述协调入口；正式验收、真实服务与发布支持范围分别记录，不代表旧安装已更新。协调对象是 Jira 站点与任务 ID 的组合，任务号用于展示；同工位和跨工位使用同一规则。Jira 保存任务级接管协调，本地原子锁和会话校验保护工位状态写入，不再维护第二套独立的 8 小时业务判定。普通任务授权与接管协调分离，期限和失效条件见[实施授权](../usage/task-authorization.md#实施授权)；接管不授予实施、推送或发布权限，也不控制 Token 预算。

每次取得或转移接管新增一条专用协调评论，记录接管者、工位及执行会话标识、是否仍在处理、接替的评论引用和必要的人工决定来源；之后只更新自己的评论；同工位接续者仅可在明确人工清理决定和停写核实后结束本工位旧会话记录，不能替旧会话报活。不修改 Jira 经办人或业务状态，不改写已冻结的归档正文、质量验收或阶段总结。复用原生评论读写、意图与回读能力，不新增客户端、字段、索引或协调服务。评论不保存本机路径、秘密、完整任务状态或授权副本。

开始或恢复工作、正常进度同步、交接及长时间处理中的主动报活时，先回读接替关系，再更新自己的有效记录并回读；只读旁观不报活，不设置后台心跳或逐文件修改同步。活动时间采用 Jira 返回的本条协调评论更新时间，只代表最后一次报告活动，不证明本地最后一次执行时间；普通任务字段变化和其他评论不计作报活。8 小时是从最后报告活动起计算的提示阈值，不是任务授权期限或自动释放时刻。

| 回读事实 | 接管处理 |
|---|---|
| 完整读取成功且无有效接管记录 | 登记本次接管并回读，检查是否出现竞争记录后继续 |
| 当前仍为同一执行会话，且未被接替 | 继续原任务，不重复询问；恢复时仍须核对在途操作 |
| 其他接管者最后报告活动不足 8 小时 | 提示接管者、工位及时间；取得真实人工交接决定并核实停写和在途操作后，登记接替关系 |
| 距最后报告活动已满 8 小时 | 仅提示可能闲置；核实旧执行者及在途操作无冲突后允许接管，无法确认则暂停冲突写入并交人工决定 |
| 多条竞争记录、身份/格式不明、读取不完整或权限不足 | 不按最新评论或未找到记录推定无人处理；展示缺口，由 Agent 补齐或引导人工处置 |
| 写入结果未知 | 先按原意图回读，不重复发送，不把本地准备完成当作接管成功 |

接管前读取须覆盖相关历史记录及分页，不能只取最近几条评论推定空闲；已被有效接替的旧记录不会因再次报活恢复接管。两条仍在处理的记录同时接替同一旧记录、或互无明确接替关系时视为冲突，不以评论时间自动选胜者。人工决定绑定实际观察到的记录；接管者、活动或接替关系变化时重新核对决定适用性。人为编辑、不可见或旧客户端未上报的活动仍可能无法发现，不承诺完整感知所有 Agent。

人工确认表示允许交接并已处理旧执行者的写入风险，不是旧进程停止的证明。回读由 Agent 在工作段边界主动发起；程序核验最近提交的完整回读，既不后台联网也不能感知未提交的新远端活动。旧会话恢复或进入下一工作段前回读，发现已被接替即停止冲突写入；本地会话转移仍由原子校验保护。普通 Jira 评论读写不提供全局原子排他，两个工位可能同时读到空闲并写入；写后回读和后续检查用于发现冲突，不能保证竞争窗口内绝无并发动作，也不能立即终止原生进程。不引入分布式锁、租约或工具拦截。

归档不结束接管。跨工位恢复先核实交接，再按当前流程恢复成果，不导入旧占用、授权或 PASS。已交接旧工位的清理只取得本地执行控制，不重新申请 Jira 任务接管；沿已冻结正文补录原归档回执、取消尚未开始删除且无未知资源动作的清理、补录原清理对象的精确外部资源回执，同样只依赖本地执行控制。新归档、重新生成正文、新增资源或继续任务写入仍需有效任务级接管。清理只结束属于自己的协调记录，不更新新工位的接管记录；本地清理与 Jira 结束回读分别报告，远端失败保留必要同步线索，不反向阻塞已获授权且已核实停写的本地清理。协调记录是共享历史，不随本地数据删除。Jira 不可用时不能推定无人接管；只暂停依赖接管判断的写入，继续只读准备及已核实可独立完成的收尾。

### 当前实现差异

| 当前行为 | 目标变化与尚待验证事项 |
|---|---|
| 当前源码 grant 默认不固定到期；显式期限、旧有限授权和撤销继续有效 | 授权与任务级接管协调分离，不承担 Token 预算控制 |
| 当前候选 `coordination` 消费原生 Jira 完整评论分页，核验任务级接替关系和报告时间；本地 `execution_control` 只保护写入 | 跨工位提示不是全局锁，工作段回读须由 Agent 发起；旧安装仍按原版合同，真实服务权限与竞争边界须单独验收 |
| 当前候选使用 clean 的 task/station 两个范围；预检核实源码保全后整区删除 | 验收结果绑定具体候选与覆盖范围，不等于旧安装已更新；purge 属注销，不当作清理工位 |
| 已提供 handoff 材料、远端代码检查、稳定正文及原生 Jira 回读入口；本地快照为尽力保存的副本 | 持久点操作见任务存档指引；查重、最新有效点选择由 Agent 核实，真实双工位验收与源码回归分开，不把本地快照当持久保全 |
| 两个清理操作先按工位标签释放 Docker 容器/网络，再删除独占环境目录；运行目录丢失仍会发现资源，驱动不可用保留未核验结果 | 当前使用目录挂载，不创建受管命名卷；不删除共享卷/镜像，不为尚未产生的资源新增通用管理框架 |
| source_pool 支持本地源码池克隆 | 复用现有能力，验证删除重建的真实耗时、流量及依赖编译成本 |
| 功能校验模式支持合同有效的旧任务原 run 接续；旧模式保留 epoch 退出要求 | 任意旧格式转换、旧在途操作采用和会话热更新未承诺，具体边界见第 10 节 |



第 10 节分别说明已实现的旧任务接续、当前兼容边界和待实现的修补能力。旧客户端仍按其实际实现处理；其它能力以各节说明及实际安装核验为准，不能因本文含有设计就视为已实现。

Docker 资源发现以原生标签和实际回读为依据，不以 runtime 目录存在为前提。存在环境配置、运行目录或原操作线索但驱动不可用时，结果保持未核验；Agent 先修复访问或核实原资源，不据错误退出码推定已清除。没有环境配置和运行线索、也没有安装可选 Docker 驱动的工位按未启用本机环境处理；若已知曾使用后人工删除全部材料，仍需 Agent 核实外部残留，不能据当前空目录宣称安全。

## 执行接管（当前源码）

`task.py coordination` 复用原生 Jira 工具的写入意图和回读。输入 JSON 包含 `site`、`issue_id`、`issue_key`、`source_ref`、`pages`；站点与项目配置一致，ID/key 来自 Jira 任务原生回读。pages 按 startAt 从 0 连续排列，每页保留 total/isLast/comments，comments 保留 id/body/updated。必须读取全部评论页，不能预先过滤正文或伪造完整标志；程序只解释带专用标识的评论。服务端可见性仍取决于账号权限，不提供身份认证或防篡改。

```sh
python3 "$product/workflow/task.py" coordination check --dir "$station" --input jira-readback.json
python3 "$product/workflow/task.py" coordination prepare --dir "$station" --input jira-readback.json --mode claim --operation-id <稳定编号> --executor <执行者说明> --expected-digest <check摘要> --conflict-check-ref <停写核实> --decision-ref <必要人工决定>
# 原生 Jira 工具发送返回的 body；comment_id 为空时新增，否则仅更新指定评论。
# 写后重新完整读取评论，输入 complete，不用本地草稿冒充回读。
python3 "$product/workflow/task.py" coordination complete --dir "$station" --input jira-readback.json --claim-id <prepare返回编号>
```

`check` 在当前会话不是唯一有效接管者时返回 2，同时给出占用者和摘要；无记录可沿 prepare 登记。`complete` 的 saved 只表示原正文已保存，verified 才表示当前完整回读中该会话唯一有效；竞争时不授予继续写入。源码接管与活动任务受管写入要求本会话的有效协调回读，不能单靠本地 claim 获得任务执行权。

报活和结束复用 prepare 的 `--mode report|end --claim-id`，每次更新使用新的稳定 operation-id，结束前也回读核对原正文。已发送结果未知沿原编号回读，不换编号重发；只有明确从未发送才用 `coordination cancel --claim-id --input --decision-ref` 取消原意图。status 可只读查询本地待办。归档不会结束协调；本地清理清除检查结果、保留当前状态信封内的协调收尾线索并报告待办，之后按 end/complete 结束自己的记录。注销前仍有远端待办时须先收尾，不能删除唯一恢复线索；这不阻塞已获授权的本地清理。

原会话丢失时，新会话可在已有有效人工接续决定和停写核实下，向 complete/cancel 提供 `--decision-ref` 与 `--conflict-check-ref`，核验本工位原意图；不借用旧会话标识，不继承其接管权或替其报活。回读和取消均绑定原 Jira 站点与任务 ID。未确认意图只阻止依赖同一任务的协调判断，不阻塞其他任务的独立处理；旧任务待办仍保留供收尾。operation-id 属于本工位，新接管不得复用本工位 Jira 历史编号；不同工位使用相同编号不构成重复评论。

`current-task.json.jira_coordination` 保存本工位必要意图、回读与最近工作段检查结果，不另建数据库。结束回读可重复，后续新操作收敛已结束记录；本地成功和 Jira 成功分别报告。Jira 协调在 epoch 38 引入；当前采用与修补按第 10 节功能合同处理，不能仅凭来源 epoch 要求退出。

本地 `execution_control` 保留会话标识、执行者说明、最近本地活动及交接依据，原子核验工位写入；本地活动不参与 Jira 8 小时判断。start 提供独立 `AGENTICOPS_EXECUTION_ID`，手动平台每会话生成一次 UUID hex，不借用其他会话标识。`execution status` 只读；`execution claim --executor --expected-control-digest --conflict-check-ref` 核实本地交接，不另设时长门槛，不改变 run/op 或实施授权。`execution heartbeat` 仅刷新本地活动，不向 Jira 报活。旧会话即使有历史任务回读，也不能绕过本地会话保护。清理原工位沿本地控制收尾，无需夺回已经交接的 Jira 任务。

## 1. 目标与范围

一个项目工位长期保存完整多仓工程，同时至多处理一个任务。并发通过多个独立工位实现。操作面区分接管、任务清理、工位清理、任务归档和工位注销。新接管要求当前任务已解绑、原操作结束，且实际源码与运行资源满足接管条件。

首版支持本地工位。每工位使用独立 Git 仓库和固定 checkout，避免共享 Git 元数据中的任务分支占用、配置和回收耦合；源码池由安装目录配置或工位初始化的显式 `--source-pool` 决定，默认 `~/.agentic-ops-repos`。缓存路径是 `repositories/<owner>/<repo>.git`，不按 origin 增加第二层隔离；同名缓存 origin 不一致时失败关闭，由研发者为新工位配置另一个源码池。接管准备源码时先下载缺失缓存或刷新已有缓存，再从缓存传输到独立工位仓库，不能用对象 alternates 等方式依赖缓存存活。缓存丢失不影响已准备工位。未完成和已完成任务均可归档或清理；归档保存已核实的 Jira 接续点并尽力保存本地副本，不冻结后续开发，清理负责释放。容器、远程调度、环境池、会话租约、多任务 runtime 和持续优化平台不属于本合同。

公共 Workflow 维护身份、占用、确认、操作恢复和结果核验；Project 定义源码仓库集合、版本解析、清理规则及构建运行指引。现役 takeover 只准备独立源码与冻结基线，不执行构建、启动或健康检查。Agent 按任务方案使用原生工具执行构建、测试和应用运行；不直接照搬含发布、上传或全局配置修改的打包脚本。根入口仍为薄转发，不建立第二套 Runtime。生命周期操作不授权合并、发布、Tag、强推或历史改写。

## 2. 身份与唯一事实

| 标识 | 归属与规则 |
|---|---|
| `station_id` | 复用工位已有稳定 `station_id` 作为工位身份，只改用户术语，不建立第二个 ID；创建新工位时生成新值，不能复制绑定文件克隆工位 |
| `issue_key` | Jira 工作项身份，用户可见 |
| `run_id` | 新接管生成 `<jira-key>-<timestamp-hex>`，时间段为 8 位小写 HEX。接管前在 Product Root 原子创建 `.archive/<run_id>` 占位；仅编号占用冲突等待 2 秒重新取时重试一次，权限及其他 I/O 错误立即返回。跨会话恢复不变，清理后重接同一 Jira 会在后续秒生成新值。旧三段式及更早格式只供既有材料读取，不再生成 |
| `operation_id` | 一次状态或资源操作的恢复身份，用户不必输入；重试沿用，独立新操作使用新值 |

对用户主要展示工位名称、任务号、任务结果与当前操作进度。写入请求携带从上下文读出的 `run_id` 和预期状态版本，执行时不得自动用新 run 补齐旧请求。`run_id` 只防止受检查操作和证据串用，不约束任意原生文件写入。

### 2.1 `run_id` 设计约束

`run_id` 是一次接管的内部关联键，用于把 current、operation、授权、质量证据、资源登记、工作分支和正式档案绑定到同一次运行。它必须便于研发识别所属 Jira 和大致接管时间，但不是全局分布式 ID、秘密值、安全令牌、排序游标或 Git revision。唯一性只要求覆盖 Product Root 中实际共存的运行材料，并由原子档案目录占位证明，不能仅凭字符串生成算法宣称。

新编号固定为 `<jira-key>-<timestamp-hex>`。`timestamp-hex` 是接管时 Unix 秒数的 8 位小写十六进制表示；不增加毫秒、随机数、工位 ID、主机 ID、计数器或重试序号。选择这一格式的理由是：正常研发接管不需要在同一 Jira、同一秒创建多个运行；自动消歧会把重复或并发接管隐藏成两个看似有效的 run，增加误接管、错误恢复和材料串用的解释成本。这里选择失败可见性和人工重试，而不是让生成器追求无条件成功。

接管必须先在 Product Root 原子创建 `.archive/<run_id>` 目录占位，不再生成 `.archive/.reservations` 文件。仅编号目录或历史预留文件已存在（`FileExistsError`）时，等待 2 秒重新取时生成编号并重试一次；等待用于跨过秒级时间戳，避免立即生成相同编号。权限不足及其他 I/O 错误保留原始异常立即返回，由 Agent 引导授权或环境处理；第二次仍失败则返回具体原因，不循环、不加随机后缀。历史预留文件仍作为占用凭据只读核验。空占位目录只证明编号已占用，不表示归档证据冻结，不妨碍已有 Jira 状态、水印或评论意图的回执与回读；历史归档快照不冻结仍在进行的任务回执，快照内容保持不可变；目标为链接或异常对象、任务已有终止档案引用、终止任务的档案已有内容或在途操作已保存冻结快照时，仍拒绝补写回执。成功占位后，同一 operation 只恢复原 run；接管意图确定未保存时仅撤销本次空目录，意图已写入但回执失败或结果无法核验时保留编号及材料。成功运行的目录跨任务退出保留，即使用户放弃归档内容也不删除占位。归档根连占位目录都无法创建时仍暂停接管，由 Agent 引导处理；目录已占位后快照写入失败才进入归档重试或明确放弃流程。

读取端继续接受既有 `<jira-key>-<timestamp-hex>-<random-hex>`、早期 `<jira-key>-<timestamp-hex>` 和 `run-*` 材料；生成端只产生当前两段式格式。本次同时改变归档待决策及原操作恢复语义，兼容处理统一见第 8 节。以后改变生成格式或冲突策略，必须结合实际场景评估工作分支、中央档案路径、授权、证据、清理恢复和旧工位读取；自动重试限于本节明确规定的一次，不增加随机消歧或持续重试。

固定回归必须证明：新生成值只有 Jira Key 与秒级时间段；既有三段式仍可读取且受 Jira Key 绑定校验；同秒同 Jira 编号占用冲突等待两秒仅重试一次，成功后固定编号，二次失败说明原因；权限及其他 I/O 错误不等待、不重试，保留原始异常且不写接管意图；接管意图确定未保存时撤销本次空目录，已写入但回执失败时保留占位。上述合同变化属于运行身份设计变更，应同步本节、生成器和身份回归测试，不能只修改其中一处。

## 3. 路径与数据合同

```text
<station>/
├── .agenticops/
│   ├── init.json               # 安装与接线归属、状态 epoch
│   ├── station.json          # 工位 ID、Project、Product Root 等稳定绑定
│   ├── current-task.json       # 唯一活动状态；空闲时 current=null
│   ├── operation.json          # 唯一未结束操作或最近操作的结果
│   ├── authorization.json      # 当前执行的授权，始终绑定 run 和范围
│   └── evidence/               # 当前执行的质量、CI、同步及本地事实
├── config/                     # 研发维护的持久配置和秘密引用
├── source/<owner>/<repo>/      # 完整独立 Git 仓库，跨任务保留
└── runtime/                    # 唯一运行配置、任务 Maven local、插件、日志及报告

<product-root>/.archive/<run-id>/
    ├── record.json             # 不变的运行身份
    └── result-<digest>.json    # 追加的已有任务状态、结果与覆盖缺口
```

`current-task.json` 固定包含 `schema_version`、单调 `revision`、`current`。`current=null` 表示无任务；非空对象包含 `issue_key/run_id/task_class/stage/outcome/engineering_baseline/task_repositories/terminal_proof/archive_ref`。`outcome` 为 `in_progress/completed/interrupted`；`archive_ref` 为空或固定为 `scope=product/run_id/digest`，实际路径始终由工位绑定的 Product Root 推导，不保存绝对路径或工位相对路径。只有 `current` 的有无决定工位是否占用，不能再在 station 或索引里重复存 occupancy。没有未完成 operation 且实际残留不影响接管，才可把无任务解释成可接管。本版归档引用存于 operation，归档不会设置 current 的 archive_ref 或禁止继续开发。

`task_store` 在读取和 CAS 写入前复用 `task-state.schema.json` 校验完整结构，冻结工程基线与任务仓库引用复用既有值校验；Gate 上下文仅调用同一只读入口。损坏、缺字段、未知枚举或非整数 revision 均拒绝，不补写默认值或改动原文件。合法历史 run 格式、空闲状态及恢复中间态保持兼容；结构校验不代表外部事实已验收，不新增 stage/outcome 自动转换，也不提供防篡改保证。

`engineering_baseline` 包含 `status=resolving|frozen`、Project/Profile 版本、解析输入、仓库条目与整体摘要；只有 frozen 可进入源码开发。`task_repositories` 是以仓库 ID 为键的变更与交付记录，引用唯一基线条目。质量、授权和 CI 状态独立留在 `.agenticops/`，都必须匹配 current 的 run/revision；不存在有效 current 时不接受活动证据写入。归档包含这些当前记录的必要脱敏副本，归档不是新的 Jira 或 Git 事实源。

`operation.json` 保存原请求、运行身份、精确处理对象、逐对象意图/回执及实际清理结果；大材料由现有 `operation-data` 内容寻址保存。退出结果分别记录 released、complete、residuals、resources，必要残留与明确保全路径随后续操作保留，不依赖正式档案。操作未完成时沿原 operation 恢复，已完成对象不重复删除；清理成功须同时核验 `done` 与 `cleanup_result.complete`；明确取消的清理另有 cancelled 标记，不冒充清理成功。

config 默认不随任务删除，只有用户明确选择的配置才进入清理。任务专用有效配置写入 runtime，正式档案只留脱敏配置、版本和秘密引用名称，不复制秘密。runtime 不以 run 分目录；暂存档案只用于原子发布，不属于第二个活动运行环境。`.archive/` 是 Product Root 的私有持久材料，目录权限为 0700、文件为 0600，不属于可删除的 `.local/`，update、rollback、setup 和 station purge 都不得删除。替换或删除整个 Product Root 前必须先保留或导出该目录。Maven 的安装级与用户级 settings 继续提供镜像、认证、代理和 profile；工位只将本地仓库定向到 runtime，不复制 settings 或共享任务构件。

### 配置按环境聚合

本节定义 epoch 33 的配置布局与读写合同。旧工位按原版退出与重建，新版初始化复用持久材料时先备份隔离旧布局，不直接加载旧配置。一个工位绑定一个项目，保存多份命名环境配置，共享本项目完整源码，只有一个活动运行现场。项目已由工位绑定确定，config 不再重复项目名称。环境名称使用小写字母、数字和连字符，由目录确定，不再维护一份可冲突的环境名称或项目绑定。

```text
<station>/config/
├── environments/
│   └── <name>/
│       ├── config.json          # 已保存的运行输入
│       ├── preparation.json     # Agent 维护的构建、装配及探测配方
│       ├── components/          # 按需保存的组件原生配置
│       ├── testing/             # 本环境的测试输入和数据源定义
│       ├── secrets/             # 本环境独占的秘密
│       └── drafts/              # 本环境唯一待采纳草稿
│           ├── config.json
│           ├── preparation.json
│           ├── components/
│           ├── testing/
│           └── secrets/         # 新增或轮换秘密的候选文件
├── shared/
│   ├── components/              # 明确跨环境共用的组件输入
│   ├── testing/                 # 明确跨环境共用的测试输入
│   └── secrets/                 # 明确允许跨环境共用的秘密
└── backups/
    └── <backup-id>/             # 不兼容旧配置的隔离备份，保留原相对结构
```

目录按需创建，不生成空目录树。config.json 保存节点、端口、架构、镜像、连接目标及资源参数等运行输入；preparation.json 保存 Agent 核验的执行配方，不要求用户填写。源码、工具链或架构变化后必须重新核验配方，保存不代表永久有效。components 与 testing 保存确实需要的输入文件，不复制生成配置；其具体格式及消费方式由 Project 定义。中央 Policy、Project 规则与通用模板仍留在产品根，不复制到 shared；机器级工具配置仍沿用原生工具约定。日志、报告、构建产物、有效配置及活动环境事实属于 runtime，不增加 config/current、环境池、独立源码或第二份任务基线。

#### 草稿与保存

每个环境只维护一份 drafts，既可用于首次填写，也可用于修改已保存环境。只有草稿的环境是未完成配置，不能部署；已保存环境有草稿时继续使用原配置。草稿缺项可复用明确的已保存输入，保存前应解析并校验完整候选组合；缺省不表示删除，删除对象必须明确。新增或轮换秘密写入 drafts/secrets，不得覆盖正在被正式配置引用的文件；草稿引用可以指向本环境已有输入或 shared，但正式配置不能依赖 drafts。

保存须校验配置、配方、组件、测试输入及秘密引用的一致性，再发布本次修改的组合；候选秘密及其引用一并转为正式位置。失败保留原已保存组合和草稿，中断后能识别并恢复未完成保存，读者不得把半更新组合当成有效配置。实现可使用最小临时发布材料，不增加长期版本库或审批台账。成功仅清除本次采纳的草稿，未采纳材料保留。保存不会部署、切换、重启或修改活动环境事实；运行状态必须区分已保存输入与实际应用的输入。原配置和草稿并存不表示支持并发编辑或多套运行现场。

#### 共享与引用

shared 仅收纳预期共同维护、共同变化的材料，不因文件暂时相同就抽取。环境对共享文件显式引用，不引入全局 defaults、多层自动继承、隐式覆盖或缺项回退；同一配置项明确选择一个来源。端口、节点身份、目标数据库及管理凭据默认归环境。禁止一个环境直接引用另一个环境的私有材料；确需共用时明确转为 shared。共享变更前从正式配置及草稿推导影响环境，不另建引用登记表；有无法读取或解析的输入时不得宣称影响范围完整。共享修改不热更新活动现场，下次显式应用时使用新的内容。活动进程只消费本次应用时生成的 runtime 有效输入或已注入的值，不直接热读或挂载可变的 config 文件；秘密有效副本保持受限权限，随运行现场按既有规则回收。

所有受管配置文件引用统一以工位 config 为根，例如 environments/dev/components/tm.yml、environments/dev/secrets/mongodb-uri 和 shared/secrets/development-license；禁止绝对路径、越界、符号链接逃逸及未允许的作用域引用。此规则不改变源码与运行产物各自的路径基准，也不要求原生工具直接理解这种引用；Project 消费者负责校验并转换成原生工具接受的输入，不修改业务文件格式冒充已有支持。

#### 秘密与生命周期

秘密按作用范围存入环境 secrets 或 shared/secrets；待采纳的新增或轮换秘密归 drafts/secrets。普通 JSON/YAML 只保存引用，不写密码、token 或带凭据的 URI；秘密目录权限为 0700、文件为 0600。原生工具只支持内嵌凭据时，由消费者在 runtime 生成受限的有效输入或向子进程注入，不能要求工具读取尚不支持的引用字段。日志、公开输出和正式档案不保存秘密内容，档案仅保留脱敏输入和引用名称。共享秘密的修改影响全部使用者，不能通过环境草稿隐式覆盖共享文件。

任务退出和普通运行清理默认保留配置、草稿与 shared。删除环境必须明确指定对象；活动使用中的环境先按既有授权处理运行现场。删除环境不连带删除共享材料，不自动回收无引用秘密；删除共享对象前核验全部正式配置及草稿，存在引用时先解除或替换，读取不完整不能判定无引用。删除配置不授权删除外部数据库、许可证记录或测试资源。路径身份、源码保护、结果未知和失败恢复仍遵循本合同的清理边界，不增加另一套清理入口。

#### 兼容与可复用验收

不兼容旧配置采用“先备份隔离、再建立干净配置、配置时优先复用”的方式，不要求新运行入口继续兼容加载旧布局。备份保存在 config/backups/<backup-id>/，保留原 config 下的相对结构、草稿和秘密文件，不递归包含 backups 自身；编号仅用于区分不覆盖的备份批次，不建立任务或配置版本状态机。备份是本机私有原始材料，不是 Product Root 的脱敏任务档案，不进入运行环境列表、配置继承或正式配置引用。目录权限为 0700，文件为 0600；不得把含秘密的备份上传到 Jira、Git 或公开日志。

先保存并核验备份的完整性和可读性，再从有效配置范围隔离已备份的不兼容材料；备份失败或结果未知时保留原件，不清空、不覆盖。范围应包含相关配置及其所需秘密，引用到范围外的材料不自动复制或删除，明确保留缺项。已有兼容的新配置不因整理旧材料被覆盖；新环境只加载 environments 与显式引用的 shared，不扫描旧路径或 backups 作为运行输入。备份默认跨任务、清理与工位注销保留，删除须明确指定备份对象，不因转换成功自动删除。本规则不新增退出检查或升级门禁，不把工位注销解释为所有进程已经停止；实际搬移仍不得破坏已知正在使用的材料，受影响时保留原件，先处理该使用关系。

##### 转换触发时机与处理顺序

转换仅在配置某个环境时按需触发，包括首次配置、继续填写草稿或修改配置时补齐缺项；升级、工位初始化和备份本身不触发批量转换，运行、状态查询和清理也不隐式转换。TapData 由 prepare-inputs 进入该流程；返回多个候选时用 --backup 选择返回的路径，不增加确认台账。

1. 先读取目标环境已有的新格式配置和草稿，复用已填写内容及有效决定；输入完整可用时直接沿正常配置流程继续，不扫描备份或重复转换。配置损坏、格式不明时先核实，不能将其视为空白配置覆盖。
2. 尚无配置或存在缺项时，从备份按环境名称、连接目标、组件和引用关系查找可复用材料，不按时间最新或名称相同盲选。没有匹配材料时进入正常新建或补缺流程；多份备份无法可靠选择或目标冲突时，展示脱敏差异，仅请研发决定无法判断的选择，再转换依赖该选择的内容。
3. 将明确匹配且可确定的输入转换为本环境 drafts 下的新格式，仅填补缺项，不覆盖已有正式配置、草稿、秘密或研发已填写内容。秘密复制到对应 drafts/secrets 并重写引用，不直接引用或修改备份；旧共享位置不自动证明共享归属。旧 preparation 只提供线索，由 Agent 对当前源码和工具链重新核验构建、装配与探测配方，不把内部字段交给研发填写。
4. 先校验转换后的新格式，汇总已复用项、冲突和缺项，再请研发补充确实缺失或需要决定的运行输入；秘密通过本地受限文件填写，不要求研发从头填写或重复确认已有有效输入。无法转换的内容保留在备份，不猜值、不将草稿标为可运行。
5. 研发补齐后，沿本节草稿保存和显式应用流程继续；转换不自动保存为正式配置、部署或切换环境。中断或失败保留备份、已有配置和草稿，不影响活动环境；继续时从现有草稿重新核对缺项，不覆盖已完成内容。

转换不迁移任务状态、授权、活动现场或旧验收结论，也不建设逐版本永久迁移器。

机器状态按第 10 节的功能合同核验，配置备份不能证明任务状态兼容。配置改造最初在 epoch 33 引入；旧模式退出重建只适用于对应旧客户端，不作为当前功能校验模式的升级前置条件。备份和运行输入转换由现役入口提供，真实应用启动仍须独立验收。项目旧路径与字段映射由 Project 指引维护，不在本合同复制。

可执行验收须覆盖：仅草稿的环境不可部署；修改及秘密轮换不改变现有活动现场；保存失败或中断不会发布混合输入；无隐式共享回退且能列出共享影响；引用不能越界、跨环境或泄露秘密；配置清理保留未授权及共享材料；单现场切换不复制源码；备份失败保留原件，备份成功后旧材料不参与新环境加载，重复备份不覆盖原批次；转换仅在环境配置缺项时触发，升级、初始化和备份不批量转换；完整配置直接复用，无匹配走正常补缺，多份候选先解决歧义；转换为草稿且不覆盖已填内容，只向研发索取缺项，秘密引用不指向备份，转换失败保留材料；备份与机器状态升级边界分离。文档审查不替代这些运行验收。

## 4. 两类仓库信息

### 4.1 完整工程基线

基线值的机器合同见 [engineering-baseline.schema.json](../../contracts/engineering-baseline.schema.json)。`workflow/engineering_baseline.py` 提供基线值构造、摘要校验、任务仓库引用和只读本地 Git 对象核验；`projects/tapdata/engineering-profiles.json` 定义完整应用的仓库集合，项目脚本 `engineering_baseline.py` 复用现役分支解析器。值构造中的 `status=frozen` 只表示输入清单已固化，调用方仍必须在接管操作中核验新鲜远端事实及全部本地 Git 对象后持久化；它不表示已创建仓库、已准备 runtime 或已绑定当前任务。基线模块本身不写状态；生命周期由 station 与 task.py 入口持锁编排。

每个 run 只有一份冻结工程基线。条目至少包含 `repository_id/origin/ref_kind/ref_name/commit_sha/resolution_source/rule_version/path`。Profile 决定完整应用源码集所需仓库，Project 的现役仓库目录仍是 origin 唯一来源。解析结果中的 current、展示回退、未核验或 unresolved 不能作为可执行基线。所有条目解析成功并核验 Git 对象后，一次固化全清单摘要；不能把部分准备冒充完整源码集，也不能把完整源码集冒充可运行环境。

首次接管从可信 origin 准备缺失仓库；已有仓库先核验路径、origin 和洁净度，再 fetch 明确引用并检出冻结 SHA，不改工位之外的主工作树。若冻结引用是 branch，则检出只由 AgenticOps 管理、名称含原引用与冻结 SHA 的本地基线分支；tag 和指定 commit 保持 detached。独立仓库保留任务分支和提交，退出时保留原分支、HEAD、索引及全部源码修改，空闲刷新和下一次接管分别核验实际源码。缺失或冲突不覆盖原仓库；只重试该操作能够证明归属的创建或同步步骤。

准备期间可只读分析，生成物只写已登记 runtime；未冻结完整清单前不能开始代码修改或签发完整工程验证结果。修改实施线需要显式终止并清理原 run 后新接管，不在同一 run 偷换基线。恢复已有 run 保留其 SHA；新 run 如需复用已有分支，必须显式提供历史基线与预期 Head，核验后将该历史基线作为该仓唯一基线，并披露与其它仓当前解析结果的差异；兼容性由实际工程验证证明，不能自动继承旧验收。

### 4.2 任务变更与交付

每项包含 `repository_id/baseline_entry_digest/work_branch/target_branch/approved_scope/verification_method/observation/deliveries/disposition`。不重复保存第二个可变基线 SHA。`observation` 记录实时 HEAD 与源码指纹；指纹涵盖 tracked 差异和未跟踪源码，不把生成物混入授权源码范围。基线、HEAD 和 PR Head 的含义不同。

任务变更仓库可在源码修改前登记，最终可以无变更；工作分支只在声明范围内使用。配套仓的 branch 基线显示为受管本地基线分支，tag/commit 基线保持 detached；两者都可产生声明的构建产物，不得把分支或 detached 当文件系统只读保证。任何配套仓源码变化都必须先加入任务修改范围。

新增修改仓库使用内部 `scope_change` 操作，不增加用户操作种类：先核对冻结条目和洁净度，持久化意图，登记范围，准备工作分支，回读实际 branch/HEAD 后提交绑定。新分支固定为 `<git_name>/<run_id>`；`git_name` 在工位初始化时从全局 Git `user.name` 校验后一次性写入 `station.json`，缺失或不合法时由研发显式补充，后续不跟随机器配置改变。创建前若本地或远端同名分支存在则失败关闭。续办保留接管时核验的既有分支，不重命名。准备分支不等于授权修改代码；现有实现授权如因范围变化失效，先撤销，再重新确认和签发，不能在失败中保留旧授权。原有仓库的授权修改不能因新增仓库被擦除。中断按同一意图恢复。

新工作分支名称不由项目规则或用户自由指定；普通新分支由工位身份和 run 唯一确定。首版每个修改仓库一个工作分支、一个明确 PR 目标。一个任务可跨多个仓库各交付一个 PR；需要同仓多版本回补时另行明确后续工作项，不在当前工位隐式切版本。替代 PR 要记录替代链并以最终有效 PR 的证据结案，不能自由文本豁免未交付成果。

## 5. 操作状态与接口语义

新接管使用 `facts.station_contract=3`。当前 station epoch 以机器契约为准；当前功能校验模式按第 10 节核验旧状态，不能仅因来源 epoch 不同要求退出。一次确认、目录回收、源码成果与外部处置以第 7、8 节为准。

编码前的新任务使用 `source-readiness` 刷新任务目标分支引用。准备先将旧证据标为 refreshing，逐仓保存 fetch 意图和结果，最终记录本次 observed 快照；失败重试安全地刷新同一 run 的证据，不推进阶段。检查全部工程身份、工作区、任务分支、冻结基线祖先关系和目标分支；ignored 内容不因未登记就阻塞源码准入，退出时仍须确认处置。等同基线时可进入授权；目标正常向前推进时，用户可用 `--confirm-digest` 与 `--decision-ref` 明确选择保留冻结基线开发、在 PR 前按项目规则同步，或退出后重新接管。分叉、回退、缺失或不可信引用拒绝。grant 及进入 implementation 时重新回读本地与远端，授权绑定 source_readiness_digest；准备过程不修改冻结基线或工作分支内容。已开始编码后不要求工作区始终洁净，也不重复以本检查替代后续代码与 CI 证据。

接管与退出使用同一持锁操作记录。接管在创建操作前检查工位身份、source 状态、runtime 残留及前次资源；可提前发现的问题不产生悬空操作。开始 clone/fetch/checkout 后失败沿原操作恢复，已有任务可转入任务清理，不生成新 run 冒充恢复。

清理先由脚本展示实际范围和源码保全缺口，Agent 将范围、不可再生材料及处置选择说明给研发，复用有效授权，不要求研发手写计划或逐文件批准。程序绑定本次预检摘要和决定来源；任务是否业务完成与清理独立，清理不改写 Jira、PR 或交付事实。

## 6. 完成事实与交付核验

### 从任务事实接续

Jira 任务是跨版本接续入口，GitHub 保存远端分支、提交、PR 与 CI 事实，Git 核验本地代码；本地 run/op、授权与质量状态不是跨 epoch 交换格式。旧版在退出前将有效方案、决定、仓库与历史基线、完整 Head、验证来源、环境缺项和未完成事项记录到现有 Jira 字段/评论及 GitHub 对象；未推送源码或本地证据须先持久化或明确保全并记录位置，不以链接文本证明对象存在。

原版退出并 purge 后，新版 Agent 从 Jira key 读取并实时核验 GitHub 成果，以现有 continuation-input 和仓库登记入口建立新 run；不读取旧状态、不继承旧授权或 PASS、不跳过本版检查点。历史设计决定在对象与范围未变时可作为真实确认来源；历史报告只保留原执行对象，按现役合同核验适用性或重验，不改写执行 SHA。续办旧分支沿用其真实历史基线，不用最新目标分支冒充起点。旧记录缺项先从代码、PR、CI 和可访问历史材料核实，再由 AI 协助研发补齐仍无法确定的输入。

该机制不新增持久状态字段、阶段或代际映射，跨一个或多个 epoch 使用同一路径；新规则提出旧材料未覆盖的要求时只补受影响缺项。正式档案仍为不可变保全证据，源码附件允许经 Git 核验取回后参与新运行，不重新激活旧 run。操作见[从 Jira 任务接续](../usage/task-authorization.md#从-jira-任务接续)。

完成入口在同一 run 中核验全部工程仓库，包括配套仓；源码 dirty/untracked、未经登记的本地变更或未处置提交阻止正常完成。生成物按项目路径及生产记录分类；未知文件不能默认归生成物。基线到最终候选无源码差异才可记录 no_change，候选必须洁净；仅“没提交”不算无变更。

每个有效交付条目保存 `repository/pr/target_branch/candidate_head/pr_head/merged_at/merge_commit/readback_ref`。正常路径要求最终本地候选 Head 与 PR 合并时 Head 相同，GitHub 已合并且目标等于登记目标，记录实际合并结果；项目使用的 merge/squash/rebase 均按服务端合并事实核验，不能要求原 Head 必为目标分支祖先。必要时核验 merge_commit 在当前目标历史中；目标历史已被改写或无法解释时停止，不猜测合并策略。

旧 PR、被替代 PR、目标错误或本地候选比已合并 PR 多出提交都不能完成。合并后需同步 PR Head 的，必须保持本地洁净且符合已有同步规则，并重新核验候选验证证据，不伪称新 Head 已测。同仓多有效目标不属于首版自动完成路径。

除了 PR，继续核验 Project 现有质量、CI、关联测试及适用的发布验收；任务类型未配置的验收不能凭空要求，已配置要求也不能被“PR 已合并”替代。completed 是本地核验结果，Jira 同步结果另存，不能假称已改 Jira。外部写入未知先回读原操作，清理不再次发送。

## 7. 清单与退出职责

数据分类与功能写入责任引用[数据生命周期规范](../development-data-lifecycle.md)。当前源码将生命周期清理收敛为同一执行链的两个范围，操作命令见[清理与退出](../usage/task-authorization.md#清理与退出)。

| 操作 | 当前源码行为 |
|---|---|
| 清理任务 | 资源停写并保全或明确放弃本地成果后，删除 source、runtime 和本地任务材料；保留 config、初始接线和登记 |
| 清理工位 | 复用任务清理，再删除工位内用户配置及其它积累；保留当前初始化清单中的接线和基础身份 |
| 任务归档 | 建立 Jira 持久接续点并核实代码远端引用，不释放任务；本地快照为尽力保存的副本 |
| 工位注销 | 清理或原操作结束后移除受管接线和登记；不自动代替源码处置，不删除远端和共享对象 |

归档不是清理前置。需要保留的方案、进度、代码和唯一数据必须先可靠保存；用户可明确放弃本地成果，但 Agent 须同步纠正可恢复进度，不能把已放弃代码描述为仍可恢复。源码预检核对真实远端、工作区、暂存区、本地引用、stash、忽略文件和外部 worktree，不用 tracking refs 证明已推送。预检不能识别全部业务价值，材料保全决定由 Agent 与研发完成。

项目清单只声明可再生路径和资源归属，不提供任意删除脚本。删除源码不执行逐仓 reset、切分支或逐分支删除，按已确认区域处理；远端分支、PR、中央档案和共享缓存不在范围内。外部 worktree、挂载和特殊对象先保留并核实。非源码区的独立 Git 仓库列入预检，需明确处置；不能因临时克隆残留永久阻塞清理。初始接线被修改或缺失时，沿本版 repair 核实恢复，再清理工位，不另建一套接线生成器。

Docker 收尾复用工位标签发现容器与网络，runtime 丢失仍能发现。驱动或回读异常保持待处理；关联数据卷时保留容器定位线索，由 Agent 核实唯一数据与独占/共享关系后处理。不删除共享镜像、卷或外部服务，清理不依赖部署健康或构建成功。

## 8. 脚本执行、异常接力与恢复

程序在工位锁内核对执行占用、原任务及预检范围，先停止相关写入资源，再删除用户已确认的区域。任务清理保留配置不是残留；本次应删除而未完成的对象是残留，不可报告完成。资源未完成时保留任务和原操作，不接新任务。停止资源可能刷新日志或数据库，整区处置覆盖停写后的最终内容；源码仍须符合已核实现场。

每个区域先记录意图，再移入原操作私有清理目录后删除。递归操作使用目录 FD，不跟随链接、不跨设备；中断只处理原目录身份。原路径后来出现的新内容保留，不沿完成回执再次删除。私有目录和实际结果核验完成后清除活动材料，最后回收任务正文缓存并释放执行占用；只保留当前操作的最小重试回执，不形成归档数据库。

任务解绑与最终材料回收不是跨文件原子事务。解绑后回收中断时，结果如实显示 released，原 operation 仍为 finalizing，执行占用尚未释放，新任务不能绕过；沿原操作继续回收后才报告 complete。已完成清理的重复回读不重新占用工位，也不释放后来的接管者。

尚未开始目录删除且没有未核验资源步骤时，可以按明确决定取消原清理，保留任务后重新预检；已经停止的资源不会自动启动。目录删除已开始则沿原操作处理，不能用新操作扩大范围或丢失恢复记录。异常由 Agent 在原授权内修复外部输入或核实处置后继续，不手改状态、制造回执或伪造通过。

归档等待原生 Jira 正文回读；结果未知时先核对原操作，不能改走清理。明确尚未发送才可沿 not_sent 决定取消；归档操作登记后、正文尚未持久保存前中断，原操作重试重新核验并生成正文；已保存的正文保持不变。已回读成功的 Jira 接续点不会因本地快照写入或格式异常变成未保存，本地异常保留并报告警告。归档后仍可继续工作，后续修改须再次保全或明确放弃。归档输入与回读协议唯一见[持久接续点操作](../usage/task-archive-and-resume.md#持久接续点操作)。

### 兼容边界

整区清理计划 schema 8 和 Jira 协调曾随 epoch 38 引入。当前功能校验模式沿第 10 节判断本次所需合同；来源 epoch 不同不要求先退出/purge。无法解释的旧在途清理仍保留原意图并按原合同收尾，不将历史清理计划改写为新计划。历史归档保留，具体能力以实际安装提交为准。

## 9. TapData 源码 Profile 与运行边界

完整应用源码集 Profile 保留机器 ID `full-application`，引用 `projects/tapdata/repositories.json` 仓库 ID，不另存 origin；首版集合为 tapdata、tapdata-common-lib、tapdata-connectors、tapdata-connectors-enterprise、tapdata-enterprise、tapdata-license、tapdata-web、tapdata-application、hazelcast，均位于 `source/tapdata/<repo>`。t-layer3-test 保留项目登记，是明确启用的验证依赖，启用后必须在基线冻结前加入；docs/docs-en 已解除 TapData 项目登记，不参与项目仓库准备和分支对齐。解除登记不删除既有本地仓库、Git refs 或任务材料。其它类型任务的精简 Profile 需单独明确，不能偷偷缩减完整应用源码集。

分支解析复用 `version-branch-alignments.json` 与现役解析器规则，输出明确 ref/SHA；现有展示回退和 keep-current 结果若无法提供确定执行依据，必须配置明确 ref 后再冻结。产品版本与模块分支不机械同名，目标分支另行登记。已有基线外仓库需要加入时，应先确认 Profile 范围，在冻结前补齐；冻结后发现遗漏而必须扩展完整工程时结束本次处理并明确清理重接，不能修改同 run 清单冒充原环境。

现役 `engineering-profiles.json` 声明源码集合、修订与可选仓库；生成目录统一由项目 `station-clean.json` 声明，不在工程 Profile 重复维护。Profile 不是可执行的应用配方。`source_prepared=true` 表示接管已核验所选仓库并检出冻结源码，不表示依赖安装、工具链、有效配置、数据库、构建产物或应用健康已验证。runtime 的建立和归属登记只是空运行目录准备，不生成这些证据，也不授予实施权限或推进任务完成。

自动化构建、启动、停止及健康检查配方属于后续独立范围，待明确真实场景和目标分支后再设计；当前不增加未消费的 `actions/toolchain_requirements/health_checks` 字段，不以空配置声明能力。工具版本、Maven profile、Node 包管理器须从目标分支和已确认环境取得，不猜值。源码准备的验收与实际应用验收分别记录；本边界不将历史未完成的应用运行验收改为通过，也不豁免业务任务本身要求的构建、联调和产物加载证明。

现役资源登记通过 station_resources.py 接收 directory/process/external/source-disposition 数组并绑定 run；file 只用于已有工具的证据登记，不替代目录归属。生产前创建生成目录，运行资源与可选分支/PR 按第 7、8 节分别处置，归档后可继续开发，正式快照不改写。

任务方案确需实际运行时，按[TapData 构建运行指引](../../projects/tapdata/runbooks/build-test-and-local-run.md)核验环境并执行：FE/TM 工作目录在 runtime 中分开，连接同一已确认 Mongo 环境，端口和 backend_url 必须互相匹配；记录 TM 可用、FE 连接成功、适用时 Web 可访问，并证明本次 connector/Jar 的生产与实际加载文件内容一致。未具备数据库或凭据只报告环境缺口，不伪造启动成功。上述为独立运行验收要求，不是 takeover 已执行的动作或当前模板已可运行的声明。

## 10. 升级与恢复

### 当前实现的兼容与切换边界

当前机器清单声明 `validation: feature`：产品切换不再仅因 epoch 不同要求退出任务或清空工位，各功能在正常入口校验本次操作需要的合同、身份与事实。epoch 保留为来源与风险信息，已有工位 init.json 不被抬成新版值；刷新接线保留来源代际，不将刷新成功当作任务验收。旧安装或回退目标没有该声明时，仍执行其原 epoch 合同；不同 epoch 且有登记工位时不得回退到旧模式。

版本切换继续核验来源、完整 SHA、Git 关系、干净安装、产品记录、全部登记工位和独占租约。有工位的跨 epoch 切换与启动侧更新均须核实停写并声明 `--writers-stopped`，当前启动流程覆盖活动任务恢复，经研发确认原/目标 SHA 及登记范围后，在兼容、租约和停写核验通过时切换；不因 epoch 不同单独阻塞，不转换任务数据。Bootstrap 不读取或转换任务、授权、配置或运行数据，不改变归档与清理语义。旧客户端无法识别新清单时，从独立、已经审查和验证的候选启动同一 installation_update.py，明确原安装根和原/目标 SHA；不复制程序覆盖安装，也不手改 epoch。

### 修补后继续现有任务的目标设计

已确认目标：启动或恢复时检查新版，Agent 说明更新内容、共享安装影响及停写要求，研发确认后切换并重新加载指引；暂不更新可继续当前任务。依赖修补遵循功能所属合同，不另建升级迁移流程。跨工位恢复由 Agent 整理持久事实，通过所属接口复核并接纳已完成事项，只补缺项；既不机械复制旧阶段，也不一律从头重做。归档、清理和环境收尾通过数据所属功能接口协作。下面的当前能力不代表这些目标已经全部完成。

当前已支持符合现行合同的旧任务原工位接续：保留任务/run、阶段、源码、历史质量事件和授权文件；授权是否仍有效由当前检查点判断。缺少新增的 Jira 接管协调时，写入口明确要求 coordination check/prepare/complete；Agent 回读真实 Jira 并完成必要交接后重试原功能。同版本正常自产状态不能要求 AI 修补程序自身缺陷。

正常入口按本次操作检查依赖。输入、配置或环境缺项由 AI 核实补齐；方案调整复用 replan、质量补充复用 review/apply、环境配置按其现役入口处理。程序复查结果，不复制旧 PASS，不根据阶段名推定新版验收通过。没有安全采用入口或身份/事件含义无法确认时保留原件，只暂停依赖动作，沿[异常接续](../maintenance-guide.md#确定性执行与-ai-接续原则)反馈；不提供万能状态导入器或逐版本迁移器。

支持范围与限制：已用 main c19087d（epoch 33）的程序生成任务与质量记录验证读取、缺协调拒绝及补齐后同 run 继续；这不证明任意历史状态可执行。升级前 Agent 必须核实在途操作及外部未知结果。旧 release/work-clean、旧清理快照等当前无法解释的未完成操作应先在原版回读收尾，不能在升级后改名、删除回执或交给新版猜测执行；未具备安全收尾路径时保留原安装，不切换该共享安装。已完成操作保留身份、请求摘要与回执校验，旧清理计划只作历史查阅，不按新版计划执行；未完成操作继续校验当前执行合同。旧 Hook 退役仍须显式确认受管文件迁移。进程和会话不热更新，切换后采用新版指引再继续。

任务状态已提供 [data inspect/preview/apply](../../workflow/task-data.md)：按当前合同诊断，支持经确认的保值字段改名与版本采用，保护原 run、revision 和全部已有值，原件由任务模块保全及回收。不接受任意状态覆盖或补造业务事实；未知语义、旧多任务布局及缺少事实仍需所属功能或维护面处理。

数据、配置和运行环境全部自动修补不是已实现能力。有效现场直接使用；不能恢复的秘密和数据由研发补齐或明确处置。功能新增外部依赖时，必须同时提供差异说明、补齐入口及复查继续路径，统一要求见[维护规范](../maintenance-guide.md#外部依赖检查与修补继续)。

### 同 epoch 恢复与跨 epoch 切换目标设计

本小节仅适用于未声明 validation: feature 的旧安装、旧模式目标及原版本维护补丁；其中跨 epoch 必须退出/purge 的规则不适用于新版功能校验模式。它不是另一套通用修补流程。

本节维护原版本退出修复与版本切换的 Bootstrap 边界；源码入口与[更新指引](../usage/update-and-rollback.md)一致，绑定安装的实际能力须单独核验。目标是解除“旧版无法归档，修复版跨 epoch，升级又要求先归档”的循环，同时保持旧任务由匹配版本退出、新版不解析旧状态的边界。恢复原有行为的补丁优先保持同 epoch；改变持久字段、状态含义或恢复语义的变更仍须提升 epoch，不为放行旧现场隐瞒不兼容。

#### 恢复版本选择与职责

当前版本可以正常退出时，直接在原版归档并 clean/release、purge，再切换新版，不强制安装中间版本。确需修复时，Agent 用原生 Git/Jira/GitHub 核对具体缺陷、补丁完整 SHA、适用原版本、审查及回归证据；同 epoch 和提交时间都不证明归档能力已修复。优先选择原跟踪分支上已验证的兼容补丁，不自动选择所谓“本 epoch 最后版本”，不维护新的逐 epoch 版本映射或修复登记表。未找到适用补丁时保全现场并继续准备不依赖退出的新版验证，不把备份当正式归档。

根入口只转发生命周期参数；Bootstrap 负责目标 Git 引用、安装范围和版本记录，仍只读取支持的产品配置、兼容清单及工位登记，不读取 task、operation、runtime 或旧授权。旧任务退出由原版本 Workflow 负责，Agent 通过原生能力补齐 Jira/GitHub 接续材料。恢复补丁和新版不兼容功能分别形成候选、审查及验收，不能把新版改动混入旧版补丁。

#### 原通道定点更新与原版本维护恢复

`agenticops update --to-ref <完整SHA> --expected-current-ref <完整SHA>` 只用于已安装产品：目标必须在记录的 origin/tracking_branch 可核验历史上，原提交为目标祖先且目标为远端通道 tip 的祖先；仅 fast-forward，不换通道、不覆盖修改。省略参数保持现役更新语义，源码模式不增加定点更新。跨 epoch 仍要求可读取的空登记；目标与原版本 epoch 相同才可保留旧工位继续退出。历史不足或无法证明引用关系时停止，不用当前分支名或相同 epoch 替代 Git 核验。

如果缺陷在现役分支提升 epoch 后才发现，同 epoch 补丁可能只能在原版本维护分支产生。`agenticops recover-install --source-branch <明确维护分支> --to-ref <补丁完整SHA> --expected-current-ref <原安装完整SHA>` 作为明确的原版本维护操作，复用同一 Bootstrap 更新实现，不是普通 update 的强制选项。仅接受 installed 模式、记录的同一 origin、原提交向前可达的目标及目标所属的明确维护分支；状态兼容性遵循本节 epoch 合同，原版本与补丁必须同 epoch，两端清单缺失或无效均拒绝；正常合并的第二父链不构成拒绝理由。具体退出缺陷是否修复仍由候选审查和回归证明。目标分支及候选未经核验、权限或授权不足时不应用。

恢复执行必须满足产品树干净、HEAD 与产品记录匹配、完整引用及安装配置可信；保留 tracking_branch、stations.json、正式档案和全部工位数据，只按正常生命周期更新 current_ref、previous_ref 和可再生版本提示。不覆盖其它维护修改；脏安装保留并先独立处理，不自动 stash、reset 或吸收无关修改。恢复模式不自动修复注册表、抬改工位 epoch、清理业务内容或提交推送。

原版本维护补丁偏离原跟踪通道后，普通 update 可能因分叉继续拒绝，这是预期保护。旧任务退出且全部 purge 后，在独立干净 Product Root 安装原通道新版，明确复用原 source/config 并从 Jira 接续；旧安装及其 `.archive/` 保留并记录位置，不强制合并维护分支或改写历史。正常原通道内的兼容补丁则在退出后继续普通 update。恢复分支只为具体旧版本缺陷服务，不承诺维护所有历史 epoch。

#### 预检、首次旧客户端与执行顺序

上述两个入口支持 `--check`：可以获取所需 Git 对象和远端引用，但不切换产品代码、不修改生命周期版本记录或工位。输出绑定 Product Root、原/目标完整 SHA、原/目标 epoch、目标来源、通道或维护模式、全部登记工位及无法核验的缺项，并说明当前只是预检、应用补丁还是完成最终版本切换。预检不是授权；执行重新获取必要事实并在 lifecycle.lock 内核验，目标变化或范围扩张不得沿用旧决定。

旧根入口没有这些参数时，从独立、已审查并验证过的原版本补丁候选启动同一个 Bootstrap 实现，明确传入原安装根、原/目标 SHA、维护分支及恢复模式。启动实现和其 Bootstrap 辅助模块来自该受信候选，不依赖旧安装已经拥有新入口，也不执行未审查远端脚本；只读旧产品配置、清单和登记，调用同一生命周期写入逻辑，不复制文件覆盖安装或新增第二套清理 Runtime。仅支持实际回归过的旧配置格式；格式不支持时拒绝，不声称新协议追溯保护任意旧客户端。候选尚不可用时不得把目标命令作为当前恢复建议。

应用同 epoch 补丁前，暂停本 Product Root 全部会加载产品代码或写入任务的 Agent、脚本和在途 Workflow 调用，并以原生进程/操作事实核对；有登记工位时，显式定点或维护恢复执行须声明 `--writers-stopped`，该声明不认证操作者或替代真实核验。生命周期锁阻止新的受管操作，不声称撤销已启动进程；无法核验停写时停止产品切换。业务环境的停写和资源处置仍沿原退出计划，不由升级器扩大范围。共享安装必须覆盖全部受影响工位；仅授权一个工位时不擅自更新共享产品根。

补丁应用成功后先回读实际产品 HEAD、版本记录和兼容清单，再同 epoch doctor/repair 刷新接线并核验旧任务和原操作保持原含义。按原版本合同执行 clean/release 并核验实际结果，然后逐工位 purge；旧版材料缺项、残留和归档失败按该原版本合同处理，不能套用本候选的删除语义；授权撤销与解绑必须回读。archive 单独成功、任务完成或一个工位已退出均不足以允许跨 epoch 切换。全部登记为空后才更新或干净安装目标版本、init，并通过 Jira/Git/GitHub 重新核验接管；新 run 不继承旧授权。

#### 安装中断与失败边界

普通入口继续拒绝 HEAD/产品记录不一致。显式 `--resume` 必须同时提供原/目标完整 SHA，并保留原模式和目标来源，复用同一 Bootstrap 实现恢复安装元数据；实际 Git 切换的 reflog 记录模式、来源分支及原/目标 SHA，不增加任务或永久升级状态，不成为任务状态修复入口。只接受下列由原操作证据及实际 Git 核验支持的组合，未知值、目标漂移、权限变化或新修改均停止：

| 实际 HEAD | current_ref | 处理 |
|---|---|---|
| 原 SHA | 原 SHA | 重新核验后从安装范围检查继续 |
| 目标 SHA | 原 SHA | 核验 Git 切换记录确为原 SHA→目标 SHA 的同模式/来源 reflog 标记、目标和同一请求后，补齐范围并写版本记录，previous_ref 设为原 SHA |
| 目标 SHA | 目标 SHA | previous_ref 必须是原 SHA，并核验同模式/来源的切换记录；仅补齐安装范围和登记版本提示，不覆盖 previous_ref |
| 其它组合 | 任意 | 拒绝，不猜测成功或自动回退 |

初次执行要求记录与 HEAD 匹配；原/目标相同时不制造更新、不改 previous_ref。每个写入边界回读实际结果；版本提示是可再生接线信息，不代表任务已验收。恢复请求及结果保留在既有维护材料或 Jira，不新增工位字段或永久升级状态机。产品配置字段、工位 epoch、既有任务确认和恢复语义保持不变，因此这一生命周期能力本身不要求提升 station_state_epoch；具体退出补丁仍需单独证明兼容。

网络、磁盘、权限、记录损坏或外部结果不明只暂停依赖步骤，保留原现场和已完成材料。无法兼容修复时，不强行保持 epoch 或让新版清理旧任务；旧版本继续维护恢复，独立新版只能接续已核验成果，旧现场保持待恢复。合并、发布、Tag、保护分支写入、强推和历史改写仍需独立明确授权；应用恢复候选与真实删除也按具体安装和退出范围授权，不因用户提出设计自动执行。

#### 验收与维护成本

复用现有 product.json、stations.json、lifecycle.lock、Git 引用、Bootstrap 模块与原 Workflow 退出验收；新增仅为定点/预检、明确原版本恢复及有限安装续接参数，无新依赖、Policy、Runtime、epoch 支持列表或任务迁移器。[PROD-001](../user-stories/v1/prod-001-install-and-connect-agent.md#升级恢复目标验收)维护正常通道、维护分支、首次旧客户端、共享工位和中断场景；原补丁的旧请求、草稿、正式档案及原操作恢复独立回归。正式候选使用 affected staged 选择器，Bootstrap 和共享入口影响回到固定完整四项。真实旧工位退出与新版本接管单独提供证据，不以设计、模拟或安装成功宣称恢复成功。

## 11. 可复用验收合同

| 场景 | 必须观察到的结果 |
|---|---|
| 清理任务 | 核实保全或明确放弃后删除源码与任务运行数据，保留用户配置；远端分支、PR 和持久档案不变 |
| 清理工位 | 同一执行链额外删除工位内用户数据，保留当前初始化接线与登记；修改过的接线先修复核实 |
| 业务状态 | 未完成任务清理不伪造完成，已完成任务不重跑交付验收；归档独立，放弃本地成果不强制归档 |
| 源码保全 | 未提交修改、未推送引用、stash、忽略唯一文件、嵌套或共享 Git 明确核实；未确认不删除 |
| 路径与资源保护 | 不跟随链接、不跨挂载、不误删外部工作树、共享缓存、共享卷或其它工位资源 |
| 写入者未停止 | 保留任务与操作，资源处置不要求构建或部署健康 |
| 中断恢复 | 沿原操作继续删除原目录，新出现内容保留；最终材料回收中断保持 finalizing 和执行占用 |
| 初始接管中断 | 即使尚未形成 current，也能按原 takeover 的 run 交接清理，不伪造任务状态 |
| 取消与重复 | 删除开始前且无未知资源步骤可明确取消；已完成清理重复回读不重新占用或释放后来的执行者 |
| 再接管 | 清理成功后可由新会话正常接管，配置按范围保留或重新补齐，不继承旧授权与 PASS |
| 工位注销 | 活动任务或未完成操作时拒绝注销，不自动扩展为源码删除；清理完成后可注销 |
| 版本切换 | epoch 不同必须原版退出并 purge 后重建，不在线迁移旧任务 |

完整验收与真实工位验证分别提供证据；测试和安装成功不代替真实任务退出事实。当前候选的实际通过范围记录 Jira，不以本文列出场景宣称已经全部通过。

## 下载缓存的准备与兼容

源码池为独立 bare 仓库，仅缓存远端分支和标签，不保存任务、授权或验证事实。每个仓库使用独占锁串行刷新及传输；首次下载和工位克隆均先在本次临时目录完成校验再发布，失败可按原操作重试。工位使用本地 Git 传输并禁用本地硬链接优化，origin 恢复为可信远端，后续推送仍指向真实仓库。源码池可以跟随远端更新标签，工位已有标签冲突仍停止，不能强制覆盖。

初始化仍只生成空工位接线；接管确定 Project Profile 后才按所选仓库准备源码。缓存不可用时停止当前源码准备，不绕过先入池的顺序；已经完成 fetch 的恢复直接核验工位已有引用，不刷新缓存或重新解释历史基线。工位 purge 不清理产品根缓存，也不清理旧版源码池。

本次只改变对象下载路径，不改变 `.agenticops/` 字段、clone/fetch 意图与回执含义，下载路径变化本身不改变 epoch。同 epoch 已完成步骤和未完成 fetch 可直接恢复；工位不存在但 clone 已回执仍拒绝重建。缓存不是工位状态的迁移来源。

## 同周期方案修订

`replan` 是当前任务内的受控修订，不创建新的任务生命周期或 run。只允许进行中的 design_review/implementation/pr_review/ci_validation。准备输出绑定当前 revision、完整任务摘要、各源码指纹、远端工作分支、项目目录和新仓的精确引用；确认后原子登记操作，先撤销授权，再准备新增仓，最后写入 design_review。所有原仓、PR 观察和交付历史保留，不能从登记中删除有变更的仓库。

工程基线仅追加 Project Profile 许可的可选仓。`extension_history` 保存前版摘要、新条目及确认引用，revision 单调增加；核验时重建摘要链，已有条目不允许修改。新增工作分支统一使用本 run，原有续办分支名称不改变。新仓必须洁净，原仓允许保持已确认的 dirty 指纹；仓库就绪与授权检查复用同一指纹，发生漂移须重新核对。构建产物、运行资源和原生工具权限仍按原规则处理。

操作中断沿原 operation_id、输入和确认引用恢复。current 写入后只完成回执，不倒退已生效方案。写入前可以 abort，保留原方案和所有已下载源码，撤销状态不复活；部分仓库的来源与指纹留在现役 current，供清理预检核对，不能当成已准备成功。仍未完成检出的源码可能需要在下一次使用前按实际现场完成准备，不能猜删或声称已可用。

质量日志不改写。受影响检查项通过本次修订摘要失效，未受影响项保留原结果和决定；任务级汇总按当前方案重新核对。新方案确认可复用本次真实人工决定的来源，不因内部摘要改变再次询问相同事实。旧报告仍对应原代码和用例，不能标记为新版本通过。兼容边界由机器清单统一声明，旧工位先原版退出并 purge。

## 源码指纹与兼容边界

质量证据、扩仓及中断恢复共用工作目录指纹。干净仓库返回精确 HEAD；dirty 仓库使用版本域、禁用外部 diff 与 textconv 后的 tracked 二进制 diff 的 SHA-256，以及按文件名字节排序的未跟踪记录生成组合摘要。每条记录明确编码文件名字节长度、原始文件名字节、普通文件或符号链接类型、普通文件的可执行标记，以及内容或链接目标的 SHA-256，防止名称与内容边界不同却得到相同输入。普通文件内容按块读取，符号链接只读取目标字符串，不跟随目标；本地指纹不是防篡改证明。

指纹和退出状态由所属功能按当前合同校验，不通过重新哈希伪造已有确认。跨 epoch 是否需要退出重建遵循第 10 节；功能校验模式保留仍有效的原 run 材料，旧模式目标仍要求原版退出并 purge。

### 目录归属与操作身份

长期目录登记表达生产归属；执行器按本次实际对象记录 device/inode、父目录身份及仓库 origin，并在处理前复核。链接、挂载、特殊对象、身份漂移和无法确认停止的写入者只使受影响对象保留。原操作不吸收新范围，已完成目录重新产生内容交由用户决定。原生处理后沿 `--resume` 回读原操作；已完成对象不重新删除，不以新计划扩大旧操作范围。

## 工位绑定的统一读取

`workflow/station_context.py` 统一读取和校验工位绑定，格式以 `contracts/station.schema.json` 为准；Bootstrap 生成与诊断、项目规则读取及项目工具复用该入口，不独立维护工位 schema 版本或兼容列表。该模块只提供确定性读取与判定，不写入、修复或迁移工位状态。文件格式版本与状态代际职责不同：格式约束来自对应 schema，代际由唯一 `station_state_epoch` 契约声明。

跨版本切换仍由 Bootstrap 比较原版本与目标版本 epoch 和工位登记，不解析旧任务；工位分析入口读取绑定后复核 epoch，任务状态写入在获得现有锁后重新核验绑定与 epoch。项目规则的上下文读取复用一次绑定快照，持锁复核不能被入口读取替代。直接替换产品版本后旧代际仍被拒绝；错误报告区分绑定格式错误与状态代际不兼容，不从 schema 版本不符推断必须执行任务迁移。

该收敛不改变有效持久字段、路径或恢复语义，保留当前 epoch；合法既有工位与任务继续可读写，损坏或不符合现役合同的绑定拒绝且不自动补写。
