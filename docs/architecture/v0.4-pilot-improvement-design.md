# AgenticOps v0.4 真实试运行改进设计

> **状态：** 成文设计和实施计划均已确认，等待 AO-2 文档批次审阅与后续 PR；本文不包含 v0.4 运行代码变更。

本文把 v0.3 在 AO-2 真实试运行中证实的七个问题收敛为 v0.4 的实现边界。改进分为运行时基础、Jira 生命周期与证据、GitHub 与反馈恢复三条轨道，目标是让安装、接管、证据、PR 事实读取和异常恢复形成可回读、可审计、可测试的完整链路。

本文只定义 v0.4 的目标行为、组件边界、失败语义和验收条件。具体代码实施在后续 v0.4 Jira 任务中按测试驱动方式推进，不在 AO-2 当前文档任务中修改 CLI、安装脚本、操作契约或安装资源。

## 1. 背景与试运行事实

v0.3 已使用真实 AO 工作项 `AO-2` 和 `tapstate/agentic-ops` 工程完成接管、计划、决策、任务证据、PR 和 PR 证据的受控试运行。试运行证明真实 Jira 读取、Agentic 所有权字段写入和人工门禁可以连接，但也证实以下问题：

| 编号 | 已证实问题 | 当前影响 |
| --- | --- | --- |
| V04-01 | 自定义 `AGENTIC_OPS_HOME` 仍把临时 `bin` 路径写入真实 shell profile | 隔离安装污染用户环境 |
| V04-02 | `fixedNow()` 固定返回 `2026-07-21T10:30:12Z` | 运行编号、接管时间、心跳和审计时间不可信 |
| V04-03 | `takeover-task` 先更新字段且不执行 Jira 转换 | 字段与状态可能部分成功，CLI 结论与 Jira 事实冲突 |
| V04-04 | 首条不完整的成功接管门禁事件被选为运行上下文锚点 | 后续带 `agentic_run_id` 的操作错误返回 `local_state_mismatch` |
| V04-05 | 默认证据模板为英文且缺少变更、验证、风险和恢复内容 | Jira 人可见内容不合规，证据不能独立支持验收 |
| V04-06 | GitHub CI 客户端请求当前 `gh pr checks` 不支持的 JSON 字段 | `write-pr-evidence` 返回 `github_ci_read_failed` |
| V04-07 | 人工恢复证据和 Jira 回读没有结构化事件 | `feedback analyze/propose` 看不到真实失败恢复，无法形成改进提案 |

这些事实以 `docs/examples/v0.3-ao-pilot-result.md`、AO-2 Jira 评论和 PR #3 为来源。v0.4 实施不得把人工恢复伪装为 v0.3 CLI 成功，也不得改写原始事件来消除缺陷证据。

## 2. 目标与非目标

### 2.1 目标

- 自定义安装目录默认不修改真实用户 shell profile，默认安装仍能幂等配置 PATH。
- 生产命令统一使用真实 UTC 时间，测试通过可注入时钟保持确定性。
- 接管转换、Agentic 字段和兼容的所有权评论在一个 Jira transition 请求中提交，并在成功后回读关键事实。
- 每次成功接管只形成一条完整接管事件；运行上下文能够跳过不完整历史事件并选择最新完整锚点。
- 任务证据和 PR 证据使用中文，任务证据包含变更、验证命令与结果、风险、恢复说明和事实来源。
- GitHub 事实读取不依赖易变的 `gh pr checks --json` 字段，并准确区分 `passed`、`failed`、`pending` 和 `not_configured`。
- 人工恢复形成结构化、可校验的本地事件，反馈分析和提案能够消费恢复事实。
- 七个问题分别具有先失败后通过的回归测试，并通过项目固定完整验证。

### 2.2 非目标

- 不自动合并 PR、自动完成 Jira、自动批准人工门禁或绕过现有策略。
- 不改变 Jira、Git、GitHub 和 CI 的权威事实源边界。
- 不建立通用分布式事务框架；原子性只利用 Jira transition API 单请求能力。
- 不重写全部 CLI handler 或全部反馈数据模型。
- 不改变 v0.3 已发布 Tag、版本号规则、发布流程或分支规则。
- 不把 GitHub 未配置 CI 解释为“检查通过”。
- 不在 AO-2 当前 PR 中实现 v0.4 代码。

## 3. 总体架构

v0.4 按三条独立轨道实施，每条轨道可以单独测试和提交，最后通过同一个端到端流程汇合。

### 3.1 轨道一：运行时基础

负责 V04-01 和 V04-02：

- 安装脚本区分默认安装与自定义安装的 PATH 副作用边界。
- CLI handler 通过统一时钟依赖取得当前时间。
- 一次操作只读取一次当前时间，再派生运行编号、接管时间、心跳和事件时间，避免同一操作内部跨秒不一致。

### 3.2 轨道二：Jira 生命周期与证据

负责 V04-03、V04-04 和 V04-05：

- Jira 客户端提供 transition、fields 和可选 comment 的单请求接口。
- `takeover-task` 解析项目 profile 的 `start_progress` 转换，执行原子接管并回读。
- 成功事件只有一条完整 `takeover_task` 事件；真实写入门禁事件只记录阻塞或失败，不记录不完整成功锚点。
- `RunContextReader` 按完整性和身份一致性选择最新有效锚点。
- 任务证据使用经校验的中文内容，PR 证据使用中文事实模板。

### 3.3 轨道三：GitHub 与反馈恢复

负责 V04-06 和 V04-07：

- GitHub 适配器通过稳定 REST API 获取 PR、检查、提交状态、评论和 Review，转换为内部规范模型。
- CI 聚合显式区分四种状态。
- 新增本地 `feedback record-recovery` 原子操作，把人工恢复、证据摘要、外部引用和回读结论写成结构化事件。
- `feedback analyze/propose` 同时消费普通失败事件和恢复事件。

## 4. 轨道一详细设计

### 4.1 安装目录与 shell profile 边界

安装脚本先判断安装模式：

```text
default_install = AGENTIC_OPS_HOME 未设置，或规范化后等于 $HOME/.agentic-ops
custom_install  = 规范化后的 AGENTIC_OPS_HOME 不等于 $HOME/.agentic-ops
```

默认行为：

- `default_install` 延续配置 `export PATH="$HOME/.agentic-ops/bin:$PATH"`。
- 写入前检查 shell profile 中是否已有完全相同的有效行；重复安装和更新不得追加重复行。
- `custom_install` 默认跳过 shell profile 修改，只在安装结果中输出临时使用方式，例如 `export PATH="<custom-home>/bin:$PATH"`。
- 自定义安装只有在调用者显式设置 `AGENTIC_OPS_CONFIGURE_PATH=1` 时才允许写入真实 shell profile。
- 非交互环境不得把 `AGENTIC_OPS_ASSUME_YES=1` 解释为 PATH 授权；更新授权与环境持久化授权是两个独立门禁。

路径比较使用规范化绝对路径，避免尾部斜杠或符号形式不同导致误判。安装日志增加 `path_profile_action`，取值为 `added`、`already_configured` 或 `skipped_custom_home`，但不得记录敏感环境变量。

### 4.2 可注入时钟

CLI 运行时新增最小 `Clock` 边界：

```go
type Clock interface {
    Now() time.Time
}
```

- 生产实现使用 `time.Now().UTC()`。
- 测试实现由用例注入固定 UTC 时间。
- `takeover-task`、事件写入、`release-agent` 和反馈文件命名等现有时间入口统一使用该依赖。
- handler 开始一次操作时调用一次 `Now()`；运行编号、`agentic_takeover_at`、`agentic_heartbeat_at` 和同一完成事件复用该值。
- 删除生产路径中的硬编码 `fixedNow()`；固定时间只允许存在于测试 fixture 或 fake clock 中。

旧事件和旧运行编号保持可读，不执行迁移或重写。

## 5. 轨道二详细设计

### 5.1 Jira 原子转换请求

Jira 客户端内部请求模型调整为：

```go
type TransitionRequest struct {
    ID      string
    Fields  map[string]any
    Comment string
}
```

真实客户端把它序列化为同一个 `POST /rest/api/3/issue/{key}/transitions` 请求：

- `transition.id` 保存转换编号。
- `fields` 保存 Agentic 所有权、运行编号、接管时间、下一动作、完成证据清理和心跳字段。
- profile 使用 Jira 评论承载所有权时，通过同一请求的 `update.comment.add` 写入 ADF 评论。

Fake client 记录完整请求，供测试断言请求次数、转换和字段。其它只需要转换的调用传入空 `Fields` 和空 `Comment`，不改变业务语义。

### 5.2 `takeover-task` 流程

接管按以下顺序执行：

1. 读取 Jira 卡片、当前用户、项目 profile 和 Standard Process Registry。
2. 执行现有准入、负责人、Agentic 绑定、任务分类、流程入口和目标仓库检查。
3. 在真实 Jira 模式下继续要求 `--confirm-real-jira-write`。
4. 使用 profile 的 `jira_transition_mapping.start_progress` 解析转换 ID；AO 项目对应转换 ID `2`。
5. 使用单次时钟值生成 `agentic_run_id` 和接管时间。
6. 构造 `TransitionRequest`，只调用一次 Jira transition API。
7. 远端请求成功后重新读取 Jira 卡片，校验状态已映射到目标标准流程阶段、`agentic_id`、`agentic_run_id`、接管时间和心跳与请求一致。
8. 回读通过后写入一条完整的成功 `takeover_task` 事件并返回 `ok:true`。

目标标准流程阶段由 `transition_mapping.start_progress` 得到，不能硬编码为 AO 的中文状态。`jira_transition_mapping.start_progress` 缺失或无法解析时，接管在远端写入前停止。

### 5.3 部分失败与重试安全

接管使用以下稳定失败语义：

| 失败码 | 远端是否可能已写入 | `retry_safe` | 处理要求 |
| --- | --- | --- | --- |
| `jira_transition_mapping_gap` | 否 | `true` | 修复 profile 后重试 |
| `jira_takeover_atomic_write_failed` | 未知 | `false` | 先回读 Jira，不得直接重试 |
| `jira_takeover_readback_failed` | 是 | `false` | 恢复连接后只读核对 |
| `jira_takeover_readback_mismatch` | 是 | `false` | 人工处理 Jira 部分事实 |
| `event_write_failed` | 是且回读通过 | `false` | 保留命令输出并记录恢复事件 |

远端成功但本地审计失败时，JSON 输出必须包含：

```json
{
  "remote_write_completed": true,
  "readback_verified": true,
  "retry_safe": false,
  "agentic_run_id": "<run-id>",
  "issue_key": "<issue-key>"
}
```

任何远端结果不明确的错误都不得声称接管失败且可安全重试。

### 5.4 成功事件与运行上下文锚点

真实 Jira 写入确认门禁、映射缺失和远端失败可以形成门禁或失败事件，但这些事件必须 `ok:false`。远端成功后不再额外写一条字段不完整的成功门禁事件。

成功 `takeover_task` 事件必须同时具有：

- `workspace`
- `agentic_run_id`
- `issue_key`
- `agent_id`
- `agentic_id`
- `agentic_takeover_at`
- `agentic_heartbeat_at`
- `task_class`
- `process_id`
- `target_repo`
- `current_stage`
- `agentic_next_action`

`RunContextReader` 对同一 `agentic_run_id` 的成功 `takeover_task` 事件从新到旧扫描：

1. workspace 或 agent 身份与查询明确冲突时返回对应一致性错误。
2. 缺少必需字段的候选只记为诊断，不作为锚点，也不覆盖后续完整候选。
3. 第一个完整且身份匹配的候选作为锚点。
4. 找不到完整候选但存在不完整候选时返回 `local_state_mismatch`；完全没有候选时返回 `run_not_found`。
5. 选定锚点后，只处理锚点之后的状态承载事件；不完整的非状态审计事件不改变恢复点。

这样可兼容 v0.3 已产生的“不完整成功门禁事件在前、完整接管事件在后”历史数据，同时继续拒绝真正的身份冲突和损坏状态。

### 5.5 中文任务证据

`development-completed.md` 改为中文元数据模板。`write-evidence` 不再只用静态元数据直接声明任务完成，而是要求 `--content-file` 指向研发工程师或 AIAgent 已审阅的中文证据正文。

证据正文必须包含以下二级标题：

```text
## 变更内容
## 验证命令与结果
## 风险
## 恢复说明
## 事实来源
```

每个标题必须有非空正文；没有已知风险或恢复动作时也必须明确写“未发现额外风险”或“无需恢复”，不得留空。CLI 校验文件位于当前项目 AI 工作空间、是普通文件且不超过操作契约限制，再把中文元数据与正文组合写入本地证据和 Jira 评论。

`--content-file` 缺失或章节不完整时返回 `missing_evidence_content` 或 `invalid_evidence_sections`，不写本地完成证据和 Jira。真实 Jira 写入仍保留独立 `--confirm-real-jira-write` 门禁。

### 5.6 中文 PR 证据

`write-pr-evidence` 继续从 GitHub 事实自动生成内容，但模板改为中文，至少包含：

- 工作空间、运行编号、Jira 卡片、目标仓库和 PR URL。
- PR head SHA。
- CI 状态、已配置检查数、失败检查数和待完成检查数。
- Review 状态和 Review 数量。
- GitHub 事实读取时间和来源。
- 当前结论、风险和需要研发工程师处理的动作。

`ci_status=not_configured` 必须显示“未配置 CI，不能视为 CI 已通过”，但是否允许继续由项目策略和人工门禁决定，GitHub 适配器不自行改变流程。

## 6. 轨道三详细设计

### 6.1 GitHub 规范模型

内部 GitHub 模型不再直接复制 `gh pr checks` 字段，而是使用稳定语义：

```go
type PullRequestFacts struct {
    URL       string
    HeadSHA   string
    Comments  []PRComment
    Reviews   []PRReview
    CI        CIStatus
    ReadAt    time.Time
}

type CIStatus struct {
    Status        string // passed|failed|pending|not_configured
    Checks        []Check
    FailingChecks []Check
    PendingChecks []Check
}
```

`gh` 只负责认证和调用 API。适配器使用 `gh api` 访问以下稳定端点并转换结果：

- `GET /repos/{owner}/{repo}/pulls/{pr}`：PR URL 和 head SHA。
- `GET /repos/{owner}/{repo}/commits/{sha}/check-runs`：GitHub Checks。
- `GET /repos/{owner}/{repo}/commits/{sha}/status`：提交状态上下文。
- `GET /repos/{owner}/{repo}/issues/{pr}/comments`：普通 PR 评论。
- `GET /repos/{owner}/{repo}/pulls/{pr}/reviews`：Review。

分页由适配器统一处理。单元测试通过 fake runner 返回 API fixture，不访问真实 GitHub。

### 6.2 CI 四态聚合

聚合顺序固定为：

1. 任一 check run 或 status context 为失败、错误、取消、超时或需要处理，结果为 `failed`。
2. 没有失败但任一检查仍排队、运行或 pending，结果为 `pending`。
3. 至少存在一个已配置检查，且全部处于成功、neutral 或 skipped 等允许终态，结果为 `passed`。
4. check runs 和 status contexts 都为空，结果为 `not_configured`。

读取 API 失败返回 `github_ci_read_failed`，不得降级为 `not_configured`。`not_configured` 只表示成功读取后确认没有检查配置。

### 6.3 结构化恢复事件

反馈事件增加可选恢复对象：

```go
type RecoveryRecord struct {
    OriginalOperation    string `json:"original_operation"`
    OriginalCode         string `json:"original_code"`
    EvidenceSHA256       string `json:"evidence_sha256"`
    ExternalReference    string `json:"external_reference"`
    ReadbackVerified     bool   `json:"readback_verified"`
    RemoteWriteCompleted bool   `json:"remote_write_completed"`
    RetrySafe            bool   `json:"retry_safe"`
}
```

`feedback.Event` 通过 `recovery,omitempty` 保存该对象。旧事件没有 `recovery` 时保持兼容。

新增本地原子操作：

```sh
agentic-cli feedback record-recovery \
  --workspace <workspace> \
  --run-id <run-id> \
  --issue-key <issue-key> \
  --original-operation <operation> \
  --original-code <code> \
  --evidence-file <file> \
  --external-reference <jira-comment-id-or-url> \
  --readback-verified \
  --remote-write-completed \
  --retry-safe=false \
  --confirm-recovery-record
```

该操作不写 Jira、GitHub 或 Git，只写当前工作空间的本地反馈事件。它必须：

- 校验运行上下文和证据文件边界。
- 自行计算证据 SHA-256，不接受调用者传入摘要。
- 要求调用者明确声明回读、远端写入和重试安全事实。
- 使用 `--confirm-recovery-record` 防止无意写入带外部事实主张的审计事件。
- 输出事件路径、摘要和去重指纹。

去重指纹由 `workspace`、`agentic_run_id`、`original_operation`、`original_code`、`evidence_sha256` 和 `external_reference` 构成。重复记录返回已有事实，不追加第二条事件。

### 6.4 反馈分析与提案

`feedback analyze` 增加恢复模式统计，`feedback propose` 同时从普通失败和恢复事件形成提案：

- 普通失败事件按 `code` 计数。
- 恢复事件按 `recovery.original_code` 计数，并保留 `recovered_count` 和脱敏的外部引用。
- 同一去重指纹只计一次，不因“失败事件 + 恢复事件”重复放大。
- 即使恢复事件本身 `ok:true`，原始失败仍是可分析模式。
- 提案输出包含证据数量、恢复数量、推荐资产和中文理由。

对于 AO-2 的 `github_ci_read_failed` 恢复记录，分析结果必须出现该失败模式，提案不得为空。

## 7. 事实源、人工门禁与安全边界

- Jira 继续是任务内容、负责人、状态、Agentic 绑定和任务评论的事实源。
- GitHub 继续是 PR、Review、提交状态和 CI 检查的事实源。
- Git 继续是分支、提交和文件差异的事实源。
- 本地事件只保存执行连续性、门禁结果和恢复审计，不能覆盖外部当前事实。
- 真实 Jira 字段、评论和转换分别受操作契约、策略、所有权和显式确认约束；原子接管把同一项已确认动作合为一个 Jira 请求，不扩大授权。
- Git push、PR 创建、合并、发布和 Jira 完成仍保持现有独立人工确认。
- `feedback record-recovery` 只能记录已经发生且经过回读的恢复，不得代替外部写入或声称外部成功。
- secrets、tokens、private keys、原始敏感响应和本机绝对路径不得进入模板、事件、fixture 或提交。

## 8. 测试设计

七个问题分别先增加可稳定复现的失败测试，再实现通过；不得只依赖最终端到端测试覆盖。

### 8.1 V04-01 安装边界

- 自定义 `AGENTIC_OPS_HOME`、真实测试 Home 和未授权 PATH 配置组合下，真实 profile 内容保持不变。
- `AGENTIC_OPS_CONFIGURE_PATH=1` 时只追加一次规范化自定义路径。
- 默认安装和更新继续幂等配置 `$HOME/.agentic-ops/bin`。
- 安装结果返回正确 `path_profile_action`。

### 8.2 V04-02 时钟

- fake clock 生成确定的运行编号和时间字段。
- 同一操作的运行编号、接管时间、心跳和事件时间来自同一个时刻。
- 生产 clock 返回 UTC，生产包中不存在固定 2026 时间值。

### 8.3 V04-03 原子接管

- Fake Jira 断言只收到一个带 `start_progress` 转换和字段的请求。
- AO fixture 断言转换 ID 为 `2`，状态目标映射为 `implementation`。
- 覆盖转换映射缺失、远端失败、回读失败、回读不一致和“远端成功但本地事件失败”。
- 后三种情况断言 `retry_safe=false`，并保留回读或恢复动作。

### 8.4 V04-04 运行上下文

- fixture 顺序为“不完整成功接管事件在前、完整成功接管事件在后”，读取必须成功。
- 多个完整候选时选择最新完整候选。
- workspace、agent、issue、流程或仓库真实冲突仍返回一致性错误。
- 只有不完整候选时返回 `local_state_mismatch`。

### 8.5 V04-05 中文证据

- 默认模板标题和人可见说明全部为中文。
- 缺少任一必需章节或章节正文为空时停止写入。
- 完整内容包含变更、验证命令与结果、风险、恢复说明和事实来源。
- PR 证据对 `not_configured` 给出明确风险说明。

### 8.6 V04-06 GitHub 事实

- API fixture 覆盖 `passed`、`failed`、`pending` 和 `not_configured`。
- 覆盖 check runs 与 commit statuses 混合、API 失败、PR head SHA、评论和 Review。
- 断言不再执行 `gh pr checks --json conclusion,detailsUrl`。

### 8.7 V04-07 恢复反馈

- 记录恢复时自动计算证据 SHA-256 并生成稳定去重指纹。
- 重复恢复记录不重复追加事件。
- `feedback analyze` 能看到成功恢复事件中的原始失败码。
- `feedback propose` 对恢复模式生成非空中文提案，并正确报告证据数和恢复数。

### 8.8 完整验证

实现完成后必须执行项目发布脚本固化的完整验证，包括：

```sh

```

同时执行四个固定 E2E 流程，至少串联：接管、计划、决策、任务证据、PR 事实、PR 证据、恢复记录、反馈分析和完成清理。自动化测试全部使用 fake Jira、GitHub fixture 和临时工作空间，不执行真实外部写入。

真实 AO 回归属于独立验收阶段。执行前必须逐项取得 Jira 写入、评论、转换、Git push、PR 和任务完成授权，不能把单元测试授权扩大为真实外部操作授权。
