# 工作项级连续执行授权设计

## 1. 状态

- 设计状态：已确认。
- 适用范围：AgenticOps 标准研发任务流程。
- 确认结论：研发工程师确认设计或修复计划后，AIAgent 可以在同一工作项授权范围内连续推进到拉取请求审查，不再为每个已授权动作重复请求确认。

## 2. 背景

当前标准把真实 Jira 写入、Git 提交、Git 推送、创建或更新拉取请求分别视为人工门禁。该边界可以阻止未经授权的高风险副作用，但在同一个目标、范围、仓库和验证方式已经确认后，逐项暂停会造成重复审查和执行中断。

本设计不取消人工门禁，而是把门禁从“每个动作单独确认”调整为“工作项范围内一次明确授权”。研发工程师仍负责确认设计、范围、风险和目标；AIAgent 在授权范围内负责持续实现、验证、提交、推送、证据回写和创建拉取请求，并统一停在拉取请求审查节点。

## 3. 目标

- 减少同一工作项在提交、推送、Jira 回写和创建拉取请求之间的重复暂停。
- 保证所有高风险副作用仍有明确、可审计的人工授权来源。
- 让授权可以被事实源回读，而不是只依赖聊天上下文。
- 在范围、风险或所有权变化时立即使授权失效。
- 保留代码审查、合并、发布和专业角色审查的独立责任边界。

## 4. 不做什么

- 不允许 AIAgent 未经设计或修复计划确认自主推进工作项。
- 不把一次授权扩展到其它 Jira 卡片、仓库、目标分支或新的需求范围。
- 不授权直接修改受保护分支、强推、改写历史、合并、发布、创建或移动 Git Tag。
- 不替代代码审查人、QA、安全、运维或流程负责人的专业审查。
- 不把聊天中的模糊同意当作可以长期复用的全局授权。

## 5. 方案选择

### 5.1 每个副作用单独确认

提交、推送、Jira 回写和创建拉取请求分别等待确认。边界清晰，但会造成重复中断，不采用。

### 5.2 工作项级连续执行授权

研发工程师确认版本化设计或修复计划时，同时明确授权工作项内的连续动作。授权绑定具体任务事实并在异常时失效。该方案兼顾效率、可审计性和人工责任边界，作为标准方案。

### 5.3 按风险等级自动授权

由策略自动判断低风险任务并允许无人工确认推进。当前分类、策略和运行时证据还不足以稳定支持，不作为现阶段方案。

## 6. 授权模型

一次有效授权至少绑定以下事实：

- `issue_key`
- `agentic_run_id`
- `agent_id` 和任务当前 `agentic_id`
- 目标仓库
- 工作分支
- 拉取请求目标分支
- 已确认的设计或修复计划版本
- 允许修改的范围和明确非范围
- 验证方式
- 已知残留风险
- 允许连续执行的动作集合
- 授权确认人、确认事实引用和确认时间

授权记录应优先写入 Jira 的决策评论或项目已配置的等价任务事实源，并在本地事件中只保存可安全引用的标识。没有稳定事实引用时，不得仅凭历史聊天摘要恢复连续执行。

## 7. 授权动作

设计或修复计划确认后，以下动作可以在同一授权窗口内连续执行：

1. 在确认范围内修改代码、测试、文档和标准资产。
2. 运行计划中声明的验证，并对范围内的普通失败进行诊断、修复和重试。
3. 按项目提交规范创建与当前 Jira 卡片绑定的提交。
4. 推送符合项目规则的任务分支。
5. 写入与本次执行直接相关的 Jira 计划确认、推送总结、阶段证据和拉取请求证据。
6. 创建或更新从授权工作分支到授权目标分支的拉取请求。
7. 回读 Git、GitHub、CI 和 Jira 事实，形成拉取请求审查包。

这些动作仍属于人工门禁动作。它们不再逐项确认，是因为同一次工作项授权已经明确覆盖，而不是因为动作风险等级被降低。

## 8. 不在授权范围内的动作

以下动作始终需要新的人工确认或对应专业审查：

- 合并拉取请求。
- 发布、部署、线上变更或影响生产数据的操作。
- 创建、移动或删除 Git Tag。
- 直接提交或推送受保护分支。
- 强推、重写提交历史、删除远端分支或其它难以恢复的操作。
- 修改需求范围、验收标准、目标仓库、工作分支来源或拉取请求目标分支。
- 引入超出已确认边界的新风险或新的架构取舍。
- 需要代码审查人、QA、安全、运维或流程负责人判断的事项。

## 9. 授权失效与停止条件

出现以下任一事实时，AIAgent 必须停止连续执行并请求新的决策：

- Jira `assignee`、`agentic_id` 或任务所有权与授权记录不一致。
- `issue_key`、`agentic_run_id`、目标仓库、工作分支或目标分支不一致。
- 实际变更超出已确认范围或验收标准需要调整。
- 风险等级扩大，或出现未在设计中说明的安全、数据、兼容性或线上风险。
- 需要强推、改写历史、删除、覆盖或其它不可安全恢复的动作。
- 必要验证无法执行、无法通过，或连续修复仍失败。
- 审查意见存在多种合理方案，需要研发工程师或专业角色取舍。
- 外部写入结果不明确，无法通过幂等键或事实源回读判断是否成功。

权限、网络或服务暂时失败时，可以在动作本身具备安全重试条件且授权仍有效的前提下重试。Git 推送成功但 Jira 回写失败时，只重试 Jira 回写，不重复推送。

## 10. 标准执行流程

```text
接管 Jira 工作项
-> 分析并形成版本化设计或修复计划
-> 研发工程师确认计划并授予工作项级连续执行授权
-> AIAgent 实现、验证、提交
-> 推送任务分支并回写必要 Jira 证据
-> 创建或更新拉取请求
-> 回读拉取请求、CI、审查和 Jira 事实
-> 输出拉取请求审查包并暂停
-> 代码审查人和研发工程师审查
-> 独立确认合并、发布或范围变化
```

## 11. 拉取请求审查包

连续执行正常结束时，AIAgent 必须一次性提供：

- Jira 卡片和 `agentic_run_id`。
- 拉取请求链接、Base、Head 和固定 Head SHA。
- 变更摘要和明确非范围。
- 提交列表。
- 验证命令与实际结果。
- GitHub check run、commit status 和审查意见的当前事实；未配置 CI 时必须明确说明，不能表述为 CI 通过。
- Jira 回写结果及可复查引用。
- 残留风险和需要审查人重点关注的内容。
- 下一项需要人工确认的动作。

## 12. 标准资产落点

实施时同步更新以下资产：

- 公司级硬规定：明确人工确认可以是绑定工作项事实的一次性连续执行授权。
- AI 员工手册：增加授权窗口、连续执行规则、失效条件和拉取请求审查输出。
- 标准流程契约：在实现阶段表达计划确认、授权事实和拉取请求审查节点。
- 默认策略：保留各高风险 gate，同时增加授权复用语义，不把 gate 改为不需要确认。
- 操作契约：明确 Git 和 GitHub 副作用可以消费同一份仍有效的工作项授权。
- 证据模板：增加授权记录和拉取请求审查包模板。
- 研发工程师指南、项目规则和当前设计：统一自然语言指挥方式和停止条件。
- 资源测试：检查授权范围、失效条件、禁止动作和审查输出在标准资产中保持一致。

## 13. 兼容与迁移

- 没有工作项级授权记录的旧任务继续使用逐项确认，不做静默放宽。
- 已经确认的设计或修复计划只有在明确包含连续动作范围时，才能作为授权来源。
- 当前 AO-2 已由研发工程师明确确认本设计，并授权在当前工作项、仓库和任务分支范围内连续推进到 `develop` 拉取请求审查。
- 当前阶段先更新标准资产和测试，不新增自动合并、自动发布或无人工确认的运行时能力。

## 14. 验证要求

- 资源测试必须证明各标准资产仍把 Git 推送、Jira 写入和创建拉取请求视为受人工门禁约束的动作。
- 资源测试必须证明有效工作项授权可以覆盖连续动作，但不能覆盖合并、发布、Tag、强推或范围变化。
- 资源测试必须检查授权失效条件和拉取请求审查包要求存在。
- 执行仓库完整的资源测试、发布工作流测试、Go 测试和 `git diff --check`。
