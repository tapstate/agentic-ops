# 事实源收敛设计

本文定义 AgenticOps 当前实现、运行资产、文档、实施计划和长期记忆出现状态分歧时的判定与收敛方式。本设计只治理“项目当前具备什么能力”的表达，不新增运行能力，也不替代 Jira、Git、GitHub 或 CI 等业务事实源。

## 1. 背景

当前仓库存在以下已确认的不一致：

- `packages/agentic-cli/internal/git/`、`packages/agentic-cli/internal/github/` 和相关命令已经存在，但部分 CLI 运行文档仍将其描述为未来实现。
- `install-resources/basic/contracts/operations/write-pr-evidence.yaml` 已存在，但当前命令注册表没有对应运行入口，不能把该契约单独视为已实现能力。
- 历史实施计划和项目长期记忆声明已经新增 `scripts/publish-release.sh`，但当前仓库不存在该脚本。
- 当前计划中仍有未完成事项，但部分总览描述声称计划已经没有未完成项。
- 部分历史计划使用完成勾选记录当时结论，却没有说明这些结论不能代表当前仓库状态。

这些分歧会让维护者和 AIAgent 无法可靠区分“已经实现”“计划实现”和“等待治理决策”，也会削弱文档、计划和长期记忆的审计价值。

## 2. 目标

本次收敛需要达到以下结果：

- 当前能力描述与可执行源码、命令注册、自动化测试和机器可读契约一致。
- 不存在实现支撑的完成结论改为待实现或历史错误记录。
- 涉及权限、审计归属和兼容承诺的事项明确标记为待决策。
- 历史计划保留实施轨迹，但不再被误读为当前能力清单。
- 长期记忆只记录当前仍成立的稳定结论。

本次收敛不新增功能，不恢复缺失的发布脚本，不重构目录，也不创建新的动态能力矩阵。

## 3. 事实判定顺序

项目当前能力按以下顺序判定：

```text
可执行源码与注册命令
-> 自动化测试和机器可读契约
-> 安装资源
-> 当前架构与运行文档
-> 实施计划和长期记忆
```

各层职责如下：

- 可执行源码与注册命令证明能力入口和实际行为存在。
- 自动化测试和机器可读契约证明行为边界、输入输出、失败码和门禁得到验证。
- 安装资源证明能力可以进入安装后的 AIAgent 工作环境。
- 当前架构与运行文档解释已经验证的系统边界和使用方式。
- 实施计划跟踪推进状态，长期记忆保存稳定结论；两者都不能覆盖前述可验证事实。

单独出现于文档、计划或长期记忆中的声明，不足以证明能力已经实现。

## 4. 状态分类

能力和事项统一使用以下语义：

- **已实现**：源码或安装资源中存在对应能力，并有命令注册、契约或自动化测试支撑。
- **部分实现**：已有可执行基线，但仍缺少设计要求中的明确环节；必须同时写明已完成边界和剩余缺口。
- **待实现**：已有确认设计，但当前仓库不存在对应可执行能力。
- **待决策**：实现方向依赖产品、权限、事实源、审计或兼容承诺决策，不能直接进入默认开发任务。
- **历史记录**：记录过去实施过程或当时结论，不作为当前能力状态。

历史计划中的错误完成结论不得静默删除。应保留简短说明，指出当前仓库核对结果以及后续由哪个当前计划继续跟踪。

## 5. 文档责任边界

### 当前架构与运行文档

`docs/architecture/` 和 `docs/runtime/` 只描述当前成立的架构边界、运行模型和稳定目标。已实现和未实现内容必须明确区分，不能使用同一种陈述语气。

### 实施计划

`plans/` 使用勾选项跟踪实施进度。仍在推进的计划必须反映当前状态；历史计划应在开头声明其历史属性，并链接到当前跟踪计划。

### 长期记忆

`/Users/lhs/wiki/30-projects/agentic-ops.md` 只保存稳定、可复用且与当前仓库一致的项目结论。发现历史记忆与仓库事实冲突时，应修正当前结论，并保留必要的日期和来源说明。

### 源码、契约和测试

本次收敛不修改源码、命令契约和测试。它们是核对当前实现的主要证据，不因文档期望而被反向解释。

本次实施修改以下文件：

- `docs/runtime/cli-runtime.md`：修正 Git / GitHub 受控能力的当前状态。
- `plans/design-implementation-gap-todo-v1.md`：修正总览矛盾并重新标定恢复、发布、更新回滚和反馈闭环状态。
- `plans/full-design-implementation-plan-v1.md`：声明历史计划属性，撤销缺失发布脚本的当前完成结论。

本次不修改 Go 源码、机器可读操作契约、安装资源、平台二进制和发布逻辑。

## 7. 验证方式

实施完成后必须验证：

1. 命令注册表与 CLI 文档描述一致。
2. 操作契约与计划完成状态一致。
3. 文档中的当前文件入口真实存在。
4. 未完成勾选项与计划总览结论不冲突。
5. `publish-release.sh` 不再被描述为当前已实现入口。
6. Git / GitHub 受控命令不再被描述为尚未创建的目录或未来能力。
7. 仓库没有生成二进制、校验和或其它范围外改动。

验证命令包括：

```sh
git diff --check
go test ./...
bash scripts/test-resources.sh
bash tests/e2e/local-fake-flow.sh
git status --short
```

还应使用 `rg` 检查错误状态描述、缺失路径引用和常见占位词。若核对发现新的实现冲突，应先更新本设计和实施计划，不直接扩展为源码修复。

## 8. 提交边界

本次工作先完成本地修改和验证，不自动提交或推送。只有研发工程师明确要求提交后，才按 AgenticOps 项目提交规则创建单一逻辑提交。
