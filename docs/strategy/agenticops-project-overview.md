# AgenticOps 旧统一 CLI 项目全景

> **冻结历史 / 迁移基线，不是现役操作：** 本文记录旧统一 CLI 阶段的项目全景。现役全景见《AgenticOps Skill 与 Python Runtime 驱动项目全景》，现役目录和入口见《项目结构》。

> 本文面向第一次接触 AgenticOps 的技术人员，集中说明项目本身的定位、优势、架构、能力、已实现内容和推进计划。本文不展开代码实现，聚焦 AgenticOps 自身。

## 1. 一句话认识 AgenticOps

AgenticOps 是把公司员工执行标准沉淀成 AI 可执行流程的 **AI 执行控制体系**。

它面向研发 Jira 任务，连接 Jira、Git、GitHub、CI 和人工审查流程，让 AIAgent 不只是“生成一个结果”，而是能够在明确授权、明确阶段和明确门禁下完成任务，并留下可恢复、可审计、可复盘的证据。

最核心的判断标准是：

> AI 是否不仅能做事，还能按公司标准、在授权范围内、对着正确事实源做事，并且在出错后知道如何停止和恢复。

## 2. 项目要解决的问题

模型可以理解需求、修改代码、执行测试和调用工具，但单次模型能力不能自动解决企业流程中的责任问题：

- 任务是否真的授权给当前研发工程师和当前 AIAgent？
- Jira 卡片是否包含目标仓库、验收标准、风险和任务分类？
- 当前阶段允许执行什么，哪些动作必须等待人工确认？
- Jira、Git、GitHub 和 CI 的状态是否一致？
- 任务中断后，新的 AIAgent 能否从事实和证据恢复，而不是依赖旧聊天？
- 失败后应该重试、重做、补充信息，还是转人工？
- 同类问题重复发生时，能否变成下一版标准流程，而不是继续依靠个人经验？

没有统一控制时，AI 执行容易出现三类问题：

1. 做出了结果，但无法证明过程符合公司标准。
2. 外部系统没有真正完成写入，聊天上下文却认为任务已经完成。
3. 每次失败都通过临时 prompt 和人工记忆补救，组织经验无法积累。

AgenticOps 的作用，是把这些问题变成可版本化的标准资产、可检查的操作和可追踪的证据。

## 3. 定位、目标与非目标

### 3.1 项目定位

AgenticOps 是企业现有研发系统之上的 AI 执行控制层：

```text
Jira 任务与流程事实
        │
        ▼
AgenticOps 标准流程、操作契约、策略门禁和人工确认
        │
        ▼
AIAgent 执行、验证、证据整理与恢复
        │
        ▼
Git / GitHub / CI / Jira 事实回写与任务审计
```

它不创建新的任务事实源，不替代 Jira、Git、GitHub、CI 或专业审查角色。

### 3.2 当前目标

先跑通一条真实、可控、可复用的研发 Jira 任务闭环：

```text
安装
→ 初始化项目 AI 工作空间
→ 拉取并检查待办
→ 研发工程师授权接管
→ 形成版本化计划并确认
→ 在授权范围内实现和验证
→ 形成完成与 PR 证据
→ 进入专业审查
→ 回写任务审计
→ 释放代理绑定并形成反馈
```

当前阶段优先保证闭环可靠，不以无人值守或无限扩大自动化范围为目标。

### 3.3 长期目标

长期目标是成为公司的 AI 操作控制层：将研发任务中验证过的员工执行标准扩展到问题调查、发布、升级、客户问题和其他公司事务。

长期运行模型是：

```text
识别事务类型
→ 判断当前阶段
→ 选择操作和运行手册
→ 执行策略门禁
→ 处理事务
→ 输出节点表单与证据
→ 回写事实源
→ 生成反馈
→ 人工确认后演进标准资产
```

### 3.4 明确不做什么

- 不替代 Jira、Git、GitHub、CI 或专业审查人。
- 不让本地日志、聊天记录或反馈报告成为任务事实源。
- 不让 AIAgent 临场猜测字段、状态、仓库、验证方式或流程阶段。
- 不把尚未验证的经验直接固化为默认策略或脚本。
- 不在没有授权和审计的情况下执行高风险写操作。
- 不把项目维护规则和业务 AIAgent 运行规范混在一起。
- 不引入 Web 控制台或后台常驻服务作为默认运行形态；标准操作通过隔离接口和本地文件协作。

## 4. 项目优势

### 4.1 从“模型会做”升级为“流程可控”

AgenticOps 不把 AI 的一次输出当作任务完成，而是把任务拆成准入、接管、计划、执行、验证、审查、审计和清理等阶段。每个阶段有明确的责任人、输入、输出和下一步动作。

这样可以回答“现在到哪一步了”“为什么停下”“谁需要确认”“能否恢复”，而不是只能重新翻聊天记录。

### 4.2 把软提示变成可执行边界

“不要推送主分支”写在 prompt 中只是建议；策略门禁可以在操作真正发生前检查授权范围、目标分支、当前阶段和人工确认，不满足条件就拒绝并给出人工动作。

这使安全规则具备三个特征：可检查、可测试、可审计。

### 4.3 保持事实源清晰

AgenticOps 不复制 Jira、Git、GitHub 和 CI 的事实，而是通过 profile 和 adapter 读取、校验和受控回写：

- Jira 是任务、负责人、状态、迭代、评论和任务证据的事实源。
- Git 是代码、测试、提交和分支的事实源。
- GitHub / CI 是 PR、检查、审查评论和合入记录的事实源。
- AgenticOps 本地事件只保存执行连续性、门禁和恢复审计。

外部写入结果不确定时必须先回读事实源，不能因为本地命令返回成功就假定远端已经完成。

### 4.4 失败可以解释、恢复和复盘

项目不把所有失败都归类为“再试一次”，而是区分：

| 失败类型 | 标准动作 |
| --- | --- |
| 临时网络或服务错误 | 满足幂等条件时重试 |
| 当前节点缺少输入 | 阻断并要求补充事实 |
| 前序表单或审查失效 | 重做指定阶段 |
| 权限、所有权或范围冲突 | 转人工，不继续执行 |
| 外部写入结果不明确 | 回读后再决定补写或停止 |

失败码、运行事件和恢复记录会进入反馈闭环，使项目能够区分模型问题、流程问题、配置问题和控制层问题。

### 4.5 标准资产可以持续进化

项目把经验沉淀为 AI 员工手册、操作契约、工作流配置、策略、运行手册、模板、表单和原子化操作。

成熟经验的升级路径是：

```text
执行记录
→ 重复问题识别
→ 改进建议
→ 人工确认
→ 标准资产版本化
→ 发布与回滚
→ 效果检查
```

AIAgent 可以提出建议，但不能未经确认自动修改公司规范。

### 4.6 对现有研发系统低侵入

AgenticOps 通过工作流 profile 适配不同 Jira 项目、状态、字段、代码仓库和审查节点，保留现有协作系统和专业职责。

项目 AI 工作空间与全局安装资料分离，既能共享公司标准，也能保存项目本地配置和任务运行上下文。

## 5. 总体架构

### 5.1 分层架构

```text
┌────────────────────────────────────────────┐
│ AIAgent 执行层                              │
│ 理解任务、修改代码、验证结果、整理证据       │
└──────────────────────┬─────────────────────┘
                       │ 调用受控操作
┌──────────────────────▼─────────────────────┐
│ AgenticOps 控制层                            │
│ 任务类型、阶段、状态、授权、契约、策略、门禁 │
│ 证据、恢复、审计、反馈和标准资产演进         │
└──────────────────────┬─────────────────────┘
                       │ 受控读取 / 回写
┌──────────────────────▼─────────────────────┐
│ 外部事实源                                   │
│ Jira、Git、GitHub、CI、项目 AI 工作空间      │
└────────────────────────────────────────────┘
```

### 5.2 五类核心职责

| 职责层 | 负责内容 |
| --- | --- |
| 任务与流程 | `task_type`、`current_stage`、`agentic_next_action`、标准流程和责任角色 |
| 操作与运行时 | 稳定输入输出、失败码、副作用、结构化 JSON 和跨平台 CLI |
| 配置与策略 | Jira / GitHub / 仓库映射、policy、人工 gate、授权范围和风险规则 |
| 证据与恢复 | `agentic_run_id`、事件、节点表单、完成证据、恢复和任务审计 |
| 反馈与演进 | 失败聚合、人工介入分析、改进建议、版本化发布和回滚 |

### 5.3 标准资产结构

| 标准资产 | 作用 |
| --- | --- |
| AI 员工手册 | 规定如何接任务、执行、停止、请求人工和回写证据 |
| Operation Contract | 规定操作的输入、输出、失败码、阶段和副作用 |
| Workflow Profile | 规定项目差异、字段、状态、仓库和模板映射 |
| Task Form | 规定每个生命周期节点必须输出的结构化字段 |
| Policy / Gate | 规定哪些动作允许、阻断或需要确认 |
| Runbook | 规定异常的排查、修复、升级和回写路径 |
| Template | 规定计划、补卡、阻塞、完成和 PR 证据格式 |
| Event / Evidence | 保存执行连续性、验证结果和审计事实 |

### 5.4 本地运行资料和接口隔离

AgenticOps 不依赖 Web 控制台或后台常驻服务。标准操作之间通过明确的输入输出接口、操作契约和本地文件交接，运行资料按 Jira 编号隔离：

```text
<project-ai-workspace>/.agentic-ops/
  tasks/
    <ISSUE-KEY>/
      runs/<agentic_run_id>/
      audit/
      feedback/
      handoff/
```

本地目录保存执行连续性、任务审计、证据、反馈和交接材料；不同 Jira 任务不能共享未命名的临时运行状态。后续如需接入审计服务，应复用同一份脱敏摘要和稳定引用，不改变本地任务目录作为当前管理入口。

## 6. 能力全景

### 6.1 安装与初始化

- 提供 macOS Intel、macOS Apple Silicon、Linux amd64 和 Linux arm64 安装资源。
- 使用 managed clone、校验和、版本元数据和本地状态管理安装、更新和回滚。
- 初始化项目 AI 工作空间，隔离全局标准资产与具体项目运行资料。
- 初始化 AIAgent 所需身份、profile、工作区规则和运行目录。
- 通过 `preflight` 检查操作系统、架构、GitHub 登录、Jira 配置、工作流配置、源码目录和工作空间匹配关系。

### 6.2 任务准入与接管

- 拉取当前研发工程师可处理的 Jira 任务。
- 检查负责人、任务类型、项目、状态、目标仓库、标准流程和权限。
- 根据 profile 将 Jira 状态映射为标准业务阶段。
- 生成并绑定唯一 `agentic_run_id`。
- 校验 `agentic_id`、工作空间和任务所有权。
- 缺少字段或映射不完整时阻断，并输出补卡或人工处理动作。

### 6.3 受控执行与人工门禁

- 所有成熟操作都有契约、输入输出、失败码和副作用说明。
- 写操作执行前检查当前阶段、策略、授权、所有权和人工确认。
- 研发工程师确认版本化计划后，可以授予工作项级连续执行授权。
- 连续授权仍受范围、风险、验证和外部事实变化约束。
- 在授权有效且验证通过时，可以自动完成提交、推送任务分支和创建目标为 `develop` 的 PR，并停在 PR 审查节点。
- `master`、`main`、`develop`、`release/*` 及同类保护分支禁止自动推送；合并、发布、范围扩张、强推、历史改写等动作不被静默放行。

### 6.4 外部系统协作

- 读取和受控回写 Jira 任务、字段、状态、评论和证据。
- 检查 Git 工作区、分支、提交、差异和验证结果。
- 读取 GitHub PR、CI checks、commit status、评论和 Review。
- 生成 PR 准备计划、审查反馈修复计划和标准证据。
- 通过项目 profile 适配不同项目的字段、状态、仓库和审查节点。

### 6.5 证据、恢复和清理

- 记录每次接管的运行编号、阶段、操作、结果、失败码和审计状态。
- 生成节点表单、完成证据和 PR 证据。
- 从结构化事件和外部事实恢复任务上下文。
- 在恢复前重新检查 Jira 所有权、Agent 绑定、目标仓库和当前阶段。
- 完成任务审计后再释放 Agent 绑定、工作空间租约和接管资源。

### 6.6 反馈与标准演进

- 按运行编号、任务类型、失败码和时间范围生成反馈报告。
- 分析重复失败、人工确认热点、缺失字段趋势和恢复模式。
- 生成可操作的标准资产改进建议。
- 通过人工确认、版本化发布和回滚控制规范演进。

### 6.7 发布与问题修复

- 支持安装资源构建、校验、发布、Hotfix 和回滚流程。
- 采用项目级版本化 Hooks 和发布脚本保护主分支治理。
- 标准资产、profile、policy、runbook 和模板优先于临时改代码修复运行问题。
- 只有确认是 CLI 逻辑错误，才进入二进制修复和新版本发布路径。

## 7. 端到端任务模型

### 7.1 正常任务

```text
研发工程师选择任务
→ AgenticOps 只读检查准入事实
→ 人工确认接管
→ 创建 agentic_run_id
→ AIAgent 读取标准资产和任务上下文
→ 形成版本化计划
→ 人工确认计划和授权范围
→ AIAgent 实现、验证和整理证据
→ AgenticOps 检查 gate 和外部事实
→ 进入 PR / CI / 专业审查
→ 回写任务审计
→ 清理绑定并结束本次运行
```

### 7.2 信息缺失

```text
目标仓库、验收标准或状态映射缺失
→ 阻断接管或推进
→ 返回稳定失败码
→ 输出 required_human_action
→ 生成补卡材料
→ 人工补齐后重新检查
```

### 7.3 中断和失败

```text
节点失败
→ 读取失败码和当前事实
→ 重试、重做、补充信息或转人工
→ 外部写入不确定时先回读
→ 记录恢复事件和证据
→ 继续或结束当前运行
```

## 9. 当前边界和待解决问题

项目需要明确区分“已经有的能力”和“下一步要做的事情”：

- 模型调用不是 AgenticOps 核心控制层的既有能力；核心保持模型无关，模型接入属于可替换的外部执行层或后续桥接层。
- 不引入 Web 控制台或后台常驻调度；需要补齐标准操作接口隔离、本地文件交接和 Jira 编号目录治理。
- 已允许在有效工作项授权下自动提交、推送任务分支并创建目标为 `develop` 的 PR；保护分支自动推送规则需要补充到 policy、契约和测试。
- 任务审计日志当前以本地 Jira 编号目录为最终管理位置，后续再评估对接独立审计服务。
- 不同 Jira 工作流中的 transition 采用 ID 严格优先、唯一名称受控兜底；来源/目标状态不匹配或出现歧义时阻断，不能由 Agent 猜测。
- 当前优先研发 Jira 主链路，更多任务类型、团队级分析和公司事务扩展尚未完成。

## 10. 推进计划

### 阶段一：稳定研发单任务闭环

目标：让研发工程师可以安全地从 Jira 接管一个任务，推进到 PR 审查并完成审计。

重点交付：

- 安装、初始化、preflight 和 profile 解析稳定。
- 接管、连续授权、阶段推进和完成清理稳定。
- 证据、PR 事实和审计可回读。
- 授权后可自动推进到任务分支提交、推送和创建 `develop` PR，但不自动推送保护分支。
- 标准操作之间通过契约接口和 Jira 编号本地目录交接任务资料。
- fake E2E、资源测试、构建测试、安装测试和 Go 测试成为固定回归入口。

### 阶段二：完成真实试运行问题修复

目标：把真实 AO 试运行暴露的控制层问题收敛为可靠基线。

重点交付：

- 隔离自定义安装目录的环境副作用。
- 使用真实、可注入的运行时间。
- 让 Jira 接管字段和状态转换原子一致，并在成功后回读。
- 修复运行上下文锚点和恢复判断。
- 完善中文完成证据和验收章节。
- 通过稳定事实接口读取 GitHub PR、CI 和 Review。
- 将人工恢复记录为结构化反馈事件。

### 阶段三：完善标准资产和项目适配

目标：让新增项目主要通过 profile、policy、runbook、template 和表单配置接入，而不是复制流程逻辑。

重点交付：

- 收敛公司层、项目层、个人层和工作空间层资产边界。
- 增加任务分类、标准流程和项目工具声明。
- 为常见缺失字段、PR 失败、CI 异常、恢复和升级补齐运行手册。
- 建立标准资产兼容性、发布、回滚和效果评估规则。
- 固化保护分支模式匹配、PR 目标分支校验和本地任务目录生命周期。

### 阶段四：按风险扩展自动化

目标：根据证据决定哪些低风险节点可以减少人工打断，哪些节点继续保留人工门禁。

重点交付：

- 按任务复杂度、影响范围和风险等级分流。
- 用真实运行记录评估连续授权和低风险自动化的安全边界。
- 增加团队级失败聚合、人工介入热点和标准效果指标。
- 继续保留合并、发布、范围变更和高风险动作的明确责任人。

### 阶段五：扩展为公司 AI 操作控制层

目标：把研发任务中沉淀的执行标准扩展到调查、发布、升级、客户问题和其他公司事务。

重点交付：

- 统一事务类型、阶段、操作、表单、门禁、证据和反馈模型。
- 让不同 Agent、不同模型和不同外部系统共享同一套治理边界。
- 以版本化标准资产替代个人经验，以反馈闭环驱动规范持续改进。

## 11. 成功标准

AgenticOps 是否成功，不以命令数量或文档数量判断，而以以下结果判断：

- 研发工程师可以在较短培训后使用标准流程接管任务。
- AIAgent 不需要猜测任务事实、字段映射和高风险权限。
- 未授权的高风险副作用能够被稳定阻断。
- 任务中断后可以从事实源和结构化事件恢复。
- Jira、Git、GitHub、CI 与任务证据保持一致。
- 失败、人工恢复和重复补卡能够进入反馈分析。
- 每个 Jira 任务的审计、证据和反馈材料能够在本地编号目录中独立定位。
- 经过确认的改进可以发布、回滚并验证效果。
- 项目增加新任务类型或新外部系统时，不需要重建核心控制层。

## 12. 结论

AgenticOps 的核心优势不是让 AI 更会聊天，也不是把所有模型和工具堆在一起，而是建立一套可以进入企业研发流程的执行纪律：

```text
明确任务
→ 明确授权
→ 明确阶段
→ 明确操作
→ 明确门禁
→ 明确证据
→ 明确恢复
→ 明确审计
→ 明确如何改进
```

当前项目已经从纯设计进入受控运行时实现阶段，具备安装、工作空间、任务接管、事实协作、门禁、证据、恢复、反馈和发布治理的基础。后续推进重点不是盲目扩大功能，而是先完成真实研发闭环的可靠性，再把成熟经验沉淀成可复用的公司级 AI 执行标准。
