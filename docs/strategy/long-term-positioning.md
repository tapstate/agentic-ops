# AgenticOps 长期定位

## 1. 长期目标

AgenticOps 首先落地在研发 Jira 任务处理场景。长期目标是把公司员工执行标准流程化、资产化，让 AI 在遇到问题时能按公司当前规范处理，并通过执行记录持续沉淀和优化规范。

AgenticOps 不要求人记住每一种事务应该怎么处理，而是把处理方式沉淀成可执行、可审计、可回滚的规范资产。

更具体地说，AgenticOps 需要回答四个问题：

- 怎么形成标准：从真实任务、失败日志、人工介入点和重复问题中沉淀。
- 形成什么样的标准：形成 AI 员工手册、操作契约、工作流配置、策略、运行手册、模板和成熟原子化操作。
- 标准流程出问题怎么办：AIAgent 优先按运行手册自助处理；不能安全处理时阻断、记录原因并转人工。
- 员工如何低培训上岗：研发工程师使用安装后的 `agentic-cli` 和标准操作入口，不需要理解源码、编译环境或每个流程细节。

## 2. 员工执行标准模型

AgenticOps 把公司流程抽象为“员工执行标准”，而不是只抽象为工具命令。

员工执行标准包含：

- 节点职责：每个流程节点要解决什么问题，由 AIAgent、研发工程师、代码审查人、QA、运维、安全或其他专业角色中的谁承担。
- 标准动作：该节点必须执行、检查或拒绝的事项。
- 标准表单：该节点完成后必须输出的结构化数据，代表对应事项已经执行过。
- 审查结论：专业角色在对应节点对 AIAgent 产出、风险和证据做出的通过、退回、补充或阻断判断。
- 推进规则：根据表单数据、审查结论、失败码和人工门禁决定下一步、重试、重做、升级或停止。

AIAgent 使用 AgenticOps 的目标，是按这些标准完成任务，而不是仅把任务做成一次代码差异。不同专业角色通过审查节点优化标准流程：他们不需要改写每次 AI 执行过程，但需要判断某类产出是否合格、某个表单字段是否足够、某个失败是否应沉淀为新的策略、运行手册、模板或工作流配置。

## 3. 公司事务处理模型

无论事务来自 Jira、PR、CI、客户反馈、线上问题还是内部流程异常，AIAgent 都应先进入统一判断模型：

```text
识别事务类型
-> 判断当前阶段
-> 选择操作 / 运行手册
-> 执行门禁
-> 处理事务
-> 输出节点表单
-> 记录过程和审查结论
-> 回写关键状态和证据
-> 生成反馈
-> 提出规范改进建议
```

该模型继续使用第一阶段已经确认的字段：

- `task_type`
- `current_stage`
- `next_action`

AIAgent 不按固定角色工作，也不靠临场记忆猜流程。每个操作的输出都应能解释当前阶段是否完成、下一步是什么、是否允许重试、是否必须重做前序节点、是否需要专业角色审查。

## 4. 框架与原子操作模型

AgenticOps 的框架应先稳定定义大的流程环节，而不是把所有执行细节一次性写死。

分层职责：

- Framework：定义任务生命周期、阶段状态、门禁、表单、错误模型、重试重做、审查节点和复盘演进机制。
- Atomic Operation：把已经成熟固化的交互逻辑沉淀为稳定、原子化、可验证、可审计的操作；脚本入口只做受控编排或调用。
- AIAgent Execution：在具体环节内处理上下文差异、完成任务、记录证据，并把可复用经验沉淀到反馈事件。
- Periodic Review：周期性分析执行记录，把高频失败、人工退回、重复补卡和有效经验转化为工作流配置、策略、运行手册、模板或操作改进建议。

成熟度原则：

- 未稳定的经验先进入执行记录和复盘建议，不直接固化为脚本。
- 重复出现、边界清晰、输入输出稳定的交互逻辑，才升级为原子操作。
- 原子操作必须小、稳定、幂等或可恢复，并有明确失败码和人工动作。
- 框架必须容错性高：允许节点失败、恢复、重试、重做、转人工和延后固化。
- 可进化方案必须保留人工审查和版本化发布，不允许 AIAgent 未经确认自动改写标准资产。

## 5. 可执行规范资产

公司规范不应只存在于口头经验、聊天上下文或散落文档中。AgenticOps 应逐步把规范拆成可版本化资产：

```text
company-handbook/
  公司级原则、通用边界、敏感信息规则

operation-contracts/
  每类事务能做什么、输入输出是什么、失败码是什么

atomic-operations/
  成熟固化的原子化操作入口

workflow-profiles/
  不同团队、不同项目、不同系统流程如何映射

task-forms/
  每个生命周期节点需要哪些字段、谁填写、谁审查、缺失时如何处理

policies/
  哪些动作必须人工确认，哪些动作禁止自动执行

templates/
  Jira 评论、拉取请求证据、任务审计记录、复盘、升级说明

runbooks/
  问题发生后按什么步骤排查、处理、升级、回写
```

这些目录是长期信息架构方向。具体落地必须按稳定架构、实施计划和发布资产逐步推进，不能因为某个阶段尚未实现就改变终态信息架构。

其中 `AgenticOps` 是项目和体系，`AgenticCLI` 是成熟经验沉淀后的执行入口组件，`agentic-cli` 是给研发工程师和 AIAgent 使用的 CLI 二进制。除非问题来自 `agentic-cli` 二进制逻辑错误，否则应优先通过标准资产自助修复、阻断或转人工。

## 6. 问题处理闭环

问题出现后，AIAgent 应按规范处理，而不是直接猜测或绕过流程。

标准流程出问题时，处理优先级是：

```text
检查当前操作 / 运行手册
-> 能按标准资产自助处理则处理
-> 需要补充 Jira 信息则阻断并输出补全模板
-> 需要调整工作流配置 / 策略 / 模板则生成改进建议
-> 存在风险、权限或标准冲突则转人工
-> 如果确认是 agentic-cli 二进制逻辑错误，再进入 CLI 修复发布路径
```

示例：Jira 卡片缺少目标仓库。

```text
AIAgent 发现缺少 target_repo
-> 查询 操作契约
-> 停止接管
-> 输出 required_human_action
-> 生成 Jira 补充模板
-> 记录 missing_field 事件
-> 按需反馈报告汇总同类问题
-> 提出改进 Jira 创建模板或字段校验的建议
```

这条链路的目标是让问题变成可分析、可治理的规范改进输入，而不是依赖某个人下次记得提醒。

## 7. 重试和重做模型

AgenticOps 必须显式支持重试和重做。

- 重试：当前节点动作失败，但输入、审查结论和流程阶段仍然有效，可以在同一 `run_id` 或同一阶段内再次执行。
- 重做：前序节点的输入、表单数据、审查结论或范围边界发生变化，必须回到对应节点重新生成表单和证据。

是否重试或重做不能由 AIAgent 凭感觉决定，必须基于：

- 当前 `task_type`、`current_stage`、`next_action`。
- 最近一次操作输出。
- 标准表单字段是否完整。
- 专业审查结论是否通过。
- failure code 是否允许 retry。
- 策略和门禁是否要求人工确认。

这让任务恢复不依赖聊天上下文，也避免“失败后继续往下做”或“信息变更后沿用旧结论”。

## 8. 规范演进门禁

AgenticOps 可以帮助生成规范改进建议，但不能未经人工确认自动修改公司规范。

规范演进必须经过：

```text
Observation 观察
-> Proposal 改进建议
-> Review 人工确认
-> Accepted Change 合入规范
-> Release 同步给使用者
-> Effectiveness Check 检查问题是否减少
```

所有规范变更必须可追溯、可回滚，并能说明影响范围。

## 9. 落地切入点

AgenticOps 先从研发 Jira 任务切入：

- 安装 AgenticOps。
- 初始化项目 AI 工作空间。
- 初始化 AIAgent 能力。
- 从 Jira 接管任务。
- 记录执行过程、节点表单和关键审查状态。
- 回写证据。
- 按需生成反馈报告。

真实 Jira / GitHub 写操作、推送、创建拉取请求、合并、发布、公司级事务平台化和规范变更，都必须按操作契约、策略门禁、人工确认和独立实施计划逐步纳入，不能因为分阶段推进而弱化长期目标或安全边界。

## 10. 长期形态

AgenticOps 长期形态是公司事务的 AI 操作控制层。

它不替代 Jira、Confluence、GitHub、Slack、飞书等事实源，而是在事实源之上提供：

- 标准流程。
- AI 操作入口。
- 门禁控制。
- 执行记录。
- 证据回写。
- 反馈分析。
- 规范演进。
