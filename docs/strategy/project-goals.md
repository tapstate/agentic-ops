# AgenticOps 项目目标

本文是 AgenticOps 设计、优化、计划和架构调整的判断依据。工作项、状态、阻塞和
验收由 Jira 管理，不在仓库维护第二份执行计划。

## 1. 产品定位

AgenticOps 是公司级 Agentic 研发基础设施，为不同 Agent 平台提供
统一的流程规则、操作门禁、任务恢复和证据边界。它不替代 Agent 平台，也不替代
Jira、Git、GitHub、CI 和人工审查。

核心投入是流程、规则和门禁的调试与沉淀。工具只服务规则执行，必须小、可替换、
可验证；如果业务联调长期消耗在工具链修改上，应视为架构边界不清晰的信号。

## 2. 当前目标

v1.x 以 ao-gate-poc 的 Hook + 声明式 Policy 思想为基线，先让 TapData 研发任务
稳定可用：

- macOS、Linux 可快速安装，后续可运行在独立 Docker 实例。
- 所有已接入 Agent 共用 Gate、Policy、任务状态和项目规则，只保留薄平台适配。
- 一个工作空间绑定一个产品项目，可同时接管该项目下多个 Jira 任务；每个任务可以
  修改多个仓库，状态、授权、审计和 CI 证据按任务隔离并统一注册。
- Jira 状态、表单、仓库分支、准入和验证方式按产品项目独立配置。
- 主流程稳定且流畅；上线后按效率、质量、体验和项目覆盖持续快速迭代。
- `v0.7` 保存重构前实现；v1.x 在 `develop` 开发，经发布流程进入 `main`。

TapTest、TapState 和其它产品在 `projects/<project>/` 独立适配，不把项目差异写入
公共 Gate、Policy 或 Agent Adapter。

## 3. 核心价值

- 基于标准资产和外部事实执行，而不是依赖一次聊天提示。
- 在副作用发生前统一自动放行、请求确认或拒绝。
- 将任务、仓库、分支、范围和验证方式绑定到明确授权。
- 支持中断恢复，保留必要事件与验证证据。
- 从高频阻塞、人工退回和失败中识别规则或项目适配改进点。

## 4. 架构准绳

```text
Standard Contract + Agent/Tool Adapter + Gate Core + Policy + Workflow + Project + Bootstrap
```

- **Standard Contract** 定义 Gate 请求、判定和 Adapter Manifest 的稳定边界。
- **Agent Adapter** 只转换平台事件与判定；**Tool Adapter** 只映射 MCP、CLI 操作。
- **Gate Core + Policy** 负责标准操作、分级和授权判定；配置是规则事实源。
- **Workflow** 只承载阶段、授权、CI、证据和恢复等小型确定性逻辑。
- **Project** 保存项目 Jira 映射、仓库分支、准入、验证和 Runbook。
- **Bootstrap** 只负责安装、更新、回退和工作目录接线。
- **Internal** 只服务 AgenticOps 仓库自身的故事审查和发布，不是产品运行层。

产品运行采用“中央产品根目录（Product Root）+ 薄项目工作空间”：源码目录和 `~/.agentic-ops`
安装目录具有相同产品结构和薄入口，非 Git 本地状态均归入各自 `.local/`；项目
工作空间使用 `.agenticops/` 区分初始化信息、工作空间配置和按任务隔离的业务运行
数据，不复制 Policy、Project Skill 或 Runtime。维护时直接在源码目录运行；发布使用时
稳定安装目录是产品根目录，两者不形成不同运行模式。

Hook、MCP、Skill 和工作目录配置是 Manifest 与模板生成的产物。Adapter 必须无状态，
不得依赖 Workflow、Project 或 Policy，并通过固定代码预算和禁止依赖检查；不支持的
平台能力通过 Manifest 声明和保守降级，不增加兼容 Runtime。

现役架构只有一套产品内核。统一 `agenticops` 入口只负责安装生命周期、工作目录
接线、诊断、修复和启动 Agent，不承载门禁、项目规则或任务状态机。不得以角色、
命令或兼容为理由恢复 `maintainer/`、
`developer/` 两个工作面，也不得恢复 `ao-work` 大一统 Runtime。未来若增加统一
入口，只能是薄启动或诊断入口，不能成为规则和业务能力中心。

## 5. 流程连续性与安全边界

未迁移能力不是系统级阻塞理由。优先使用 Agent 原生能力或 Adapter；没有安全自动
路径时，只暂停当前副作用步骤并输出结构化人工接力，继续无依赖的准备工作。

以下原因必须停止：业务事实不可信、权限不足、风险要求人工决策、外部写结果不明。
合并、发布、Tag、强推、历史改写和保护分支写入不被普通任务授权覆盖。

- Jira 是任务、需求、负责人、状态、评论和任务证据事实源。
- Git 是代码、分支、提交和本地验证事实源。
- GitHub PR/CI 是审查、检查和合入记录事实源。
- `.agenticops/` 只保存工作空间绑定、初始化清单及本地执行、恢复、授权和门禁事件。

Hook 是流程控制点，不是本机安全沙箱；凭证最小化、服务端保护、CI 和人工审查仍
是最终安全边界。AgenticOps 故障不得静默绕过或伪造成功。

## 6. 能力迁移与持续迭代

旧版能力不按文件或命令逐项恢复。迁移前先证明它解决真实、高频的问题：

1. 公司通用操作边界进入 `policies/`。
2. 产品项目差异进入 `projects/<project>/`。
3. 平台协议差异进入 `adapters/`。
4. 协作指导进入 Skill，构建和排障知识进入 Runbook。
5. 只有输入输出稳定且必须确定执行的逻辑进入 `workflow/`。

优先级按处理效率、产出质量、使用体验和项目覆盖排序。新增能力必须绑定真实研发
故事并提供与风险相称的可执行验证。

## 7. 不做什么

- 不建立新的任务、代码、审查或 CI 事实源。
- 不为 Agent 已有能力重复实现 Jira、Git、GitHub 客户端。
- 不让不同 Agent 各自维护流程规则。
- 不把项目特例写入公共内核。
- 不依赖 Skill 散文代替可执行门禁。
- 不把中央源码池作为正确性前提；它只可能是后续效率优化。
- 不以功能数量作为成功标准，以主流程稳定、效率和产出质量为准。
