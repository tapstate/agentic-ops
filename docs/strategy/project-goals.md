# AgenticOps 项目目标

本文是 AgenticOps 设计、优化、计划和架构调整的判断依据。工作项、状态、阻塞和验收由 Jira 管理，不在仓库维护第二份执行计划。

## 1. 产品定位

AgenticOps 是公司级 Agentic 研发基础设施，为不同 Agent 平台提供统一的流程检查点、任务恢复和证据边界。Agent 自主使用原生工具执行，AgenticOps 在本地流程进入、退出、恢复和完成时检查明确条件。它不替代 Agent 平台，也不替代 Jira、Git、GitHub、CI 和人工审查。

核心投入是提高研发流程的产出质量与处理效率。流程明确阶段成果和验收标准，脚本加速稳定的重复操作、减少 Agent 分析处理，检查核验实际成果而非指定工具的成功回执。工具必须小、可替换、可验证；如果业务联调长期消耗在工具链修改上，应视为架构边界不清晰的信号。

## 2. 当前目标

v1.x 沿用 ao-gate-poc 的标准契约与声明式 Policy 分层，将使用者门禁收敛到确定性 Workflow 检查点，先让 TapData 研发任务稳定可用：

- macOS、Linux 可快速安装，后续可运行在独立 Docker 实例。
- 所有已接入 Agent 共用 Gate、Policy、任务状态和项目规则，只保留薄平台适配。
- 一个工位绑定一个产品项目；同一时间只处理一个任务，完整多仓工程按任务准备，现役源码保留行为与目标清理行为分开说明，并发由多个工位承担。
- Jira 状态、表单、仓库分支、准入和验证方式按产品项目独立配置。
- 主流程稳定且流畅；上线后按效率、质量、体验和项目覆盖持续快速迭代。
- `v0.7` 保存重构前实现；v1.x 在 `develop` 开发，经发布流程进入 `main`。

TapTest、TapState 和其它产品在 `projects/<project>/` 独立适配，不把项目差异写入公共 Gate、Policy 或 Agent Adapter。

### 单任务工位

工位采用“一工位、一套完整工程、一个当前任务”的模型。目标是接管、处理、归档和恢复形成成果闭环，清理操作收敛为“清理任务”和“清理工位”，普通授权不因时间流逝失效；同工位执行接管采用闲置判断与显式交接。具体行为只在[工位合同](../architecture/single-task-station.md#任务生命周期目标合同)维护，数据管理统一遵循[数据生命周期开发规范](../development-data-lifecycle.md)。不新增环境池、归档数据库或分布式接管锁。

完整目标的实现状态由工位合同集中说明。当前源码候选已引入两个清理范围，旧安装仍按其实际版本执行；文档调整不授权跨 epoch 采用旧状态或绕过成果保全。

## 3. 核心价值

处理到一半因 AgenticOps 优化而升级时，研发以同一 Jira 任务继续工作。有效设计、决定、GitHub 分支/提交/PR/CI、验证依据和剩余事项在正常协作节点持续记录；升级前补齐未持久化成果。目标是在安全切换程序并采用新版指引后，现接管任务按正常流程继续；符合当前要求的现场直接使用，不符合时由所属功能发现差异、AI 修补、程序复查后继续。默认保留任务及仍有效的运行身份、授权和成果，不把退出、purge 或新建 run 作为升级必经步骤；无法安全采用的局部现场才评估重建。旧记录不全由 AI 从可信来源核实并协助研发补齐，不新增逐版本迁移器或第二份任务台账。

这一目标尚未由当前实现完整支持：现役 epoch 检查与跨代际退出路径仍有效，见[工位合同](../architecture/single-task-station.md#10-升级与恢复)。具体开发要求集中在[外部依赖检查与修补继续](../maintenance-guide.md#外部依赖检查与修补继续)。不承诺运行进程或 Agent 会话无缝热更新，也不承诺任意历史数据自动无损转换。

- 基于标准资产和外部事实执行，而不是依赖一次聊天提示。
- 在 Workflow 实际变更状态前核对准入、方案确认与证据；缺项时明确补齐方式，只暂停依赖该条件的推进。
- 将任务、仓库、分支、范围和验证方式绑定到明确授权。
- 支持中断恢复，保留必要事件与验证证据。
- 从高频阻塞、人工退回和失败中识别规则或项目适配改进点。

## 4. 架构准绳

```text
Standard Contract + Agent/Tool Adapter + Gate Core + Policy + Workflow + Project + Bootstrap
```

- **Standard Contract** 定义 Gate 请求、判定和 Adapter Manifest 的稳定边界。
- **Agent Adapter** 只声明平台指引、接线与启动方式；**Tool Adapter** 只声明原生 MCP 接线，不分类或拦截工具调用。
- **Gate Core + Policy** 负责标准操作、分级和授权判定；配置是规则事实源。
- **Workflow** 只承载阶段、授权、CI、证据和恢复等小型确定性逻辑。
- **Project** 保存项目 Jira 映射、仓库分支、准入、验证和 Runbook。
- **Bootstrap** 只负责安装、更新、回退和工作目录接线。
- **Internal** 只服务 AgenticOps 仓库自身的故事审查和发布，不是产品运行层。

产品运行采用“安装目录 + 薄项目工位”：安装目录默认是 `~/.agentic-ops`，保存 AgenticOps 中央产品资产、本机配置及 `.archive/<run-id>` 正式任务档案；项目工位使用 `.agenticops/` 保存初始化和单 current 状态，config/source/runtime 分离配置、源码与运行产物，不复制 Policy、Project Skill 或 Runtime。正式档案不放在工位内，避免随工位清理丢失。AgenticOps 源码目录仅用于产品维护，不是用户的第三种工作目录。

安装目录的 `update` 只跟随安装时记录的分支；它不得自动覆盖本地修改、处理分叉或推送本地提交。

MCP、Skill、平台指引和工作目录配置是 Manifest 与模板生成的产物。Adapter 使用声明式 Manifest 与模板，必须无状态，不得依赖 Workflow、Project 或 Policy；不生成工具 Hook 或兼容 Runtime，不支持的平台启动方式显式声明为手动。

使用者工位不生成通用 Agent 工具 Hook。Git、GitHub、Jira、编辑、构建与测试交给 Agent 原生权限和服务端控制；不承诺检查点能阻止 Agent 在阶段推进前执行这些动作。Workflow 在持锁的状态变更入口校验当前 run、预期阶段及确认绑定；不保留通用工具 Hook 执行链。已有 Hook 接线必须显式确认迁移，普通 start/refresh 不得静默撤除。工位没有可写的门禁档位开关；源码和安装产品根共用这一产品语义。

现役架构只有一套产品内核。统一 `agenticops` 入口只负责安装生命周期、工作目录接线、诊断、修复和启动 Agent，不承载门禁、项目规则或任务状态机。不得以角色、命令或兼容为理由恢复 `maintainer/`、`developer/` 两个工作面，也不得恢复 `ao-work` 大一统 Runtime。未来若增加统一入口，只能是薄启动或诊断入口，不能成为规则和业务能力中心。

## 5. 流程连续性与安全边界

辅助能力缺失或脚本异常不是系统级阻塞理由。Agent 可在原授权和范围内使用原生能力或 Adapter 接管剩余工作，复用已核验成果，再按相同标准验收；材料缺项可通过研发交互补齐。没有安全执行路径时，只暂停受影响的步骤，说明已完成内容、剩余缺项和所需决策，继续无依赖的准备工作。验收能力异常时保持待核验，不伪造通过。

以下原因必须停止：业务事实不可信、权限不足、风险要求人工决策、外部写结果不明。合并、发布、Tag、强推、历史改写和保护分支写入不被普通任务授权覆盖。

- Jira 是任务、需求、负责人、状态、评论和任务证据事实源。
- Git 是代码、分支、提交和本地验证事实源。
- GitHub PR/CI 是审查、检查和合入记录事实源。
- `.agenticops/` 只保存工位绑定、初始化清单及本地执行、恢复、授权和门禁事件。

当前 run 保存 Jira 初始快照、用户确认后的有效执行事实及同步差异。Jira 回读不自动覆盖本地确认；版本不推导 Git 分支。评论、水印、版本与状态同步失败只形成待办，不阻止不依赖它的本地阶段。未知结果先核对原操作，PR 后总结统一披露跳过处理与警告；本地完成不代表 Jira 已同步或验收通过。

流程检查点不是本机安全沙箱；凭证最小化、服务端保护、CI 和人工审查仍是最终安全边界。AgenticOps 故障不得静默绕过或伪造成功。

方案确认在流程检查点核验，不再代表每次外部调用均经过 AgenticOps 授权。Jira 同步保留准备、原生调用与结果回读，取消通过 Hook 强制单次调用的保证；结果未知必须先回读。直接改写本地状态文件不属于受支持入口，检查点与本地记录也不提供身份认证或防篡改安全边界。

功能固化与 AI 接续的判断、异常处理和跨功能闭环验收统一遵循[开发原则](../maintenance-guide.md#确定性执行与-ai-接续原则)。正常流程依赖 AI 修补程序自产状态属于产品缺陷，不能作为智能化收益；现役能力与待实现改进分开验证。

## 6. 能力迁移与持续迭代

旧版能力不按文件或命令逐项恢复。迁移前先证明它解决真实、高频的问题：

1. 公司通用操作边界进入 `policies/`。
2. 产品项目差异进入 `projects/<project>/`。
3. 平台协议差异进入 `adapters/`。
4. 协作指导进入 Skill，构建和排障知识进入 Runbook。
5. 只有输入输出稳定且必须确定执行的逻辑进入 `workflow/`。

优先级按处理效率、产出质量、使用体验和项目覆盖排序。优化先考虑删除重复约束、纠正判定和复用现有能力；新增规则、配置或状态的收益应足以承担使用与维护成本，不能把一次故障直接扩大为通用约束。新增能力必须绑定真实研发故事并提供与风险相称的可执行验证。

## 7. 不做什么

- 不建立新的任务、代码、审查或 CI 事实源。
- 不为 Agent 已有能力重复实现 Jira、Git、GitHub 客户端。
- 不让不同 Agent 各自维护流程规则。
- 不把项目特例写入公共内核。
- 不依赖 Skill 散文代替可执行门禁。
- 不把源码池作为已准备工位的正确性前提；源码池仅用于下载加速，缺失仓库先下载入池，再生成独立工位源码。
- 不以功能数量作为成功标准，以主流程稳定、效率和产出质量为准。
