# AgenticOps 项目目标

本文是 AgenticOps 做设计、优化和计划前必须读取的目标文档。它用于判断后续演进方向：项目为什么存在，最终要进化成什么，当前阶段先做到哪里，以及新增能力应该按什么准绳取舍。

本文只记录长期价值、最终目标、阶段目标和演进准绳。具体推进事项、状态跟踪、阻塞和验收由 Jira 管理；项目 AI 工作空间只保存本地执行与恢复状态，仓库不再建立第二份计划事实源。

## 0. 产品身份与角色

一个业务项目 AgenticOps 工作空间代表一名公司的 AI 研发员，而不是一套供多人共享和临时切换身份的工具。项目工作空间的交付产物是可被指导、可持续升级的研发员；Skill、Python Runtime、Shell Bootstrap、Rule 和标准资产共同构成这名研发员的能力。

公司员工指导员负责为研发员安装和升级能力、明确任务与授权、校对产出、执行人工门禁，并把反复出现的问题反馈为标准改进。维护 `tapstate/agentic-ops` 源头项目也是公司员工指导员的一项职责，其目标是指导和进化研发员，不是代替研发员执行日常业务任务。

安装与项目必须分离：`~/.agentic-ops` 是 developer-only sparse managed clone，提供一名研发员的运行能力与安装级身份/凭证（`user/identity.yaml`、`user/.env`），不代表任何具体项目，也不包含项目维护能力。业务项目工作空间保存项目、Jira 站点、仓库、流程和任务上下文，并持安装目录身份引用（agent.json schema v4 `install_identity_ref`）防错装。同一安装下的多个项目工作空间继承同一研发员身份；多名研发员必须使用隔离安装，不允许跨安装或从工作空间拼接身份凭证。

项目必须在结构、命令和 AI 入口上硬隔离两个工作面：`maintainer` 只维护 AgenticOps 源头，入口为 `ao-maint`；`developer` 只执行其它业务项目的研发任务，入口为 `ao-work`。根仓库 AI 入口固定进入 `maintainer`，业务项目工作空间 AI 入口固定进入 `developer`；不得依赖同一命令的 mode 参数、聊天上下文或 AI 自主判断切换工作面。

## 1. 项目价值

AgenticOps 的核心价值，是把 AIAgent 从临场聊天助手变成流程内可管理、可审计、可恢复、可复盘的执行主体。

它要解决的问题不是“让 AI 做更多事”，而是让 AI 在公司认可的员工执行标准内做事：

- 让 AIAgent 面向标准资产工作，而不是依赖一次聊天里的临场提示。
- 让公司员工指导员继续负责任务授权、范围确认、风险判断和关键动作确认。
- 让代码审查人、QA、运维、安全和流程负责人继续在对应节点做专业审查。
- 让每次 AI 执行都有 `agentic_run_id`、标准表单、事件记录、证据和下一步动作。
- 让失败、阻塞、补卡、人工退回和重复问题成为可分析的流程改进输入。
- 让成熟经验沉淀为操作契约、工作流配置、策略门禁、运行手册、模板、Skill 和 Python Runtime 原子操作。

AgenticOps 的价值不在于替代现有协作系统，而在于让 AI 员工进入现有协作流程，并把执行过程变成可治理的标准资产。

## 2. 最终目标

AgenticOps 的最终目标，是成为公司事务的 AI 操作控制层。

它不替代 Jira、Git、GitHub、CI、审查流程或人工决策，而是在这些事实源之上提供：

- 标准流程：定义任务分类、阶段、标准动作、表单输出和推进规则。
- 门禁控制：明确哪些动作允许自动执行，哪些必须阻断、补充信息或等待人工确认。
- 证据回写：把关键状态、关键信息、表单数据、验证结果和任务审计记录写回对应事实源。
- 反馈分析：从执行记录、失败码、人工退回和重复补卡中发现流程问题。
- 规范演进：把经过人工确认的改进建议沉淀为标准资产，并支持版本化发布和回滚。

长期形态中，AIAgent 遇到公司事务时，应先识别事务类型、判断当前阶段、选择操作或运行手册、执行门禁、输出节点表单、记录过程和审查结论，再回写关键状态和证据。它不能靠猜测绕过事实源、流程负责人或专业审查。

## 3. 阶段目标

AgenticOps 先落地研发 Jira 任务链路。

当前阶段要优先跑通一条真实、可控、可复用的主链路：

```text
安装 AgenticOps 共享能力
-> 初始化业务项目工作空间并创建研发员
-> 配置研发员账户和能力
-> 拉取该研发员 Jira 账户名下待办
-> 公司员工指导员授权接管任务
-> 研发员本地执行、验证和整理证据
-> 回写任务证据
-> 公司员工指导员确认高风险动作
-> 按 Project Profile 进入既有拉取请求、CI、专业审查和合入流程
-> 提交任务完成审计
-> 形成反馈分析和改进建议
```

developer 业务流程按 Profile 显式版本化：旧 `development_change_v1` 继续停在内置拉取请求审查节点；`development_change_v2` 取消 developer 标准流程内置代码审查，改为绑定最终 PR Head 持续观察必需 CI，在最多三次授权内修复后通过即结束 AIAgent 运行。该模式不取消项目另行要求的 QA、安全、运维或流程审查，也不授权合并、Jira Done、发布、Tag 或保护分支写入。

阶段目标的重点是闭环可靠，而不是扩大自动化范围。真实 Jira 写操作、Git 推送、GitHub 拉取请求创建、合并和正常发布都必须经过策略门禁和人工确认。AgenticOps 源头维护的快速 Hotfix 是显式例外：公司员工指导员只需调用 `maintainer/scripts/hotfix.sh <KEY>` 即构成本次授权，脚本自行完成分支切换、远端同步和原子合并，不再设置额外门禁或与 Jira 交互，只用 Git 一致性检查、自动合并冲突检测和 atomic push 防止部分推送与历史改写。

## 4. 不做什么

AgenticOps 不做以下事情：

- 不替代 Jira，也不创建新的任务管理事实源。
- 不做脱离公司员工指导员的自主研发机器人。
- 不绕过代码审查人、QA、运维、安全或流程负责人的专业审查。
- 不用本地运行日志、反馈报告或聊天上下文替代 Jira、Git、GitHub / CI 等事实源。
- 不让 AIAgent 临场猜测 Jira 字段、目标仓库、验证方式、任务分类或流程阶段。
- 不把尚未稳定的临场经验直接固化成脚本、策略或默认流程。
- 不让 Shell Bootstrap 承载 Jira、GitHub、Git、操作契约、策略门禁、证据或反馈的业务判断；这类确定性操作由 Python Runtime 承载。

如果一个设计会让 AgenticOps 变成新的事实源、绕过人工门禁、弱化专业审查，或把阶段性实现当成长期架构，应先停止并重新审视目标。

## 5. 演进准绳

后续设计、优化和计划必须按以下准绳判断。

### 服务明确故事线

新增能力必须服务公司员工指导员故事或研发员工作故事。

- 公司员工指导员故事关注研发员创建、标准资产治理、授权、校对、发布、诊断、反馈、回滚和兼容性。
- 研发员工作故事关注初始化、任务接管、恢复、受控执行、证据和任务审计。

AgenticOps 研发员是产品主角；底层 AIAgent 是推理执行者，Python Runtime 是受控操作层，Shell Bootstrap 是安装入口，它们不各自形成独立产品身份。

两类故事都是项目质量合同。故事文档和机器注册表保存在仓库，声明保护行为、影响路径、固定验收和证据要求；Jira 只管理变更计划、进度、确认和验收记录。代码变更命中故事后，worktree / staged 阶段只输出候选预警并完成同一内容指纹的固定验收，不在代码事实形成前请求确认。功能、修复和任务分支统一停在 PR 当前 Head 审查，其它允许分支统一停在本地 commit 推送前审查；公司员工指导员逐项审查确认事项、变更点和风险。原任务级授权不能隐式覆盖故事修订，内部 `impact_id` 不能替代可查阅的 commit 或 PR 事实。

### 尊重事实源边界

Jira 是任务、需求、负责人、迭代、状态、评论和任务证据的事实源。Git 仓库是代码、测试、提交和分支的事实源。GitHub 拉取请求与 CI 是代码审查、CI、审查评论和合入记录的事实源。

AgenticOps 可以生成执行记录、诊断包和反馈分析，但不能用这些本地资料替代既有事实源。

### 优先沉淀标准资产

当问题重复出现时，优先判断它应该沉淀到哪类标准资产：

- AI 员工手册：协作方式、停止条件和证据要求。
- 操作契约：输入、输出、失败码、副作用和人工动作。
- 工作流配置：项目差异、字段映射、状态映射、仓库映射和审查节点。
- 策略门禁：高风险动作、阻断规则和人工确认。
- 运行手册：标准异常的排查、修复、升级和回写路径。
- 模板：Jira 评论、补卡说明、证据、阻塞说明和审计记录。
- Skill：组织标准流程、调用原子操作、解释结果并识别能力缺口。
- Python Runtime 原子操作：边界清晰、输入输出稳定、可验证、可审计的成熟交互逻辑。

问题应优先通过标准资产、Skill 或 Python Runtime 自助处理、阻断或转人工。只有确定性逻辑已经稳定且当前 Runtime 无法安全覆盖时，才评估新的实现载体。

### 保持运行与安装边界

AgenticOps 当前目标运行形态为：

```text
Skill + Python Runtime + Shell Bootstrap + Rule
```

- Skill 负责选择标准流程、组织操作和在能力不足时触发 AI 判断或人工确认；每个 Skill 只属于一个工作面。
- Python Runtime 负责结构化数据、本地状态、外部系统适配、门禁、证据、恢复和反馈；maintainer/developer Runtime 使用不同包和入口，不得互相导入。
- Shell Bootstrap 只负责安装、更新、回滚、Python 环境准备、统一启动，以及把可选安装授权输入转交 Python Runtime；不实现身份或凭证业务逻辑。
- Rule 负责事实源、权限、语言、分支、授权和停止条件。
- Python 源码和标准资产随稳定 `main` 更新后直接生效，不构建 AgenticOps 自有平台二进制。
- Go 历史实现已退出现役结构，不维护 Go/Python 双轨，也不恢复 `agentic-cli` 兼容入口。旧版本只由版本分支、Tag 和 Git 历史保留；已提取的契约、安全门禁、失败码、fixture 和验收行为必须由 Python Runtime、标准资产和固定验收继续保护。

### 保留人工门禁

任何高风险动作都必须经过策略门禁和人工确认，包括真实 Jira 写操作、推送、创建拉取请求、重新提交修复、合并、发布、范围变更和线上风险相关动作。唯一例外是 maintainer 快速 Hotfix：显式执行 `maintainer/scripts/hotfix.sh <KEY>` 本身即为动作授权，不再追加确认；脚本自行切换和同步 `develop`，该例外只允许把本地已提交的 `develop` 以 Jira key Merge commit 原子直合到 `main`，不得扩大为普通直推、强推、Jira 写入或其它发布动作。

AgenticOps 可以准备计划、整理证据、分类审查意见和输出建议，但不能在没有明确授权和审计记录的情况下执行高风险副作用。

### 先反馈，后固化

未成熟经验先进入执行记录、反馈分析和改进建议。只有重复出现、边界清晰、输入输出稳定、失败码明确、风险可控，并经过人工确认的经验，才可以固化为工作流配置、策略、运行手册、模板或原子化操作。

规范演进必须遵循：

```text
观察
-> 改进建议
-> 人工确认
-> 合入标准资产
-> 发布同步
-> 效果检查
```

业务任务中发现自动化不足、人工干预过多或输出质量不高时，应先由公司员工指导员校正确保业务任务正确完成；任务结束后生成脱敏改进方案。人工确认后，离开业务项目的 `developer` 工作面，切换到独立 AgenticOps worktree 的 `maintainer` 工作面，完成改进并创建 `develop` PR，不要求指导员重新描述问题。

AgenticOps 源头维护与业务项目执行必须使用不同目录、命令、Python 包、授权、配置、状态和规则加载集合。业务任务不得加载 AgenticOps 设计红线和源头发布规则；AgenticOps 改进 worktree 也不得继承业务项目的分支、提交和验证规则。发现跨面加载或调用时必须停止，不允许 AI 临场放行。

任何自动修改公司规范、默认策略或工作流配置的设计，都必须先请求用户决策。

## 6. 使用方式

做以下工作前，必须先读取本文：

- 新增或调整设计。
- 制定或重排实施计划。
- 优化流程、门禁、策略、标准资产或文档结构。
- 调整架构、事实源、角色责任、自动化程度或发布边界。

普通小修、测试、构建和不影响方向的局部文档措辞调整，不需要因为本文额外增加流程负担。
