# AgenticOps Skill 与 Shell 驱动项目全景

> **状态：** 新方向总体设计草案，等待研发工程师审阅确认。  
> **参考基线：** 《AgenticOps 项目全景》、项目目标、Tapdata workflow profile、AO 试验工作流和源码发布规则。  
> **适用范围：** 本文定义 AgenticOps 从 Go CLI 运行时迁移到 Skill、Shell、Rule 和本地任务文件驱动后的目标形态，以及按可验证交付目标划分的推进阶段。  
> **实现状态说明：** 当前仓库仍包含 Go CLI、四平台二进制和相关发布资产。本文描述目标设计，不把尚未完成的迁移写成当前能力。

## 1. 一句话认识新方向

AgenticOps 是把研发任务标准沉淀为 **Skill、Shell、Rule、模板和项目映射** 的 AI 执行协作体系：AIAgent 优先调用已经固化的标准操作，在项目工作空间用本地文件维护细粒度进展，通过 Jira Description、Comment 和工作流状态向团队汇报，并把使用中发现的问题反馈为可审查、可发布、可验证的 AgenticOps 改进。

最核心的判断标准是：

> 研发工程师能否安装 `main` 上的 AgenticOps，在 Tapdata 真实任务中按标准完成工作；流程不合理时能否先由人工安全校正，再通过 AO 工作项和受保护的发布流程把修复交付给下一次使用。

## 2. 为什么调整实现方向

AgenticOps 已经验证了 Jira 接管、任务证据、PR 事实、恢复和反馈等控制概念，但当前 Go CLI 把大量仍在演进的流程判断固化成命令、handler、契约、测试和四平台二进制。每次流程变化都需要本地编译、重新生成平台产物、更新校验和并执行完整二进制发布，反馈到可用版本的周期偏长。

当前阶段更需要快速验证员工执行标准，而不是优先稳定一个编译型运行时。因此目标实现改为：

- 用标准流程定义阶段、输入、输出、门禁和推进规则。
- 用 Skill 组织 AIAgent 如何选择和调用标准操作。
- 用 Shell 固化确定性、可重复、可测试的本地与外部操作。
- 用 Rule 约束事实源、语言、分支、授权、人工门禁和停止条件。
- 用本地任务文件保存细粒度进展、恢复点和待同步材料。
- 用 Jira 保存团队共享的任务契约、过程汇报、迭代状态和审计结论。
- 只有 Skill 和 Shell 都无法稳定覆盖的语义判断，才交给 AI 结合上下文执行。

Go 从目标运行时中移除。未来如果某组 Shell 操作已经长期稳定，并且出现明确的跨平台、安全性、性能或维护收益，再以独立设计重新评估是否迁移到 Go；不把“以后可能重写”作为当前交付前提。

## 3. 已确认的产品与治理决策

### 3.1 使用场景

- 日常研发以 Tapdata Jira 任务和 Tapdata 代码仓库为主。
- AO 的 `Agentic 缺陷` 工作类型、专用字段和工作流继续保留，用于 AgenticOps 自身流程试验、反馈修复和受控验收。
- AO 试验结果不能直接替代 Tapdata 真实研发任务验收。

### 3.2 安装与更新

- AgenticOps 安装到 `~/.agentic-ops`，该目录是跟踪稳定 `main` 的 managed clone。
- 安装后主要消费 Skill、Shell、Rule、模板、标准流程和项目映射，不要求本机安装或编译 Go。
- 项目 AI 工作空间保存具体项目配置和任务运行文件；具体任务数据不得写入 `~/.agentic-ops`。

### 3.3 分支与发布

- `main` 是稳定安装来源，继续禁止直接提交和直接推送。
- 日常 AgenticOps 改进分支通过 PR 合入 `develop`。
- 稳定交付通过受控的 `develop -> main` 发布 PR 完成，不允许普通任务 PR 直接进入受保护的 `main`。
- Hotfix 仍从最新 `main` 建立专用分支，并通过 PR 合入 `main`；不得用“标准资产改动较快”为理由绕过保护分支。

### 3.4 操作固化优先级

执行一个任务动作时，按以下顺序选择能力：

```text
标准流程已经定义的阶段与目标
-> 已固化 Skill
-> 已固化 Shell 操作
-> 项目 Rule、模板和 Jira 映射
-> AI 基于当前事实执行尚未固化的判断
-> 无法安全判断时阻断并请求人工处理
```

AI 判断不是默认捷径。可确定、重复出现、输入输出稳定的动作应优先固化为 Skill 或 Shell；尚未稳定的经验先记录为反馈，不直接升级为全局默认流程。

## 4. 项目定位、目标与非目标

### 4.1 定位

AgenticOps 位于 AIAgent 与现有研发事实源之间：

```text
研发工程师与 AIAgent
        │
        ▼
标准流程 + Skill + Rule + Shell + 模板
        │
        ├── 本地任务状态：细粒度进展、恢复点、待同步材料
        │
        └── 项目映射：Jira 阶段、字段、评论、仓库和审查节点
        │
        ▼
Jira / Git / GitHub / CI
```

AgenticOps 不替代 Jira、Git、GitHub、CI 或专业审查角色。它负责让 AIAgent 按确定的员工执行标准工作，并在标准能力不足时留下可定位、可校正、可回馈的缺口。

### 4.2 当前目标

先在 Tapdata 跑通一条无需 Go 运行时的真实研发任务闭环：

```text
从 main 安装 AgenticOps
-> 初始化 Tapdata 项目 AI 工作空间
-> 读取并检查真实 Jira 任务
-> 初始化本地任务目录和运行编号
-> 分析任务并汇报 Jira
-> 形成计划、人工确认并更新稳定任务契约
-> 实现、验证、提交和创建 develop PR
-> 汇报 Jira 进度与完成证据
-> 从本地文件和外部事实恢复中断任务
-> 发现流程问题并形成 AgenticOps 改进反馈
```

### 4.3 非目标

- 不让本地 `progress.yaml` 成为团队任务状态的替代事实源。
- 不让 Shell 自行发明业务规则、Jira 字段或状态映射。
- 不要求每个本地细粒度阶段都创建一个 Jira 状态。
- 不把 AO 的专用 Agentic 工作流强加给 Tapdata 日常研发任务。
- 不因为移除 Go 而弱化 Jira 权限、GitHub 分支保护、人工确认和专业审查。
- 不要求流程首次出现时立即固化；不稳定判断允许由 AI 执行并形成反馈。
- 不引入 Web 控制台、后台常驻服务或新的任务管理事实源。

## 5. 分层架构

### 5.1 标准层

标准层描述一个研发任务应该如何推进，而不绑定具体命令实现。每个标准流程至少定义：

- 稳定的 `process_id` 和适用任务分类。
- 入口、执行、等待、阻塞和完成阶段。
- 每个阶段的必要输入、标准操作和完成条件。
- 应生成的本地产物和应汇报的外部事实。
- 人工门禁、专业审查、停止条件、重试和重做起点。
- 可映射到 Jira 的粗粒度业务阶段。

标准层是 Skill、Shell、项目映射和 AI 判断共同遵守的上层契约。

### 5.2 Skill 层

Skill 负责把标准流程转化为 AIAgent 可执行的工作指导：

- 识别任务类型和当前阶段。
- 读取必要的 Rule、项目资产、模板和映射。
- 选择并调用已有 Shell 操作。
- 对需要语义理解的分析、计划和风险判断给出步骤与输出要求。
- 在信息不足、授权失效、外部写入不确定或风险扩大时停止。
- 把未被现有能力覆盖的问题记录为反馈，而不是静默绕过标准。

一个 Skill 可以编排多个原子 Shell 操作，但不能把外部写入结果只存在于对话上下文。

### 5.3 Shell 操作层

Shell 固化输入输出稳定、能够独立验证的操作，包括：

- 安装、更新、工作空间初始化和环境检查。
- 创建任务目录、生成运行编号、读取和更新本地状态。
- 追加只增事件、校验报告章节、生成 Jira 汇报材料。
- 读取 Jira、Git、GitHub 和 CI 事实。
- 按项目映射执行确定的 Jira Comment、Description 章节合并和状态转换。
- 在外部写入后回读，识别已完成、未完成或结果不确定。
- 创建 Git worktree、执行固定验证、准备提交和 PR 材料。
- 生成脱敏诊断包和 AgenticOps 改进反馈。

Shell 必须遵守以下边界：

- Shell 可以执行标准流程已经确定的业务操作，但不得在脚本内部猜测业务规则。
- 项目差异来自可审查的映射或 Rule，不能散落在通用脚本的条件分支中。
- 外部写入前必须显示目标和副作用；需要人工确认的动作不能静默执行。
- 外部写入结果不明确时必须先回读，不能盲目重试。
- 输出、失败码和退出码必须稳定，便于 Skill 和自动化测试消费。
- 不通过命令行、日志、事件或诊断包泄露 token、private key 和原始敏感内容。

### 5.4 Rule 与模板层

Rule 保存不能由当前任务临场改变的约束：

- 规则优先级和事实源边界。
- 中文交互和 Jira 人可见内容要求。
- Jira 任务归属、分支、worktree、提交、推送和 PR 规则。
- 人工门禁、专业审查和停止条件。
- Tapdata 项目差异与 AO 试验边界。

模板负责生成 Jira 分析、计划、决策、阻塞、验证和完成汇报。模板可以快速演进，但必须保留稳定操作标记和必要证据字段，避免恢复时只能解析自由文本。

### 5.5 AI 判断层

AI 负责尚不能用固定规则安全表达的认知工作：

- 结合 Jira 和代码理解问题。
- 判断缺失信息是否能通过代码事实补全。
- 形成实现方案、修改范围、风险和验证方式。
- 处理需要专业取舍的审查意见和异常。
- 总结人工校正，提出应沉淀为 Skill、Shell、Rule、映射或模板的建议。

AI 不负责绕过现有操作，也不应手工重复已经由 Shell 固化的机械步骤。AI 判断形成的新经验必须先经过真实任务验证和人工审阅，才能成为默认标准资产。

## 6. 本地任务状态模型

### 6.1 目录结构

具体项目 AI 工作空间按 Jira 编号隔离任务资料：

```text
<project-ai-workspace>/.agentic-ops/
  tasks/
    TAP-123/
      task.yaml
      progress.yaml
      decisions.yaml
      journal.ndjson
      sync.yaml
      reports/
        analysis.md
        plan.md
        blocked.md
        verification.md
        review.md
        completion.md
      feedback/
        observation.md
      runs/
        <agentic_run_id>/
          summary.yaml
          evidence/
```

### 6.2 文件职责

| 文件 | 职责 | 约束 |
| --- | --- | --- |
| `task.yaml` | 保存任务编号、项目、仓库、分支、运行编号和稳定身份引用 | 不复制完整 Jira Description |
| `progress.yaml` | 保存本地细粒度阶段、已完成检查、下一步和阻塞原因 | 只能按标准状态迁移更新 |
| `decisions.yaml` | 保存人工确认、授权范围、计划版本和失效原因 | 必须能关联 Jira 评论或其它项目认可的事实 |
| `journal.ndjson` | 追加操作、结果、失败码和安全摘要 | 只追加，不改写历史，不保存敏感原文 |
| `sync.yaml` | 保存最近 Jira/GitHub 回读引用和待同步动作 | 不把待同步内容误报为已同步 |
| `reports/` | 保存准备汇报或已经汇报的中文材料 | 每份报告标记内容哈希和外部引用 |
| `feedback/` | 保存本次使用发现的流程缺口和人工校正 | 不自动修改全局标准资产 |

### 6.3 本地状态与外部事实冲突

恢复或推进前必须同时读取本地状态和外部事实：

1. 核对 Jira 任务、负责人、状态、最近决策和最近汇报引用。
2. 核对 Git 分支、工作区和提交事实。
3. 存在 PR 时核对 PR head、CI 和 Review。
4. 本地记录与外部事实一致时继续。
5. 本地只记录“待同步”但外部已完成时，回读并补记成功，不重复写入。
6. 本地声称已完成但外部不存在对应事实时，标记冲突并停止，不能自动覆盖任何一方。

本地文件是执行连续性和恢复入口；Jira、Git、GitHub 和 CI 仍分别拥有团队任务、代码、PR 和检查事实。

## 7. 标准研发任务流程

目标标准流程使用：

```yaml
task_type: development_task
process_id: skill_driven_development_v1
```

| 标准阶段 | 标准操作目标 | 主要本地产物 | Jira 汇报 | 推进门禁 |
| --- | --- | --- | --- | --- |
| `initialized` | 读取任务和项目事实，初始化运行目录 | `task.yaml`、首条 journal | 可选接管汇报 | 任务、负责人、项目和仓库可确认 |
| `analyzing` | 结合 Jira 与代码形成问题分析 | `analysis.md` | 分析或补卡 Comment | 影响范围和缺失事实已说明 |
| `planning` | 形成版本化计划、验证方式和风险 | `plan.md` | 计划 Comment | 计划内容完整 |
| `waiting_plan_confirmation` | 保存研发工程师决策和授权范围 | `decisions.yaml` | 决策 Comment；稳定契约合入 Description | 明确确认后才能实现 |
| `implementing` | 在已确认范围内修改代码并持续记录 | `progress.yaml`、Git 事实引用 | 只在关键检查点汇报 | 授权、范围和所有权持续有效 |
| `verifying` | 执行约定验证并说明未验证项 | `verification.md` | 验证 Comment | 验证结果足以进入审查 |
| `preparing_review` | 准备提交、推送和 PR 审查包 | `review.md` | PR 与证据 Comment | 分支、验证和授权检查通过 |
| `waiting_review` | 等待并处理 CI、Review 和专业结论 | 更新 `review.md` | 必要的修复或阻塞 Comment | 专业角色给出结论 |
| `completing` | 汇总变更、验证、风险和恢复说明 | `completion.md` | 完成 Comment；必要时更新 Description | 证据和审查完整 |
| `completed` | 回读外部完成事实并关闭本次运行 | `summary.yaml` | 映射完成状态 | Jira、GitHub 与本地记录一致 |
| `blocked` | 记录阻塞事实、已尝试动作和恢复条件 | `blocked.md` | 阻塞 Comment | 人工处理或满足恢复条件后重做指定阶段 |

本地阶段比 Jira 状态更细。多个本地阶段可以映射到同一个 Jira 状态，不能为了表达 AIAgent 内部进度而扩张 Tapdata 工作流。

## 8. Jira 协作与项目映射

### 8.1 Jira 内容职责

| Jira 载体 | 保存内容 | 更新方式 |
| --- | --- | --- |
| Description | 当前确认有效的目标、范围、非范围、验收标准、确认方案和验证契约 | 只合并已映射章节，保留其它人工内容 |
| Comment | 分析、计划、决策、阶段进展、阻塞、恢复、验证、PR 和完成证据 | 追加历史，不覆盖旧评论 |
| Custom field | 项目已经认可且 profile 明确映射的结构化结论 | 仅更新白名单字段 |
| Status | 团队共享的粗粒度业务阶段 | 只使用项目映射中的 transition |
| Worklog | 真实投入时间 | 不承载计划、决策或任务证据 |

每次 Jira 写入都应使用稳定操作标记或内容哈希。网络中断导致结果不确定时先回读 Comment、Description、字段或状态，再判断是否需要补写。

### 8.2 Tapdata 主流程映射

Tapdata 使用现有 `Story`、`Bug`、`Task`、迭代状态和仓库，不新增 Agentic 专用工作类型。目标映射原则是：

- `initialized` 映射到 Tapdata 待办类状态。
- `analyzing` 至 `verifying` 映射到进行中类状态。
- `preparing_review` 和 `waiting_review` 映射到项目已有的 PR/测试阶段；没有独立状态时保持进行中并通过 Comment 与 PR 汇报。
- `blocked` 映射到明确配置的阻塞状态；项目没有可用状态时保持当前状态并追加阻塞 Comment。
- `completed` 只在完成证据和项目验收条件满足后映射到完成类状态。

具体状态名、transition、Description 章节、字段和仓库选择必须来自 Tapdata 项目映射，Skill 和通用 Shell 不得硬编码。

### 8.3 AO 试验映射

AO 保留 `Agentic 缺陷`、专用运行字段、五个状态和受控 transition，用于：

- 记录 AgenticOps 在 Tapdata 使用中发现的问题。
- 试验新的本地阶段、Jira 汇报和恢复策略。
- 验证无人值守或高控制流程，但不自动推广到 Tapdata。
- 承载 AgenticOps 源头仓库的 Jira 绑定、分支、PR 和验收证据。

AO 试验能力只有在真实任务中重复成立、人工审查通过并形成兼容迁移方案后，才允许进入 Tapdata 默认标准资产。

## 9. 安装、反馈、修复与发布闭环

### 9.1 安装和更新

安装流程只要求 Git、Shell 和现有外部工具：

```text
从受保护 main 安装或更新 ~/.agentic-ops
-> 校验仓库来源和目标提交
-> 安装或链接 Skill、Rule 和 Shell 入口
-> 保留用户本地配置
-> 输出安装引用和回滚点
```

更新失败时回到上一已验证提交。任务本地状态位于项目 AI 工作空间，更新 `~/.agentic-ops` 不得覆盖具体任务资料。

### 9.2 使用中反馈

Tapdata 任务中发现 AgenticOps 不合理时：

```text
记录实际行为和预期行为
-> 研发工程师人工校正当前任务
-> 将校正结果写入任务 feedback/observation.md
-> 创建或关联 AO Agentic 缺陷
-> 在 AgenticOps worktree 中修改 Skill / Shell / Rule / 映射 / 模板
-> 使用原场景和回归场景验证
-> PR 合入 develop
-> 通过受控发布 PR 进入 main
-> 使用者更新 ~/.agentic-ops
-> 回到原场景检查问题是否消失
```

人工校正只解决当前任务，不自动成为全局标准。反馈至少包含：

- 实际发生了什么。
- 预期标准是什么。
- 当前任务如何安全校正。
- 建议修改哪个标准资产。
- 影响范围和兼容风险。
- 可复现输入和验收证据。

### 9.3 发布治理

Go 移除后，发布不再构建四平台二进制，但仍保留以下治理：

- `develop` 是日常集成分支。
- `main` 是稳定安装分支。
- `main` 只能通过受控 PR 合入，不允许直接提交或推送。
- 发布必须固定待发布 HEAD，执行标准资产、Shell、安装和真实场景回归。
- 发布前展示影响范围和人工确认；合并后回读 `origin/main` 包含固定 HEAD。
- 安装端可以定位当前提交、更新到新稳定提交并回滚到上一稳定提交。
- Hotfix 仍需要 Jira 绑定、受控 PR、验证和回同步决策。

版本是否继续使用 Git tag，应在移除二进制发布时单独确认；不能默认沿用“编译版本线”的语义，也不能因为取消二进制而取消发布审计。

## 10. Go 移除与迁移边界

目标状态中不保留 Go 源码、Go module、四平台二进制、二进制 checksum、Go 构建测试或依赖 Go CLI 的安装步骤。

迁移必须按用户可验证能力逐项替换，不能先删除 Go 再声明流程以后补齐：

1. 盘点当前 Go 命令背后的用户故事和保护行为。
2. 将仍需要的能力归入 Skill、Shell、Rule、模板或项目映射。
3. 为替代操作建立固定输入、输出、退出码、失败码和测试 fixture。
4. 用 Tapdata 真实任务或受控外部事实验证替代能力。
5. 证明安装、任务执行、恢复、反馈和发布不再调用 Go 后，删除对应 Go 实现和产物。
6. 更新项目目标、规则、故事线、架构、安装、发布和验证文档，消除双重事实。

迁移期间允许短期同时存在旧 CLI 和新入口，但新流程不得继续增加 Go 能力。每个旧入口都必须有明确的替代、废弃或确认删除结论，不能无限期保留兼容层。

## 11. 以可验证交付目标划分的推进阶段

推进阶段以“用户能够完成什么、如何证明”划分，而不是以代码目录、语言迁移或文档批次划分。每个阶段必须形成可独立演示的交付，上一阶段未验收不得用后续实现掩盖缺口。

| 阶段 | 可验证交付目标 | 核心验收证据 |
| --- | --- | --- |
| 一 | 无 Go 完成本地标准任务演练 | 隔离安装、状态迁移、中断恢复和 Shell 回归通过 |
| 二 | Tapdata 真实任务完成分析与计划确认 | Jira Comment、Description、状态映射和本地同步引用可回读 |
| 三 | Tapdata 真实任务交付到 PR 审查 | 任务分支、验证、`develop` PR、Jira 证据和审查包一致 |
| 四 | 中断、失败和不确定写入能够恢复 | 不重复外部副作用，失败码、回读和 journal 能解释恢复结果 |
| 五 | 使用中问题完成 AO 反馈、修复和稳定发布 | AO 工作项、修复 PR、发布 PR、`main` 安装引用和复验闭环可追溯 |
| 六 | 无 Go 版本达到稳定交付基线 | 多环境安装与真实任务验收通过，Go 运行资产已移除，发布治理仍成立 |

### 阶段一：无 Go 完成本地标准任务演练

**可交付结果：** 在一台没有 Go 环境的开发机上，从 `main` 安装 AgenticOps；AIAgent 能初始化 Tapdata 工作空间和一个示例任务目录，按标准阶段生成分析、计划、决策、验证、完成和反馈文件，并在中断后从本地状态恢复。

**验收场景：**

1. 使用隔离安装目录模拟首次安装和再次更新。
2. 初始化 Tapdata 项目工作空间，不连接真实 Jira 写接口。
3. 使用固定 fixture 创建 `TAP-DEMO-1` 任务。
4. 推进到等待计划确认，中断会话后重新读取并恢复。
5. 完成后生成任务摘要和一条流程反馈。

**验收证据：**

- 环境中不存在 `go` 命令仍能完成演练。
- 本地目录结构、状态迁移、journal 追加和报告章节校验通过。
- 重复执行初始化和汇报生成不破坏已有数据。
- Shell 自动化测试、安装测试和 `git diff --check` 通过。

**进入下一阶段的门禁：** 本地任务进展不依赖聊天上下文，不调用 Go，不把 fixture 结果描述为真实 Jira 成功。

### 阶段二：Tapdata 真实任务完成分析与计划确认闭环

**可交付结果：** 研发工程师能选择一张真实 Tapdata Jira 任务，AIAgent 读取 Jira 与代码事实，在本地维护进展，把分析和计划作为中文 Comment 汇报，把人工确认后的稳定契约合入 Description 映射章节，并正确映射 Jira 当前状态。

**验收场景：**

1. 选择一张允许试验的真实 Tapdata 任务。
2. 回读负责人、任务类型、当前状态、Description、Comment 和目标仓库映射。
3. 完成代码分析；信息不足时先形成补卡 Comment 并停止。
4. 信息足够时形成版本化计划并等待研发工程师确认。
5. 写入确认 Comment 和稳定 Description 章节，再回读验证内容。

**验收证据：**

- Jira Comment 使用中文且不重复写入。
- Description 章节级更新保留人工维护的其它内容。
- 本地 `sync.yaml` 能关联 Jira 回读引用和内容哈希。
- Tapdata 状态通过项目映射解释，不使用 AO 专用状态。
- 未确认计划时不能进入实现阶段。

**进入下一阶段的门禁：** 真实 Jira 与本地进展一致，外部写入结果不明确时能够停止和回读，研发工程师确认该流程可用于实际开发。

### 阶段三：Tapdata 真实任务交付到 PR 审查

**可交付结果：** 在计划确认和有效授权范围内，AIAgent 能用 Skill 与 Shell 完成代码实现、验证、提交、任务分支推送、创建目标为 `develop` 的 PR，并把验证与 PR 证据回写 Jira，最后停在专业审查节点。

**验收场景：**

1. 从阶段二已经确认计划的任务继续执行。
2. 使用项目规则要求的 worktree 和任务分支。
3. 修改代码并执行任务约定验证。
4. 检查范围、分支、提交信息和敏感内容。
5. 推送任务分支并创建或更新 `develop` PR。
6. 回读 PR head、CI、Review 和 Jira 证据。

**验收证据：**

- Git 差异只包含任务范围。
- 验证命令和结果记录完整，未执行项明确说明。
- 未直接推送 `develop` 或 `main`，未自动合并 PR。
- PR head、Jira 评论和本地审查包相互关联。
- 授权失效、范围变化或验证受阻时停止并形成阻塞材料。

**进入下一阶段的门禁：** 研发工程师和代码审查人能只依靠 Jira、PR 与本地审查包判断任务当前结果和风险。

### 阶段四：中断、失败和不确定写入能够恢复

**可交付结果：** 对阶段二和阶段三的任务人为制造中断、网络失败或外部写入结果不确定后，新 AIAgent 能从本地状态与外部事实恢复，不重复 Jira 评论、不重复推送、不丢失人工决策，也不会把未完成任务误报为完成。

**验收场景：**

- Jira Comment 请求返回不确定结果，但实际远端已写入。
- 本地报告已生成但 Jira 尚未写入。
- 任务分支已推送但 Jira 证据失败。
- PR 已创建但本地完成事件未写入。
- Jira 负责人、任务范围或目标分支发生变化。

**验收证据：**

- 每种场景都有稳定失败码、`retry_safe` 结论和人工动作。
- 恢复先回读 Jira/Git/GitHub，再决定补记、重试或阻断。
- 只追加 journal 能解释恢复前后的事实变化。
- 重复执行恢复流程不会产生重复外部副作用。

**进入下一阶段的门禁：** 所有高风险不确定场景都能保守停止或幂等恢复，不依赖旧聊天历史。

### 阶段五：使用中问题能够完成修复发布闭环

**可交付结果：** Tapdata 任务中发现一个真实 AgenticOps 流程问题后，研发工程师能先校正当前任务，再创建 AO `Agentic 缺陷`，通过独立 worktree 修改标准资产，PR 合入 `develop`，经受控发布 PR 进入 `main`；安装端更新后能够复验原问题已经解决。

**验收场景：**

1. 在 Tapdata 任务中记录一个可复现流程缺口。
2. 保存人工校正方法、影响范围和期望标准。
3. 创建 AO 工作项并绑定 AgenticOps 分支、验证和 PR。
4. 修复 Skill、Shell、Rule、模板或映射。
5. 用原失败场景和至少一个回归场景验证。
6. 合入 `develop`，再通过受保护的发布 PR 进入 `main`。
7. 更新 `~/.agentic-ops`，回到原场景复验。

**验收证据：**

- 普通任务 PR 没有直接进入 `main`。
- AO 工作项、AgenticOps PR、发布 PR、稳定 `main` 提交和安装引用可相互追溯。
- 当前任务的人工校正与全局标准修改明确区分。
- 更新失败可以恢复到上一稳定提交。
- 修复前后的行为差异能够用相同输入复现。

**进入下一阶段的门禁：** 从问题发现到稳定安装生效的周期可度量，且不需要编译或发布 Go 二进制。

### 阶段六：无 Go 版本达到稳定交付基线

**可交付结果：** 新研发工程师在受支持的 macOS/Linux 环境中只依赖 Git、Shell 和项目声明的外部工具，即可从 `main` 安装 AgenticOps，并完成至少一条 Tapdata 真实任务主链路；仓库不再包含运行所需的 Go 源码和平台二进制，AO 试验能力继续可用。

**验收场景：**

- 在所有受支持环境执行干净安装、更新和回滚。
- 执行阶段一的本地演练。
- 执行阶段二至三的 Tapdata 真实任务代表流程。
- 执行阶段四的关键恢复场景。
- 执行阶段五的反馈修复发布演示。
- 使用 AO `Agentic 缺陷` 验证 AgenticOps 自身改进流程。

**验收证据：**

- 安装和任务主链路不检测、不下载、不编译 Go。
- Go module、Go CLI 源码、四平台二进制和相关构建发布步骤已经移除。
- Skill、Shell、Rule、模板和项目映射具有固定测试入口。
- Tapdata 与 AO 的真实验收报告均可追溯。
- `main` 保护、`develop -> main` 发布 PR、Hotfix 和回滚规则仍然成立。

**阶段完成标准：** 研发工程师能够把 AgenticOps 当作可持续使用和改进的研发流程资产，而不是需要维护编译型运行时的工具项目。

## 12. 质量与验证体系

目标验证体系按用户故事分层：

| 验证层 | 证明内容 |
| --- | --- |
| 静态校验 | Skill 元数据、标准流程、Rule、映射和模板结构有效，Shell 语法与格式正确 |
| 原子操作测试 | Shell 输入、输出、退出码、失败码、幂等和敏感信息处理符合契约 |
| Fixture 流程 | 不写真实外部系统即可回归本地阶段、报告、恢复和冲突处理 |
| 隔离安装测试 | 在没有 Go 的环境验证安装、更新、配置保留和回滚 |
| Tapdata 真实验收 | 证明主流程适配日常研发 Jira、仓库、PR 和审查事实 |
| AO 试验验收 | 证明 AgenticOps 自身反馈、改进和高控制流程可运行 |
| 发布验收 | 证明固定 HEAD 经 PR 进入 `main`，安装端取得同一稳定提交 |

自动化测试不能替代真实 Jira 和 GitHub 验收；真实验收也不能替代可重复的 fixture 回归。每个交付阶段必须同时说明已自动验证的行为和仍需人工判断的事实。

## 13. 成功标准

AgenticOps 新方向是否成功，以以下结果判断：

- 从问题反馈到标准修复进入稳定安装版本的周期显著缩短。
- 大多数确定性操作通过 Skill 和 Shell 复用，不由 AI 每次临场重做。
- AI 只在需要语义理解和专业取舍时介入，并能在能力不足时主动反馈。
- Tapdata 研发工程师能完成真实任务闭环，不需要理解 AgenticOps 源码或 Go 构建。
- 本地进展可恢复，同时不取代 Jira、Git、GitHub 和 CI 的事实源地位。
- Jira Description、Comment 和状态各自承担清晰职责，映射缺失时能够阻断。
- 任何写入 `main` 的变更都经过受保护的发布路径。
- AO 试验能够验证新流程，但不会直接改变 Tapdata 默认流程。
- 使用中发现的问题可以人工校正、形成 AO 工作项、修复、发布、更新并复验。
- Go 移除后，安全门禁、证据、恢复和发布治理没有退化。

## 14. 与现有资料的关系

本文确认后，应以单独实施计划同步处理以下现有事实：

- 《项目目标》中 Go CLI 和 Shell 业务边界的旧表述。
- 《当前设计》《CLI 运行时》和《项目全景》中以 Go 运行时为中心的架构。
- 项目维护者与研发工程师故事中依赖 `agentic-cli` 的触发和验收方式。
- 操作契约的执行载体、安装资源目录、版本号、更新回滚和发布脚本。
- AGENTS.md 中运行时方向、固定验证和发布要求。
- Go 源码、平台二进制、checksums 和相关测试资产。

在迁移完成前，旧文档描述当前已实现基线，本文描述目标方向。发生冲突时不得自行拼接两套运行方式；应根据当前交付阶段明确选择已经验收的新入口或仍保留的旧入口。
