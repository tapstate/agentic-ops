## 4. 已证实问题

### 4.1 自定义安装目录污染真实 shell profile

**证据：** 使用自定义 `AGENTIC_OPS_HOME` 隔离安装时，安装脚本仍把临时 `bin` 路径写入真实用户 shell profile。

**根因方向：** profile 路径按真实用户 Home 解析，而 PATH 内容按自定义安装目录生成；现有测试只覆盖临时 Home 与默认安装目录组合。

**恢复：** 已精确删除本次新增的临时 PATH 行，并确认不存在残留。

### 4.2 运行时使用固定时间

**证据：** 接管输出、运行编号、Jira 接管时间、心跳和本地事件都使用 `2026-07-21T10:30:12Z`，与真实执行日期不一致；源码中的 `fixedNow()` 直接返回该固定值。

**影响：** 运行编号可能重复，审计时间不可信，心跳无法反映代理存活状态，基于时间的反馈和恢复判断可能错误。

### 4.3 接管字段与状态转换未原子执行

**证据：** `takeover-task` 更新所有权字段后返回 `ok:true`，但实现没有调用 Jira transition，AO-2 仍处于“待接管”。AO 流程设计要求转换 `2` 与 Agentic 字段在同一 Jira 转换请求中原子完成。

**影响：** 可能出现字段已绑定但状态仍允许接管的部分成功，并发代理无法依靠 Jira 转换获得唯一锁；CLI 成功结论与 Jira 事实冲突。

**恢复：** 回读确认部分写入后没有重复接管，只补执行已授权的转换 `2`，再回读为“执行中”。该恢复无法恢复原子性，因此必须保留为缺陷证据。

### 4.4 首条不完整门禁事件破坏运行上下文

**证据：** 同一次真实接管先写入一条缺少 `task_class` 和 `process_id` 的成功门禁事件，再写完整接管事件。`RunContextReader` 选择第一条成功 `takeover_task` 作为锚点，导致后续带正确 `--run-id` 的 `add-task-comment` 返回 `local_state_mismatch`。

**影响：** 真实接管成功后，计划、决策、证据和 PR 证据等需要运行上下文的后续操作会被错误阻断；若省略运行编号绕过，会破坏任务审计关联。

**恢复：** 不省略运行编号、不篡改事件文件、不重复失败命令；在所有权、状态和运行编号回读一致后，按 v0.3 相同 ADF 格式执行单次评论恢复写入，并记录本地审计缺口。

### 4.5 默认证据不符合中文与验收要求

**证据：** v0.3 `write-evidence` 使用的 `development-completed.md` 标题和字段说明为英文，只包含工作空间、运行编号、任务分类、流程、阶段、仓库和固定 `status`，没有变更内容、验证命令、结果、风险或恢复说明。

**影响：** 直接写入会违反 AO 项目 Jira 人可见内容使用中文的规则，也不能单独证明任务验收结果；运行上下文缺陷还会在生成本地文件前阻断命令。

**恢复：** 在隔离工作空间生成中文、脱敏的证据主体，包含当时已观察到的变更、验证、五个问题和审计缺口；经独立人工确认后再单次写入 Jira，不声称 v0.3 已返回 `audit_submitted=true`。后续 PR 阶段新增的两个问题分别由 PR 恢复证据和本报告补充记录。

### 4.6 GitHub CI 客户端依赖不兼容字段

**证据：** v0.3 `check-ci-status` 调用当前 GitHub CLI 2.97.0 时，请求 `gh pr checks` 不提供的 `conclusion` 和 `detailsUrl` JSON 字段，命令返回 `github_ci_read_failed`，从而阻断 `write-pr-evidence` 正常路径。

**影响：** 即使 PR 可读取，AgenticCLI 也不能稳定形成 PR、CI 和 Review 证据；GitHub CLI 版本变化会直接泄漏为运行时失败。

**恢复：** 使用稳定的 GitHub REST API 回读固定 PR head。PR #3 的 head `70fc0cf6df2d67f323f9e815cd0039c6a0aa8844` 没有 check runs、commit statuses、Review 或评论，因此 CI 结论是 `not_configured`，不是 `passed`。恢复证据经确认后写入 Jira 评论 `46517`。

### 4.7 人工恢复事实没有进入反馈事件

**证据：** 本次完成证据和 PR 证据都经过人工恢复、外部回读和校验和审计，但 v0.3 没有记录结构化恢复事件。`feedback analyze` 和 `feedback propose` 只读取到两条普通事件，均返回空模式和空 proposal。

**影响：** 已成功恢复的真实缺陷不会进入持续改进输入，分析结果可能错误地表现为“没有问题”；恢复引用也无法通过运行编号进行统一聚合和去重。

**恢复：** 当前报告保留 Jira 评论 ID、证据 SHA-256、原始失败码和回读结论，不篡改既有事件。v0.4 增加本地 `feedback record-recovery` 原子操作后，再由分析和建议消费结构化恢复记录。

## 8. 结论和下一步

v0.3 已证明 AO profile、真实 Jira 读取、所有权字段写入和人工门禁可以连接真实流程，但隔离安装、真实时间、原子接管、运行上下文、中文证据、GitHub CI 读取和恢复反馈尚不满足可靠日常使用要求。不能仅依据 CLI `ok:true` 判断外部写入完成，也不能把“未配置 CI”解释为“CI 已通过”，必须回读 Jira 和 GitHub 权威事实。
