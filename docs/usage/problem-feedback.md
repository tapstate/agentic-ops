# 研发工位问题反馈流程

本文统一说明所有项目研发工位共用的问题反馈流程：研发在使用工位接管和执行任务时，通过共享 [ao-feedback](../../skills/shared/ao-feedback/SKILL.md) 快速总结问题、整理必要复现资料并提交 AO Jira；维护者从 AO 项目问题列表统一受理、分析和处理。`ao-feedback` 是研发上报入口，操作范围为提交、补充和查询，不承担维护者的分诊、修复或任务流转职责。使用时核验绑定安装是否包含该技能并已刷新接线，不能以源码文件存在证明旧安装或任一 Agent 会话已支持。交付进度和实际验收以 [AO-119](https://tapdata.atlassian.net/browse/AO-119) 为准。

产品方向和事实源以[项目目标](../strategy/project-goals.md)为准，协作能力归属及可见范围以[工程架构](../architecture/agenticops-v1-architecture.md)和 [Skill 维护规范](../skill-maintenance.md)为准。本文不改变任务授权、工位状态、升级或发布规则。

## 1. 使用者入口与最少操作

研发在发生问题的工位 Agent 会话中直接提出反馈，例如“用 ao-feedback 把刚才接管失败的问题提交到 AO，附上必要的复现资料”。Agent 复用上下文完成问题总结、复现资料整理、脱敏、查重和建单，返回一个 AO 编号与已记录摘要。正常路径只需这一句话，无需另填表单、查版本、导出日志或手抄 run。期望行为和影响已经明确时不重复询问；只有缺项会影响正确性、权限或归属时才集中补问。

目标入口是所有受管项目工位共用的共享 `ao-feedback` 技能，支持提交问题、补充已有反馈和查询处理情况，不以 TapData 或其它特定项目作为准入条件，也不要求使用者具有维护者角色。来源项目从工位绑定读取，用于定位和后续分类，反馈目的地始终是 AO。技能遵循[统一帮助合同](../skill-maintenance.md#技能调用与帮助)，不要求记忆子命令。工位启动失败、未绑定任务或尚未安装时，可以在能访问相关材料的独立 Agent 会话中整理反馈；不能为了反馈先修工位、接管任务或生成 run。技能缺失时，按现役文档和已有授权由 Agent 原生能力接力，不能声称该技能已安装。

| 用户表达 | 目标行为 |
|---|---|
| “用 ao-feedback 把刚才接管失败的问题提交到 AO” | 自动总结问题和整理必要复现资料，向 AO 创建或补充反馈；该请求覆盖本次必要 Jira 写入，不另加整包审批 |
| “先整理一下，暂时别提交” | 只在当前会话给出脱敏草稿 |
| “为什么失败，帮我排查” | 排障，不自动创建反馈或上传现场；确有产品问题时可建议反馈 |
| “查询 AO-123 的处理情况” | 回读状态、负责人、修复与交付证据、下一步，不自行改状态 |
| “把本次复测仍失败的结果补到 AO-123” | 在原任务补充本次版本、步骤和结果，继续跟进同一问题 |

反馈覆盖所有项目研发在使用工位接管和执行任务中遇到的问题，包括接管准入、工程准备、技能引导、流程检查、恢复、归档清理、项目适配及相关安装接线障碍。不能要求研发先确定是公共内核、项目配置、Agent 行为还是使用问题，归因不清也应将现象和资料提交 AO，由维护者统一分类。预期人工门禁与流程缺陷应区分，但是否属于缺陷不是提交的前置条件；所需决定确实缺失可以记录为使用障碍，错误拒绝、重复索取已有效的决定或提示不清也可以反馈。已确认的独立业务产品缺陷仍遵循业务项目规则，AO 记录关联及分流结果，不复制业务修复台账；这一后续分流不能用于拒绝接收尚未定位的工位问题。

## 2. 信息采集与现场保全

先读当前会话及已出现的失败结果，再按问题补必要材料。提交结果必须同时包含清晰的问题总结和必要复现资料，使维护者脱离原聊天也能理解问题，并据此尝试复现或继续定位。能从可信来源获得的信息由 Agent 提取；没有的信息标为未知，不为填满模板扫描整台机器、重跑昂贵测试或触发有副作用的复现。不可安全复现或偶发的问题仍可先提交，说明已观察到的发生过程、证据和未能复现的原因，由维护者继续定位。

| 信息 | 可信来源及采集边界 |
|---|---|
| 场景、实际与期望、影响和是否阻塞 | 当前会话、失败输出和使用者已有说明；推测与事实分开，只有无法判断的关键项才问用户 |
| 发生过程、必要命令、退出结果、已尝试处理 | 本次工具回执或用户描述；移除命令中的秘密，不把命令执行成功当作成果已验收 |
| 复现前置条件、触发输入与最短步骤 | 从真实发生过程提取，保留必要的非秘密配置、最小示例或命令片段及执行顺序，分别给出预期和实际结果；不把推测步骤写成已验证复现 |
| AgenticOps 版本与来源 | 绑定安装的版本、完整 SHA 和 dirty 情况；与维护源码候选版本分开，没有安装则明确缺失 |
| Agent、操作系统及相关工具版本 | 当前可核验会话和本机只读查询；仅采集与故障有关的版本，不读取全量环境变量 |
| 工位项目、业务任务、run、阶段和 operation | 优先使用绑定版本支持的只读入口及原操作回执；无任务可反馈，损坏或跨 epoch 时保留读取错误，不强行用新版解析旧状态 |
| 错误证据与既有成果 | 必要脱敏片段、相关事件或回执、已有档案中的相关摘要，以及可授权访问的 Jira、PR、CI 链接；只读所需部分，不上传整份现场 |

`station status --json` 是现有基本信息入口，见[工位源码与材料](station-materials.md#查看工位基本信息)。其结果包含本机绝对路径，不能原样上传。任务及操作材料的身份和读取边界见[工位合同](../architecture/single-task-station.md)；诊断读取失败本身也可作为证据，不影响已掌握现象的整理。活跃现场变化时注明观察时间与来源，不拼接不同 run 的材料冒充同一快照。

外部正文仅保留定位所需内容：路径使用 `<station>`、`<product-root>` 等占位，移除凭证、带鉴权参数的 URL、客户数据、个人目录和无关业务细节。业务 Jira/PR/CI 链接也需检查访问范围和敏感信息；原系统权限不会限制已复制到 AO 的正文，不能因能读取就认定能扩大共享。无法确认可共享时保留安全摘要，只暂停相关内容上传。自动脱敏不能证明材料绝无敏感信息，无法判断的部分不发送。

原始日志、完整会话、config、runtime 和 `.agenticops/` 不整包上传，也不建立新的“反馈包”或本地队列。反馈所需的最小证据应进入 Jira，避免原工位退出后只剩不可访问的本机路径；现场和正式档案仍按原合同保留，不为反馈冻结或复制整套工位。确需补充材料时由维护者提出具体范围和用途，不能要求用户重新整理已有信息。

问题摘要至少让维护者看清“哪个项目在做什么、在哪里遇到什么问题、造成什么影响”；复现资料按实际需要给出“必要环境和前置条件、触发输入、操作顺序、预期/实际结果、脱敏错误及相关证据”。来源业务任务、run 和 operation 可取得时自动附上，接管尚未成功时明确未生成，不要求研发补造。正文和必要片段以可阅读、可复制的形式直接进入 AO 问题，不只留下“见原聊天”或维护者无法访问的本机文件路径。

## 3. 查重与维护任务创建

反馈目标集中为 [tapdata.atlassian.net](https://tapdata.atlassian.net) 的 AO 项目。Agent 从当前连接核验站点与项目，不使用业务 Profile 的 project key，也不修改业务工位绑定。使用原生 Atlassian 能力；缺连接或权限按[必需 MCP 配置](mcp-setup.md)处理，不另造 Jira 客户端或收集 token。

优先在 AO 检索相关操作、症状与版本；能确认问题相同时补充已有任务，返回同一编号，不覆盖原描述、负责人或已有结论。只有标题相似不算重复；范围不同则创建独立任务并引用相关候选。已完成问题在所声称修复版本上复现时，补原任务并交维护者重新核验，不静默另建一张相同故障单。检索不可用时披露“查重未完成”，只要站点、建单权限、负责人和安全正文可核验，继续已授权提交，由维护者在 AO 列表统一去重，不增加用户审批。查重失败与此前写入结果未知必须区分，后者仍按第 5 节先核查原写入，不能借此重复建单。

一条反馈默认就是一个维护工作项，不另建“反馈单→分析单→修复单”链条。新反馈用 AO 当前可创建的任务类型受理，故障确认后由维护者按实际项目类型处理，不为本流程新增类型、必填自定义字段或工作流。仅有可独立交付的多个问题时才拆分，原反馈保留所有子项链接和最终结果。

建单时由 Agent 生成简短中文标题和正文。正文按上述采集结果整理问题总结与必要复现资料，保留来源项目、业务任务及接管/执行所处步骤，便于维护者从 AO 问题列表统一查找和处理；不要求另填来源项目登记表或新增必填字段。它是 Agent 整理结果，不是用户填写表单。Reporter 保留 Jira 真实调用者；代他人反馈时，在可核实且可共享的范围内说明原反馈者及来源，不冒用身份，也不把技术账号当作原反馈者。

新维护任务必须显式填写 Assignee。已有明确接手的当前维护者优先；没有接手人时，从 AO Jira 项目实时读取项目负责人，作为本流程默认维护负责人，再核验其可分派性。不能默认分给普通反馈者，不在文档或工位另存账号映射。负责人缺失、不可分派或有冲突时只询问所需负责人并保留草稿，不创建无人负责的维护任务。当前维护会话已明确的负责人继续有效，不重复询问。

创建后回读项目、摘要、关键正文和 Assignee，核验与请求一致才报告“已记录”。负责人不一致或字段缺失时保留实际编号，停止后续依赖步骤并修正或请求必要决定，不重复建单。成功回执简要给出 AO 编号、负责人、记录内容摘要、已知缺项和业务任务是否仍受阻；“已记录”不代表维护者已受理，更不承诺修复时间。

## 4. 维护受理与修复反馈

维护者通过 AO 项目现有问题列表统一查看各项目提交的问题，从同一 AO 任务接续，见[维护接续指引](../maintenance-guide.md#从-jira-接续维护任务)。`ao-feedback` 不承担列表巡检、任务接管、分诊、修复、转派或状态推进；这些操作由维护者沿现有维护流程执行。默认维护负责人承担分诊、必要转派和反馈责任；处理人变化后，新的 Assignee 接续该责任。只在需要补充影响修复决策的材料时集中提问，复用已有来源，不要求研发重复总结或登记。

| 节点 | 同一任务中的结果与下一责任 |
|---|---|
| 受理或暂缓 | 维护者说明归因依据、影响范围、是否可安全继续及下一步；暂缓时写明原因和再次处理的条件，不能宣称已解决 |
| 配置或使用问题 | 提供具体处理方法及适用版本，由用户授权后处理或自行操作；用原失败场景核验结果，不凭建议已给出就关闭 |
| 需要产品修复 | 维护者记录方案与验收，沿既有源码维护流程开发、审查和验证；反馈请求本身不授权修改业务源码、提交、合并或发布 |
| 修复候选通过 | 在原任务记录修复提交、PR、验证范围和未覆盖项；未发布时明确仍不可通过普通更新获得 |
| 修复可交付 | 维护者在原任务补充实际可获取版本/完整 SHA、适用范围、升级恢复入口和最小复测步骤，面向可核实的原反馈者给出反馈 |
| 原场景复测 | Agent 记录实际安装版本、与原问题对应的操作及可观察结果；安全且已有授权的验证由 Agent 完成，否则只让用户执行必要操作或确认业务结果 |

修复反馈首先写回原任务；原反馈者账号可核实时使用 Jira 原生提及，查询请求则直接在当前会话展示。Jira 通知受账号、权限和通知设置影响，评论回读成功仅证明反馈已记录，不等于消息已送达或用户已阅读。不额外搭建消息系统、定时监控或自动订阅；需要跨会话提醒时由用户另行明确授权。

完成必须有与反馈目标对应的验证依据。无需用户操作且维护者能验证相同环境与原场景时，引用该证据完成闭环；依赖用户环境时，修复可获取后仍保留待复测事实，由维护者跟进。用户无回应、候选测试通过、PR 已合并或版本已发布均不能单独证明原问题消失，也不能用等待超时自动关闭。

“待复测”等措辞是任务正文或评论中的事实说明，不新增 Jira 状态。复用 AO 实际可用流转和现有验收节点，关闭前由维护者核对上述证据；无法执行所需流转时保留事实并说明状态未同步。多个反馈场景共用一张任务时逐项披露结果，不能用一个现场通过代替全部覆盖。

复测失败时在原任务补充本次版本、证据和与原现象的关系，由维护者决定按现有流转继续或重开；确认是独立新问题才另建关联任务。判定为预期行为、不处理或重复的问题，也应给出依据、替代操作或主任务链接，并反馈给提出者；不得标记为“修复验证通过”。反馈记录与业务任务的继续、退出和归档分别判断。

## 5. 失败与中断恢复

| 异常 | 处理与恢复 |
|---|---|
| Jira 缺连接、权限或负责人 | 当前会话保留脱敏草稿、具体缺项与操作建议；已掌握信息不重采，不建立持久待发队列 |
| 创建或补充评论超时，结果未知 | 保留工具操作标识、请求目标及时间；先回读任务、评论或近期创建结果，按内容、作者、版本和现场关联核对，不以短暂查不到推定未写入 |
| 已知编号但回读失败或分派异常 | 返回该编号并标为待核验，停止依赖动作，不再创建；确认原写入未发生后才可重试，仍不明确时交人工核验 |
| 工位损坏、旧 epoch 或已清理 | 使用可取得的原回执、正式档案摘要和外部证据；披露缺口，不改状态、迁移旧任务或要求恢复完整工位才受理 |
| 修复尚不可安全应用 | 记录修复候选与实际安装的区别，按[更新与回退](update-and-rollback.md)选择适用途径；不因反馈修复而自动升级、清理或重放有副作用的命令 |

只读查询可恢复进度，提交和补充各自需要对应授权。已有明确有效的授权继续复用；“查询”不包含代用户确认复测、转派或关闭任务，维护者的转派和状态操作也不进入反馈技能范围。反馈辅助能力失败不额外阻断可安全继续的业务步骤，原任务的事实、权限和高风险停止边界继续有效。

## 6. 实施边界与验收场景

实现采用简短的共享 `skills/shared/ao-feedback/SKILL.md`，引用本文的统一使用合同，通过既有共享 Skill 安装、发现和刷新接线覆盖所有受管项目工位，不在某个 Project 下复制技能或维护项目白名单。共享技能按现有合同也可在源码维护根发现，但这不把它定义为维护者技能或维护任务处理入口。它只编排问题总结、必要资料采集和原生 Jira 提交、补充、查询，不增加 Bootstrap 业务命令、Runtime、Hook、状态字段、客户端或第三方依赖；工位 epoch 不因该方案改变。固定逻辑和权限保证不得用 Skill 散文冒充，外部可执行约束继续由原生平台和现役流程负责。

本文集中保存反馈设计，首次使用、FAQ 和维护指引只导航；Jira 保存实施、进度、评审和验收结果。当前设计不要求新建反馈登记表、独立维护工作流、现场包或账号路由配置，维护成本限定为共享技能、既有接线验证及本文。以下场景为后续实现的验收合同，不能把文档核对或 fixture 通过报告为真实反馈已交付。

| 场景 | 应验证的结果 |
|---|---|
| 不同项目的研发工位反馈接管/执行问题 | 共用同一技能和 AO 目标，无维护者角色或项目白名单限制；来源项目与原业务任务上下文保留 |
| 已有明确现象、期望与影响，业务任务正在执行 | 一句反馈获得可回读 AO 编号及负责人，无需用户填表；业务绑定、current/run、阶段和授权均未改变 |
| 接管未完成或问题归因未明 | 可以提交，run 缺失如实说明；不要求先完成接管或证明 AgenticOps 根因 |
| 维护者只读取 AO 问题及其中的证据 | 能理解问题总结并按必要前置条件、输入和步骤尝试复现或继续定位，不依赖原聊天或不可访问的本机文件 |
| 从 AO 列表统一受理各项目问题 | 列表中能找到各项目反馈及来源信息，维护者通过既有维护流程处理；反馈技能不执行分诊、修复、转派或状态推进 |
| 未安装、无活动任务或无法启动 | 用已有材料受理，缺项如实披露，不先建 run 或修工位 |
| 仅排障、仅草稿和明确提交 | 前两者无外部写入；明确反馈只执行必要写入，不重复确认已获授权 |
| 明确重复、相似不同及已关闭后复现 | 分别复用原任务、独立记录、补原任务并交维护者核验；不只凭标题合并 |
| 用户不是维护者或负责账号不可分派 | 新单显式分给已核验维护者；无有效人选时保留草稿，不静默分给反馈者；已有任务不擅自转派 |
| 输入含秘密、客户信息、个人路径或受限链接 | Jira 最终正文、必要评论和链接中不含敏感原文，不发送全量日志或配置 |
| 创建/评论结果未知及 Assignee 不一致 | 保留实际编号或操作标识，先核对原写入；恢复不重复创建或评论，不错误报告成功 |
| 候选通过、已发布但用户未更新、用户不回应 | 分别报告真实阶段，均不凭这些条件单独报告原问题已修复闭环 |
| 修复可获取、原场景通过或再次失败 | 原任务有版本、可执行复测步骤及证据；通过按覆盖情况关闭，失败补原任务并由维护者继续或重开 |
| 不修复、分拆及通知不可验证 | 记录理由或子项链接并反馈，剩余场景不丢失；不宣称 Jira 评论已送达用户 |
| Codex、Claude、旧安装刷新和无关仓库 | 共享来源一致，既有安装/发现/删除合同通过，无关仓库不发现该技能；同 epoch 既有状态保持原义 |

Skill 实现和安装接线变更按[维护验证](../maintenance-guide.md#5-验证)执行正式验收；真实 AO 权限、提交回读、查询和修复反馈复测另以经授权的真实场景核验。模拟通知、局部命令成功和维护者口述不能替代这些证据。
