# 更新与回退

本文现役命令继续按当前实现使用。[任务生命周期目标合同](../architecture/single-task-station.md#任务生命周期目标合同)定义完整目标；持久归档与[执行接管](../architecture/single-task-station.md#执行接管当前源码)已进入当前源码，两个清理范围也已进入当前源码；旧安装是否具备这些能力须核实实际版本。源码保留仍按工位合同区分当前实现；授权期限见[实施授权](task-authorization.md#实施授权)，旧安装不会因文档变化而更新。数据职责统一见[数据生命周期开发规范](../development-data-lifecycle.md)。

## 目标设计与当前实现

当前源码声明功能校验模式，支持符合现行合同的旧任务原工位接续。安装切换、缺项补齐及尚不支持的旧在途操作，统一以[工位合同](../architecture/single-task-station.md#10-升级与恢复)为准。不能将版本切换成功当成任务验收，也不能手改 epoch、绑定、授权或 PASS。

升级前先核实所有工位的在途操作、未持久成果与停写；旧 release/work-clean 或旧清理快照须先用原版核实收尾。已完成这些核验的正常开发任务无需退出、purge 或新建 run。旧客户端不识别新清单时，用已审查候选的 Bootstrap 入口执行：

```sh
python3 <候选>/bootstrap/installation_update.py --product-root <原安装> --mode update --to-ref <目标完整SHA> --expected-current-ref <原完整SHA> --check
python3 <候选>/bootstrap/installation_update.py --product-root <原安装> --mode update --to-ref <目标完整SHA> --expected-current-ref <原完整SHA> --writers-stopped
```

这里只切换原跟踪通道内可快进到达的代码。切换后启动新会话，刷新接线并运行正常 task status/quality status；Jira 协调缺失按 coordination check/prepare/complete 回读、确认并补齐，再重试原功能。原 run 和历史事件保留，当前证据按当前规则重算。缺项没有安全入口时保留现场并反馈，不改活动状态。

旧安装或回退目标未声明 `validation: feature` 时仍受旧 epoch 保护。以下关于跨 epoch 先退出、purge 的说明仅适用于旧模式；启动侧经研发明确确认并核实停写后，也可更新到跨 epoch 的功能校验目标，具体参数见下节。当前不承诺任意旧格式转换、旧在途操作自动采用或平台会话热更新。

## 启动与任务恢复时的更新选择

当前源码在 `station start` 启动或恢复会话时检查更新，不因已有任务跳过；同一会话内重试 takeover 或原 operation 仍沿原操作继续，不逐次联网检查。旧安装必须先采用包含此入口的版本，远端已发布不等于本机已获得能力。产品调用互斥见[工程架构](../architecture/agenticops-v1-architecture.md#产品调用与版本切换互斥目标设计)。

发现新版时输出原/目标完整 SHA、登记工位范围、兼容性和切换条件，保留原任务。Agent 说明更新内容及共享影响，研发可选择暂不更新：在启动命令追加 `--update-current-ref <原SHA> --update-target-ref <目标SHA>`，本次继续可信旧版，不持久关闭检查。

研发确认更新后，核实所有产品调用和未受管会话停写，在启动命令追加：

```sh
--apply-update --writers-stopped --update-current-ref <原SHA> --update-target-ref <目标SHA> --expected-stations '<探测返回的 stations JSON 数组>'
```

确认绑定具体版本及工位范围；版本或登记变化时重新展示，不沿用旧决定。单独 `--writers-stopped` 只声明停写，不代表同意更新。启动侧非阻塞取得独占租约后复查来源与目标，更新产品、修正当前工位接线并 doctor，再启动采用新版指引的会话；不创建新 run、不转换任务状态。其它工位仅报告待刷新。目标声明功能校验时不因 epoch 不同单独拒绝。必要依赖差异由所属功能按修补合同处理，未知旧在途语义仍须保全核实，不据此声称所有历史操作都可采用。

| 结果 | 本次行为 |
|---|---|
| 无更新且安装可信 | 启动或恢复原任务 |
| 发现兼容新版，尚未确认 | 展示影响和选择，不修改原任务；可明确选择继续旧版 |
| 具体更新已确认，停写、范围与租约满足 | 切换并核验版本和当前工位接线，启动新会话 |
| 存在其它调用或会话租约 | 不切换，可继续旧版、协调停写后重试或选择独立安装 |
| 旧模式目标不兼容 | 不自动清理；可继续旧版、独立安装或按旧合同处理 |
| 网络或目标材料不可得 | 当前安装可信时继续，披露检查失败，不宣称已经最新 |
| 安装身份不可信或更新结果未知 | 暂停依赖该安装的操作，先回读原切换，不盲目重试 |

检查可能更新 Git 对象库和远端跟踪引用，不修改工位任务。新版只指原 repository/tracking_branch 上可快进的新提交，不按 Tag 或版本字符串排序。受管会话监督进程持有共享租约直到退出，停写声明不能覆盖实际租约。旧测试容器仍挂载产品代码时也须停写。当前无已验证的平台热重载能力，切换后使用新会话并重新读取指引；CLI 替身通过不证明真实平台已加载新 Skill，真实平台另验。

独立安装适用于无法协调其它工位或不宜结算其任务的情况。用户指定独立安装目录与需对接的工位后，沿用原可信仓库和已确认通道安装并核验实际目标；安装期间分支前进时重新评估，不能声称仍是原预览 SHA。新建空工位直接绑定新版；复用原路径先由原版退出当前任务并 purge，再由新版 init，明确 --reuse-materials 保留 source/config。空闲旧工位也必须先受控解绑；不手改 product_root，不复制 current、operation、授权或旧 PASS。旧 Product Root 与其正式档案保留，其它工位不改绑定、不停任务、不升级。原版退出失败时停在原现场恢复，允许改用新路径工位或暂不更新，不要求先修复所有其它工位。

用户仅选择更新当前工位，不授权更新共享根或结算其它工位；整体更新涉及全部登记工位时需取得对应范围的明确决定。材料保全及跨 epoch 退出继续引用本页既有合同，不因新任务接管自动扩大清理范围。旧客户端首次应用与回退至旧版沿手工停写边界处理，不宣称新协议可追溯保护未接入进程。

## 同 epoch 恢复与跨 epoch 切换的目标入口

本节为已提供源码入口的现役恢复路径；不等于本页开头所述的功能内聚修补目标。

“原版无法退出，而修复版跨 epoch”的完整解法及定点更新、原版本维护恢复、预检和有限续接入口由[工位合同](../architecture/single-task-station.md)统一维护，属于[完整退出优化](../architecture/single-task-station.md)的产品切换部分，本页不另定义规则。当前源码已提供入口；旧安装是否具备能力须回读实际提交与帮助，源码可用不代表旧安装已应用。无参 update 仍跟随原记录分支，定点更新不能换通道。原版退出修复先在原 epoch 验收，不混入新版不兼容功能，不要求旧现场先升 epoch 才能清理。

当前遇到此循环时，先核实原版本退出缺陷和适用的兼容修复，复用原版本维护成果；尚无受信、可验证的应用路径时保全旧现场并停在恢复应用之前。不要手改 epoch、复制新版文件覆盖安装、删除登记，或把独立新版启动当作旧工位已退出。补丁应用、真实退出和最终升级分别核验，工作进展及待验证项记录在 Jira。

安装入口支持以下参数，命令中的 SHA 必须由修复、审查及验收证据选定：

```sh
<product-root>/agenticops update --to-ref <目标完整SHA> --expected-current-ref <原完整SHA> --check
<product-root>/agenticops update --to-ref <目标完整SHA> --expected-current-ref <原完整SHA> --writers-stopped
<product-root>/agenticops recover-install --source-branch <维护分支> --to-ref <补丁完整SHA> --expected-current-ref <原完整SHA> --check
```

定点或维护恢复有登记工位时，执行前核验全部共享产品调用停写并声明 `--writers-stopped`。安装中断只用原模式、来源及原/目标 SHA 加 `--resume` 续接；它不恢复业务任务。第一次旧客户端没有入口时，从已审查的匹配候选执行 `python3 <候选>/bootstrap/installation_update.py --product-root <原安装> --mode update|recover-install`，加同样的完整参数；只支持已回归的 product.json schema 2、单 epoch 清单及 stations.json schema 1，不在线迁移旧状态。

## 部分克隆更新与材料准备

安装更新先获取来源分支和缺失版本材料，再核验兼容性与切换条件，最后准备安装范围并切换版本。阶段、结果和恢复提示使用中文；Git 原始诊断、命令参数和结构化回执的协议字段保留原文。当前版本不变时显示“已核验当前版本并补齐安装范围”，不误称发生版本更新。设计及限制见[现役架构](../architecture/agenticops-v1-architecture.md#7-生成清理与升级分层)。

`--check` 会联网获取材料并写入 Git 对象库和远端跟踪引用，但不会切换产品或修改工位；“预检通过”不代表实际更新已完成。若提示“版本材料补齐失败，本次未执行版本切换”，应保留现场，检查记录的来源远端、连接与认证后重试原命令；不要设置环境变量绕过本地核验，也不要直接覆盖产品文件。若为原切换后的 `--resume`，安装可能已处于目标 HEAD，仍须按原模式及 SHA 核验续接，不能仅凭下载失败提示推断已回退。材料补齐不豁免目标兼容模式、停写与安装身份检查；具体拒绝原因按预检结果处理。

更新失败时，先看具体原因，再按“现场”中的 HEAD、产品记录和跟踪分支核对安装。失败不等于已经回退：若 HEAD 与产品记录不同，或切换执行后中断，保留现场并用原模式、来源及原/目标完整 SHA 加 `--resume` 续接；不要直接重试无参 update。只有已确认在切换前拒绝，才在消除原因后重试原命令。

- 安装有未提交修改：在提示的安装目录运行 `git status`，先核对并保全修改，再独立处理；更新器不自动 stash 或覆盖文件。
- 来源不一致、目标不属于来源分支、不能快进或历史不足：核对 `.local/product.json`、`git remote get-url origin` 和完整 SHA；来源可信但历史不足时补齐历史，再重试。维护分支偏离原通道时按本页维护恢复边界处理，不用 reset 或强制合并绕过。
- 旧模式目标跨 epoch 更新因仍有绑定工位被拒绝：按失败提示列出的工位，用原版本退出并 purge，全部解绑后重试。兼容性定义以[工位合同](../architecture/single-task-station.md#10-升级与恢复)为准。
- 定点更新、维护恢复或功能校验模式跨 epoch 更新要求停写：核验全部共享产品调用已停写后，在原命令中加 `--writers-stopped` 重试；无需退出或 purge 工位。该参数不代替实际停写。
- 工位登记缺失、损坏或安装版本无法核验：保留安装与工位，请维护者根据原操作和可信记录核查，不手改登记或 epoch。

旧版若报“原安装不在恢复主线上”或“恢复路径经过不同 epoch”，属于已移除的历史路径限制。先核对两端 epoch、Git 祖先关系及安装身份；同 epoch 且满足其它切换条件时，应使用已审查修复候选的入口执行，不能靠重复调用旧 updater 获得修复，也无需因此 purge 工位。

旧 updater 不会因为远端已经修复而自动获得新逻辑。首次应用仍按本页的已审查候选入口处理；源码回归通过不代表已有安装已修复。

## 共享 Skill 资源与接线

安装范围包含 `docs/` 人读文档，项目 Skill 可直接打开质量检查、授权和工位合同等相对链接，不依赖维护源码目录。旧安装缺少该目录时，在绑定 Product Root 运行新版 `agenticops update` 补齐；同一提交也会刷新安装范围，不改变任务状态或原回退指针。安装范围补齐不代表业务任务已验收。

安装只包含 `skills/shared/`，维护根和工位通过各自原有受管清单接入共享技能。新增共享技能不修改任务状态或 epoch；同 epoch 旧清单在 `station repair` 时补齐，现有任务与授权保持原语义。`station doctor` 可报告缺资源、缺链接与漂移；修复不覆盖未受管同名文件。

旧版 updater 首次切换到支持共享 Skill 的版本时，可能保留旧 sparse-checkout 范围。此时先在绑定安装产品根再次运行 `./agenticops update`，由新版更新器补齐共享子树，再运行 `station doctor --station <工位路径>` 和 `station repair --station <工位路径>`。产品 HEAD 未变化时只补齐资源，不覆盖原回退指针；不要复制技能到用户目录来补偿缺失。重新执行 update 仍遵守原来的脏树、远端及兼容检查。

新版更新与回退按目标 Git 树选择共享子树，维护 Skill 始终不进入安装。回退后由目标版本的原生 repair 清理其不再需要、且清单归属和目标仍匹配的生成链接；漂移则停止并保留材料。生成与清理沿用原有清单，目标版本不读取或迁移任务数据。该支持不追溯改变旧 updater；缺资源或失败时不宣称共享技能已经可用。

## 第一阶段：同版本生成与清理

执行 `agenticops version` 查询当前产品版本；在源码或工位目录使用 `./agenticops version`，也可用安装入口 `~/.agentic-ops/agenticops version`。输出为 `<分支>-<标签>-<提交数>-<提交编号>`；工位入口显示其绑定 Product Root 的版本，不读取业务仓库版本。产品存在未提交修改时附加 `-dirty`，供诊断使用；接管水印仍拒绝使用脏产品版本。查询不更新产品或工位状态。

先在同一个 Product Root 版本完成闭环：

1. agenticops station init --station <绝对路径> --project tapdata，生成绑定、空 current 和 config/source/runtime；正式档案在绑定 Product Root 的 `.archive/` 中按 run 保存。
2. 在工位中接管任务。处理中不能接新任务；按需归档保全成果，再执行任务清理，精确授权范围以项目 Skill 和 CLI 为准。
3. 明确执行 agenticops station purge --station <绝对路径> --yes。清理验证生成归属，不删除 source/config、Product Root `.archive/` 和未知用户材料；本版 purge 先调用统一退出脚本，保留未知对象并返回结果，不将已解绑误称清理无残留。
4. 确认 .agenticops 与受管接线已移除，再初始化。保留目录非空时明确追加 --reuse-materials；这只允许保留既有真实目录，不授权覆盖、删除或导入旧任务。runtime 必须为空，重新生成新的 station_id。

接线刷新使用 station repair；任务或工位清理使用 `workflow/station-clean.py --scope task|station`，先预检并确认材料处置，详见[清理与退出](task-authorization.md#清理与退出)。

## 第二阶段：跨版本编排

升级器只编排产品切换，不读取 current task、operation 或 runtime，也不实现任务清理。新版功能校验模式与旧 epoch 模式的唯一边界见[工位合同](../architecture/single-task-station.md#当前实现的兼容与切换边界)。有工位时跨 epoch 更新要求停写声明；旧模式目标仍要求空登记。回退不转换任务，新版已经产生的状态不能交给旧版猜测采用。

## 任务处理中升级后继续

任务未完成而产品必须升级时，先按[从 Jira 任务接续](task-authorization.md#从-jira-任务接续)补齐 Jira/GitHub 中的有效设计、代码、验证和待办。目标为功能校验模式且旧操作已核实可继续时，保留工位更新后沿原 run 接续；缺项由所属入口说明并补齐。仅在需要旧模式切换或局部现场无法安全采用而明确选择重建时，才按原版合同退出、purge 后从 Jira 接续；这不取消 Jira 任务，也不复制旧授权。

共享安装有其它活动工位时，不注销其登记或更新共享安装来绕过检查。用户只授权隔离当前工位时，先在原版本退出当前工位，明确复用 source/config，以相同产品版本在独立安装目录重新绑定；随后只对独立安装执行升级。记录全部受影响工位并回读绑定和版本，另一工位的源码、运行状态及产品版本不在处置范围。

旧版本记录不足时，可以用临时脚本保全本地材料，并由 AI 根据旧会话、实际 Git 与报告补齐 Jira/GitHub。保全工具不成为永久兼容器；恢复不要求输入本机备份路径，未上传的必要附件仍需可靠保全或重新生产。原版本清理失败就保留原版本恢复，新版本只验收自身接管输入。

## 本次首次切换

通用工具 Hook 执行链在 Manifest v3 中退役，原 Hook 的可执行依赖不再随产品安装。旧安装按其实际兼容模式执行切换；`repair --accept-checkpoint-migration` 仅处理受管接线，不转换任务或证明业务状态兼容。人工或全局 Hook 不自动扫描、删除，不能证明归属的文件应保留并由用户处理。

当前 epoch 以机器契约为准，清单不再维护最低 updater protocol、旧 epoch 映射或支持列表。本版不提供旧状态兼容 Runtime 或逐版本迁移器。功能校验模式沿原任务校验和接续；只有旧模式目标要求退出，或现场无法安全采用且用户选择重建时，才先保全材料、按原版清理并注销绑定，再更新和初始化。旧源码池、Git refs、导出材料和 Product Root `.archive/` 不由新版本删除。替换或删除整个 Product Root 前必须先保留或导出 `.archive/`。新升级规则只保护采用此协议后的切换，不追溯保护旧升级器。

若手动替换产品文件或源码分支绕过升级器，应先核验安装 HEAD、产品记录、工位绑定和在途结果，按安装恢复入口处理。不能仅凭新版能够读取任务认定切换完成；不手改 epoch、注册表或当前状态。

任何清理失败都留在原版本处理，不能自动进入新生成步骤。已有确认只覆盖其明确路径与材料；新增文件、范围变化和未知结果先回读并取得缺失决定。合并、发布、Tag 和保护分支写入仍需独立授权。

### 修补会话与任务检查的边界

功能校验模式下，启动前发现任务或操作数据不符时，更新探测保留诊断，允许在可信产品与安全接线检查通过后启动 Agent 分析修补。station repair/doctor 核验接线、目录和产品绑定，不承担任务字段语义转换，也不覆写已有任务文件或旧目录。旧 epoch 模式仍沿其严格检查。

这不开放任务推进：新接管及原功能的读取、写入、授权和质量检查保持严格。Agent 先按所属依赖描述核实并与研发确认差异，沿修补入口应用，再由原功能复查。会话能启动、工位接线通过和任务数据可继续是三个不同结论；损坏 JSON、未知语义或不可恢复材料仍需处理，不能靠启动成功宣称兼容完成。

## Python 3.12 升级与回退

新运行基线为 Python 3.12.x，业务项目 Python 保持独立。操作前核对实际安装 SHA；旧客户端不会因源码或文档更新获得新能力。先准备可信 3.12 解释器并保留原版可用解释器；安装可通过 `AGENTIC_OPS_PYTHON` 指定其绝对路径，不覆盖系统 Python。专用产品环境在 `.local/venv/product`，不包含内部维护依赖，不把业务虚拟环境复制到产品根。

升级依次核验来源、原/目标完整 SHA、全部登记工位及在途操作，保全必要成果，预检目标解释器，再按既有停写与独占租约合同切换。Python 环境准备失败时不切代码；正常任务保留原 run、源码、config 和历史证据，切换后刷新接线、doctor，并在新会话中由任务所属入口复查，不能把启动成功当作验收通过。旧客户端首次切换使用已审查候选的 Bootstrap 和显式 3.12 解释器，沿本页定点更新命令执行；不先覆盖旧安装脚本。

回退前停写并核验原 SHA、原可用解释器及旧版本状态兼容性。回退代码和接线，不清理产品环境、任务材料或旧解释器；旧版仍按其原运行要求执行。结果未知先回读，沿原/目标 SHA 的既有 resume 协议处理，不盲目重复切换。若新版运行已产生旧版无法理解的状态，保留现场并停止回退，不能覆盖任务状态或复制旧 PASS。

专用环境损坏时，保留原目录，使用独立可信 3.12 解释器及受审查候选 Bootstrap 诊断和恢复；明确配置可绕开损坏解释器启动恢复工具，但正常升级不会静默覆盖坏环境。无法协调共享产品根全部工位时，不更新共享根，沿既有独立安装合同处理。源码验收只证明隔离测试结果，实际工位升级须另行核验具体安装、SHA、工位范围及停写授权。
