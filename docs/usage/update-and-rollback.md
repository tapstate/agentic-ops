# 更新与回退

以下命令在安装目录的使用工作面执行，不需要进入业务工作空间：

```sh
~/.agentic-ops/agenticops update
~/.agentic-ops/agenticops rollback
```

`update` 仅 fast-forward 到安装时记录的分支；`rollback` 回到最近一次更新前的提交。安装目录有本地修改、HEAD 偏离安装记录或远端历史异常时，命令会停止，不会覆盖现场。

产品使用单调递增的 `workspace_state_epoch` 管理工作空间持久化兼容性。`update` 和 `rollback` 在切换产品提交前读取目标兼容性清单；当前与目标 epoch 相同，或目标明确支持当前 epoch 时，不要求结束任务。若目标不支持当前 epoch，命令会检查全部已登记工作空间并失败关闭，列出 workspace、issue、status、run 和旧状态残留。

遇到不兼容提示时，产品版本尚未切换。留在当前版本完成或明确停用任务，把需保留的任务材料和绑定信息导出到工作空间之外并核验，再按明确确认的范围使用当前版本的 `workspace purge` 受控解绑。任务级 purge 不等于注销工作空间；即使任务为空，不兼容的绑定也必须先解除。脏 worktree、未合并成果、不可访问工作空间或无法识别的旧状态必须人工决定处置，不自动删除源码池、Git 分支或导出材料。这些本地操作不修改 Jira。

全部不兼容工作空间均处置完毕后，重新执行原 `update` 或 `rollback` 命令，预检通过才切换产品。任一步失败都保留原产品版本，不以部分工作空间已清理视为全部成功。切换成功后再明确初始化新工作空间；初始化失败恢复初始化操作，不重复旧清理，也不自动删除保留材料。

本次单任务工位切换不另行发布兼容过渡版本，也不承诺旧安装可直接 update 到不兼容的新工位版本：旧用户先用旧版本保存材料并受控解绑，再安装新版本、明确重建工作空间。新升级规则从新版本开始保障后续升级与回退，不能追溯保护本次旧客户端的切换。当前基础代码的 Updater 能力为协议 2，机器清单仍保持 epoch 2 和最低协议 1；完整新工位版本才提升 epoch 并要求最低协议 2，以拒绝旧升级器直接进入。新安装不经过旧升级器，不能将这种重新安装路径表述为兼容在线升级。

手动替换文件或直接切换源码可能绕过升级预检。新入口必须拒绝不兼容状态，不能自动 repair；先根据更新前记录的产品提交定位可信旧版本，并在独立产品目录中核验恢复方式，不盲目执行可能同样被兼容门禁拒绝的 rollback。找不到原版本、来源或绑定证据时停止并人工处理。此文不承诺对任意手工替换都有自动恢复路径；直接绑定源码的业务工作空间也必须遵守切换前处置顺序。

工作空间无法启动或 `doctor` 报接线漂移时，使用已绑定的产品根目录修复：

```sh
~/.agentic-ops/agenticops doctor --workspace <项目工作空间>
~/.agentic-ops/agenticops repair --workspace <项目工作空间>
```

`doctor` 只读检查；`repair` 只重建受支持代际的可再生接线，不执行跨代际采用或在线数据迁移。更新后，已启动的 Agent 需重启。

不要用 `rollback` 管理 AgenticOps 源码仓库；源码维护使用 Git 流程，见[维护指引](../maintenance-guide.md)。
