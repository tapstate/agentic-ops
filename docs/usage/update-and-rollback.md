# 更新与回退

当前清单、归档和退出语义使用 epoch 31。epoch 30 及以前的工位须先使用原版本结束任务并归档释放或清理，再显式 purge 后切换并初始化；目标版本不解析或迁移旧任务。兼容值仍以[机器清单](../../contracts/station-state-compatibility.json)为准。

本页负责用户切换产品的顺序与失败边界。工位数据合同见[工位合同](../architecture/single-task-station.md)。不要把“更新成功”“工位生成成功”和“应用验收通过”混为一谈。

## 新任务前检查与更新目标设计

本节定义目标行为，尚未实现；当前安装不会仅因接管请求自动检查或更新。多工位调用与切换的唯一互斥设计见[工程架构](../architecture/agenticops-v1-architecture.md#产品调用与版本切换互斥目标设计)，稳定场景验收见 [PROD-001](../user-stories/v1/prod-001-install-and-connect-agent.md#新任务前更新目标验收)。既有 `update --check`、定点更新和恢复入口继续复用，不另建更新器。

仅空闲工位接新任务、或从外部成果建立新 run 时进入检查；先回读 current 与 operation，已有 run 和在途 takeover 按原请求恢复，不插入自动升级。检查在创建 operation/run、档案占位或下载业务源码之前完成；无需等 Jira 分支选择齐备才发现产品更新。任务准入与 Jira 状态不因更新而放宽。

新版定义为安装记录的 repository/tracking_branch 上可快进到达的新提交，不按版本字符串或其它通道 Tag 排序。Bootstrap 探测返回当前/目标完整 SHA、来源分支、检查时间、epoch 兼容结论及独立的切换阻塞原因；同 SHA 为无更新，缺少证明 Git 祖先关系的历史或两端兼容材料为未知；状态兼容只比较端点 epoch，遵循工位合同，不逐提交核验。兼容但正在使用与不兼容是不同结果。现有 --check 会因跨 epoch 登记非空直接拒绝，目标探测须能报告发现的新版本及阻塞详情，同时保持实际应用入口的拒绝条件。

| 结果 | 本次行为 |
|---|---|
| 无更新且当前安装可信 | 继续原接管 |
| 同 epoch 兼容且取得独占安全窗口，来源与实际目标未变化 | 自动应用目标，回读版本及产品记录，修正当前工位接线并核验会话采用新版后继续 |
| 同 epoch 兼容，但存在其它产品调用、会话租约或未受管会话无法确认停写 | 不切换；提供暂不更新、协调暂停后更新、独立新版安装三种适用选择 |
| 不兼容 | 用户选择继续旧版、独立安装新版，或按原版退出全部登记工位后整体更新；不默认执行清理 |
| 网络、认证或目标材料暂不可得 | 报告未能确认更新；当前安装及绑定可信时继续旧版，不误报已经最新 |
| 目标兼容性未知 | 禁止升级，当前版本自身可信时可继续旧版 |
| 当前安装身份、HEAD/记录不可信，或更新结果未知 | 暂停依赖该安装的接管并核验现场，不自动回退或盲目重试 |

检查可以写 Git 对象库和远端跟踪引用，不切换 HEAD、写版本记录、改回退指针、改工位状态或执行目标代码。目标探测复用材料准备能力并使用既有有界网络超时；一次失败不自动轮询。新接管的有效选择绑定 Product Root、工位、原/目标 SHA 及影响范围，只在本次协作材料中复用，不增加永久偏好或任务字段。检查后目标变化须重新展示；自动更新分支重检后重新评估，用户选择不兼容升级或扩大范围的决定不得沿用到新目标。沉默不代表选择，等待时可继续独立材料核查。

同 epoch 不要求结束业务任务，但切换必须满足调用与会话停用条件；不能把锁空闲、任务空闲或暂停业务进程当作同一事实。选择继续旧版不关闭下次新任务检查。实际更新后的产品 SHA、版本记录、当前工位 repair/doctor 及绑定分别回读；其它工位只报告待刷新，不自动 repair --all。取得新版磁盘文件不等于当前 Agent 已发现新版技能：默认采用已验证的重载能力或在工位新开会话，重新读取 AGENTS、Project 准入和项目/共享 Skill，核验实际版本后才创建 run。平台证据不足时保持会话生效待核验，不启动嵌套 Agent，不重启整个桌面应用。

独立安装适用于无法协调其它工位或不宜结算其任务的情况。用户指定独立安装目录与需对接的工位后，沿用原可信仓库和已确认通道安装并核验实际目标；安装期间分支前进时重新评估，不能声称仍是原预览 SHA。新建空工位直接绑定新版；复用原路径先由原版退出当前任务并 purge，再由新版 init，明确 --reuse-materials 保留 source/config。空闲旧工位也必须先受控解绑；不手改 product_root，不复制 current、operation、授权或旧 PASS。旧 Product Root 与其正式档案保留，其它工位不改绑定、不停任务、不升级。原版退出失败时停在原现场恢复，允许改用新路径工位或暂不更新，不要求先修复所有其它工位。

用户仅选择更新当前工位，不授权更新共享根或结算其它工位；整体更新涉及全部登记工位时需取得对应范围的明确决定。材料保全及跨 epoch 退出继续引用本页既有合同，不因新任务接管自动扩大清理范围。旧客户端首次应用与回退至旧版沿手工停写边界处理，不宣称新协议可追溯保护未接入进程。

## 同 epoch 恢复与跨 epoch 切换的目标入口

“原版无法退出，而修复版跨 epoch”的完整解法及定点更新、原版本维护恢复、预检和有限续接入口由[工位合同](../architecture/single-task-station.md)统一维护，属于[完整退出优化](../architecture/single-task-station.md)的产品切换部分，本页不另定义规则。当前源码已提供入口；旧安装是否具备能力须回读实际提交与帮助，源码可用不代表旧安装已应用。无参 update 仍跟随原记录分支，定点更新不能换通道。原版纯历史重放及合法退出修复先在原 epoch 验收，新默认会话准入不混入兼容补丁，不要求旧现场先升 epoch 才能清理。

当前遇到此循环时，先核实原版本退出缺陷和适用的兼容修复，复用原版本维护成果；尚无受信、可验证的应用路径时保全旧现场并停在恢复应用之前。不要手改 epoch、复制新版文件覆盖安装、删除登记，或把独立新版启动当作旧工位已退出。补丁应用、真实退出和最终升级分别核验，工作进展及待验证项记录在 Jira。

安装入口支持以下参数，命令中的 SHA 必须由修复、审查及验收证据选定：

```sh
<product-root>/agenticops update --to-ref <目标完整SHA> --expected-current-ref <原完整SHA> --check
<product-root>/agenticops update --to-ref <目标完整SHA> --expected-current-ref <原完整SHA> --writers-stopped
<product-root>/agenticops recover-install --source-branch <维护分支> --to-ref <补丁完整SHA> --expected-current-ref <原完整SHA> --check
```

定点或维护恢复有登记工位时，执行前核验全部共享产品调用停写并声明 `--writers-stopped`。安装中断只用原模式、来源及原/目标 SHA 加 `--resume` 续接；它不恢复业务任务。第一次旧客户端没有入口时，从已审查的匹配候选执行 `python3 <候选>/bootstrap/installation_update.py --product-root <原安装> --mode update|recover-install`，加同样的完整参数；只支持已回归的 product.json schema 2、单 epoch 清单及 stations.json schema 1，不在线迁移旧状态。

## 部分克隆更新与材料准备

安装更新先获取来源分支和缺失版本材料，再核验兼容性与切换条件，最后准备安装范围并切换版本。阶段、结果和恢复提示使用中文；Git 原始诊断、命令参数和结构化回执的协议字段保留原文。当前版本不变时显示“已核验当前版本并补齐安装范围”，不误称发生版本更新。设计及限制见[现役架构](../architecture/agenticops-v1-architecture.md#7-生成清理与升级分层)。

`--check` 会联网获取材料并写入 Git 对象库和远端跟踪引用，但不会切换产品或修改工位；“预检通过”不代表实际更新已完成。若提示“版本材料补齐失败，本次未执行版本切换”，应保留现场，检查记录的来源远端、连接与认证后重试原命令；不要设置环境变量绕过本地核验，也不要直接覆盖产品文件。若为原切换后的 `--resume`，安装可能已处于目标 HEAD，仍须按原模式及 SHA 核验续接，不能仅凭下载失败提示推断已回退。不同 epoch、有绑定工位或其它切换条件不满足时，即使材料已补齐也仍会拒绝更新。

更新失败时，先看具体原因，再按“现场”中的 HEAD、产品记录和跟踪分支核对安装。失败不等于已经回退：若 HEAD 与产品记录不同，或切换执行后中断，保留现场并用原模式、来源及原/目标完整 SHA 加 `--resume` 续接；不要直接重试无参 update。只有已确认在切换前拒绝，才在消除原因后重试原命令。

- 安装有未提交修改：在提示的安装目录运行 `git status`，先核对并保全修改，再独立处理；更新器不自动 stash 或覆盖文件。
- 来源不一致、目标不属于来源分支、不能快进或历史不足：核对 `.local/product.json`、`git remote get-url origin` 和完整 SHA；来源可信但历史不足时补齐历史，再重试。维护分支偏离原通道时按本页维护恢复边界处理，不用 reset 或强制合并绕过。
- 跨 epoch 更新因仍有绑定工位被拒绝：按失败提示列出的工位，用原版本退出并 purge，全部解绑后重试。兼容性定义以[工位合同](../architecture/single-task-station.md#10-升级与恢复)为准。
- 同 epoch 定点更新或维护恢复要求停写：核验全部共享产品调用已停写后，在原命令中加 `--writers-stopped` 重试；无需退出或 purge 工位。该参数不代替实际停写。
- 工位登记缺失、损坏或安装版本无法核验：保留安装与工位，请维护者根据原操作和可信记录核查，不手改登记或 epoch。

旧版若报“原安装不在恢复主线上”或“恢复路径经过不同 epoch”，属于已移除的历史路径限制。先核对两端 epoch、Git 祖先关系及安装身份；同 epoch 且满足其它切换条件时，应使用已审查修复候选的入口执行，不能靠重复调用旧 updater 获得修复，也无需因此 purge 工位。

旧 updater 不会因为远端已经修复而自动获得新逻辑。首次应用仍按本页的已审查候选入口处理；源码回归通过不代表已有安装已修复。

## 共享 Skill 资源与接线

安装范围包含 `docs/` 人读文档，项目 Skill 可直接打开质量检查、授权和工位合同等相对链接，不依赖维护源码目录。旧安装缺少该目录时，在绑定 Product Root 运行新版 `agenticops update` 补齐；同一提交也会刷新安装范围，不改变任务状态或原回退指针。安装范围补齐不代表业务任务已验收。

安装只包含 `skills/shared/`，维护根和工位通过各自原有受管清单接入共享技能。新增共享技能不修改任务状态或 epoch；同 epoch 旧清单在 `station repair` 时补齐，现有任务与授权保持原语义。`station doctor` 可报告缺资源、缺链接与漂移；修复不覆盖未受管同名文件。

旧版 updater 首次切换到支持共享 Skill 的版本时，可能保留旧 sparse-checkout 范围。此时先在绑定安装产品根再次运行 `./agenticops update`，由新版更新器补齐共享子树，再运行 `station doctor --station <工位路径>` 和 `station repair --station <工位路径>`。产品 HEAD 未变化时只补齐资源，不覆盖原回退指针；不要复制技能到用户目录来补偿缺失。重新执行 update 仍遵守原来的脏树、远端及兼容检查。

新版更新与回退按目标 Git 树选择共享子树，维护 Skill 始终不进入安装。回退后由目标版本的原生 repair 清理其不再需要、且清单归属和目标仍匹配的生成链接；漂移则停止并保留材料。生成与清理沿用原有清单，目标版本不读取或迁移任务数据。该支持不追溯改变旧 updater；缺资源或失败时不宣称共享技能已经可用。

## 第一阶段：同版本生成与清理

执行 `agenticops version` 查询当前产品版本；在源码或工位目录使用 `./agenticops version`，也可用安装入口 `~/.agentic-ops/agenticops version`。输出为 `<分支>-<标签>-<提交数>-<提交编号>`；工位入口显示其绑定 Product Root 的版本，不读取业务仓库版本。产品存在未提交修改时附加 `-dirty`，供诊断使用；接管水印仍拒绝使用脏产品版本。查询不更新产品或工位状态。

先在同一个 Product Root 版本完成闭环：

1. agenticops station init --station <绝对路径> --project tapdata，生成绑定、空 current 和 config/source/runtime；正式档案在绑定 Product Root 的 `.archive/` 中按 run 保存。
2. 在工位中接管任务。处理中不能接新任务；结束后 release 或 clean，精确授权范围以项目 Skill 和 CLI 为准。
3. 明确执行 agenticops station purge --station <绝对路径> --yes。清理验证生成归属，不删除 source/config、Product Root `.archive/` 和未知用户材料；本版 purge 先调用统一退出脚本，保留未知对象并返回结果，不将已解绑误称清理无残留。
4. 确认 .agenticops 与受管接线已移除，再初始化。保留目录非空时明确追加 --reuse-materials；这只允许保留既有真实目录，不授权覆盖、删除或导入旧任务。runtime 必须为空，重新生成新的 station_id。

接线刷新使用 station repair；工作清理使用 workflow/station-clean.py --action work-clean。

## 第二阶段：跨版本编排

升级器只编排产品切换，不实现任务清理逻辑。兼容清单只维护 `station_state_epoch` 一个配置项。升级器在 Git 引用切换前比较当前与目标值：相同可直接更新；不同则必须存在可读取的空工位登记。任一仍登记的工位都会停止切换并列出路径，提示继续使用原版本按其退出合同执行 release/clean 与 `station purge`。本版归档失败按[工位合同](../architecture/single-task-station.md#8-脚本执行异常接力与恢复)处理用户决定，旧版本不得套用本版语义。单独执行 archive 仍占用工位，不满足升级条件。登记缺失、损坏或无法读取同样停止。升级器不读取 current task、operation、runtime 或旧状态；原版任务与旧状态必须由原版处理，不由目标版本猜测迁移。

同 epoch 更新执行 `agenticops update`，随后 doctor 检查、repair 刷新接线。epoch 变化后，研发先在原版本完成任务并解绑全部工位，更新成功后再用目标版本重新 init；不自动 repair、init 或导入旧任务。rollback 只适用于安装目录，并使用相同的“epoch 变化则登记必须为空”规则；产品源码使用 Git 治理流程，不自动移动源码分支。

## 任务处理中升级后继续

任务未完成而产品必须升级时，先按[从 Jira 任务接续](task-authorization.md#从-jira-任务接续)补齐 Jira/GitHub 中的有效设计、代码、验证和待办。原版本按其合同记录未完成事实、退出并 purge；这只结束本地 run，不取消 Jira 任务。之后按目标版本初始化，通过 Jira key 接续既有分支，重新建立本版执行与授权。跨多个 epoch 同样处理，不逐级转换旧状态。

共享安装有其它活动工位时，不注销其登记或更新共享安装来绕过检查。用户只授权隔离当前工位时，先在原版本退出当前工位，明确复用 source/config，以相同产品版本在独立安装目录重新绑定；随后只对独立安装执行升级。记录全部受影响工位并回读绑定和版本，另一工位的源码、运行状态及产品版本不在处置范围。

旧版本记录不足时，可以用临时脚本保全本地材料，并由 AI 根据旧会话、实际 Git 与报告补齐 Jira/GitHub。保全工具不成为永久兼容器；恢复不要求输入本机备份路径，未上传的必要附件仍需可靠保全或重新生产。原版本清理失败就保留原版本恢复，新版本只验收自身接管输入。

## 本次首次切换

通用工具 Hook 执行链在 Manifest v3 中退役，原 Hook 的可执行依赖不再随产品安装。该变更提升工位 epoch；即使某个工位已经不生成 Hook，也必须先由原版本退出并 purge，再切换重建。`repair --accept-checkpoint-migration` 只处理同 epoch 的已托管产物，不是跨 epoch 升级入口；人工或全局 Hook 不自动扫描、删除，不能证明归属的文件应保留并由用户处理。

当前 epoch 以机器契约为准，清单不再维护最低 updater protocol、旧 epoch 映射或支持列表。本版不提供旧状态兼容 Runtime：用户先用仍可运行的原版本保存材料、清理旧任务及其受控源码现场、注销旧绑定，然后再更新或重新安装并明确初始化。旧源码池、Git refs、导出材料和 Product Root `.archive/` 不由新版本删除。替换或删除整个 Product Root 前必须先保留或导出 `.archive/`。新升级规则只保护采用此协议后的切换，不追溯保护旧升级器。

若手动替换产品文件或源码分支绕过升级器，新入口拒绝旧状态。应恢复与旧状态匹配的原产品版本完成清理，或先保全旧现场、使用独立空目录安装和初始化；不手改 epoch、注册表或当前状态。

任何清理失败都留在原版本处理，不能自动进入新生成步骤。已有确认只覆盖其明确路径与材料；新增文件、范围变化和未知结果先回读并取得缺失决定。合并、发布、Tag 和保护分支写入仍需独立授权。
