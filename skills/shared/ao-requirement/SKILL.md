# 需求理解与设计

目标是让需求合理、明确、可实施、可验证，并帮助研发理解问题、项目现状、设计取舍和验收，能够据此决策。允许结论是不做、复用或缩减需求。不要把用户提出的实现方式直接当作必要需求，也不要将完整文档或一句“确认”当作理解和质量的证明。

## 先建立项目上下文

维护面与使用面共用方法，不按角色维护两套设计。根据用户明确目标、现有项目绑定及仓库规则确定正在设计哪个产品的需求；工位绑定与请求不一致时澄清目标，不静默更改绑定，也不把中央工具源码当作业务源码。跨项目需求分别核查各项目约束，补充接口和整体验收。

按当前问题需要，读取项目目标、架构、源码、已有需求、使用和验证指引；优先使用项目已有导航、Profile 和原生读取能力，不要求新建需求配置表，不一次加载全部资料。保留支撑关键判断的来源，区分已核实事实、待验证假设和建议；文档与实际行为冲突时核查相关源码或运行证据，无法核实时明确缺口。

需求分析不要求已有工作项、活动 run 或先接管任务。源码尚未准备时可先澄清业务问题，但不能宣称项目可行性已验证。工作项系统、记录位置、字段、权限和验证命令遵循目标项目规则；技能不固定 Jira、分支、状态或特定架构。读取不到材料时继续不依赖它的分析，不编造项目事实。

## 核实问题与价值

从具体角色和场景解释当前行为、期望结果、差距及影响；频率、收益或损失缺少证据时标明估计。核查现有能力与相关工作，区分能力缺失、使用入口难发现、配置问题和已有缺陷。

先考虑删除、纠正、复用与更简单方案，再判断是否值得新增能力。说明适用范围及实现、使用、维护成本；有异议直接说明依据、风险和替代解释，不迎合，也不为了展示分析而给小需求凑多个方案。能够复用或不值得做时给出可操作的建议，不强行产出新增设计。

## 让讨论支持理解和决策

讨论可往返，不要求逐项填表。每次围绕最重要的理解缺口或决策，先用具体场景、前后行为、必要的流程图解释，再询问影响正确性、范围或风险取舍的缺失信息。可以自行核实的事实先查；普通实现选择自主判断，已有有效输入和确认不重复索取。

在关键决策处讲清选择、推荐理由、代价、影响及不确定性，技术细节以支撑决策为限。根据研发对案例、预期和取舍的具体反馈发现理解偏差；区分事实争议、理解偏差与偏好差异。存在明显理解缺口时换例子或补证据，不催促确认，不要求考试式复述，也不声称能够保证研发已经理解。研发理解后仍可不同意推荐方案。

尽早用正常、异常和边界案例讨论验收，使研发知道什么结果代表需求得到满足。等待回复时继续无依赖的分析；沉默或超时不代表确认。记录具体决策及适用范围，补充要求时复用既有成果，只重新核查受影响部分。

## 按需求深化设计

按实际需求选择[类型设计参考](references/design-types.md)中的重点，混合需求组合使用，不要求研发先分类。类型决定关注点，复杂度和风险决定深度；简单需求说明明确行为及验收即可。

复杂设计需要把目标行为与当前实现衔接起来，定位职责、关键接口和依赖；按影响评估架构冲突、兼容性、数据、权限、性能、失败、中断恢复和退出路径。每项实质风险说明触发条件、影响、缓解方式和剩余未知，不给不相关项增加表单。项目专属兼容和迁移规则从项目读取，不在本技能另设规则。

无法通过阅读确认的关键假设，提出最小实验、输入条件和成功标准；实验执行仍遵循已有授权。设计就绪需要验证过的事实或明确可接受的前置条件，不能把未验证假设包装成已可行。

验收与目标对应：写清场景或指标、输入条件、预期结果、验证方法及必要环境；覆盖关键失败和回归，区分模拟、真实应用和发布证据。不只写“测试通过”，也不预设所有需求都必须采用同一种测试。

## 拆分、评审与交接

小需求保持一个工作项。大需求先形成整体设计，再按可交付成果拆分；每项说明目标、范围、输入与前置依赖、关键接口、实施步骤和验收，按风险补充恢复方式。独立执行指前置成果具备后可执行，不是没有依赖；不要只按文件或技术层拆票。保留整体场景验收，避免各项完成而整体不可用。

每个拟实施方案都要评审，默认当前 Agent 核对项目事实和合同；不自动委派。检查真实问题是否解决、是否过度设计、项目适配与兼容是否正确、关键解释和决策是否齐备、步骤依赖与验收是否可执行；复杂项同时核对跨项接口和整体验收。

每个方案最多五轮，一轮包含审查当前方案、提出有依据的问题、调整并核对关闭情况。尽早收敛，不凑轮数；澄清理解不计为评审，但实质重做设计仍计入，不因改名、拆票或恢复会话重置同一方案的轮次。记录主要意见、调整、不采纳理由和未决项，不逐字保存讨论。第五轮仍有关键缺口时保留“待决策”或“待验证”，说明缩减范围、验证或暂缓建议，不自动通过；不受影响的就绪部分可单独交付。

交接保持一份连贯结果：问题与范围、项目现状和依据、选定设计与关键取舍、研发决策、可执行验收、工作项依赖、评审结论及未决事项。深度以执行者不必重新决定关键行为和架构为准，不预写全部代码。关键解释已提供、所需决策已取得且实施与验收清晰时，才标记设计就绪。

沿用项目已有记录位置和工作项，外部创建或修改遵循项目规则及有效授权，回读核验关键字段；写入结果未知时先核查原操作，不盲目重建，不宣称同步成功。无需外部系统的讨论先保留会话结果，不自行创建平行台账。需求确认不自动授权实施、提交或发布；已有有效授权不重复请求。交接到项目现有开发和验证流程，方案评审不能代替实现审查及验收。
