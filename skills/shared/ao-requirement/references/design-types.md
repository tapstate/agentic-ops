# 按需求选择设计重点

仅阅读与当前需求相关的部分；各类型可以组合，问题是设计提示而非必填表单。共同的价值判断、研发交互及收敛条件以 [SKILL.md](../SKILL.md) 为准。

| 类型 | 应查明和解释 | 设计与验收重点 |
|---|---|---|
| 新增能力 | 谁在什么场景下需要什么结果，现有能力为何不足 | 完整使用路径、输入输出、正常与异常行为、权限与能力边界；验收完整用户场景 |
| 现有能力改进 | 当前障碍，改进前后可观察差异，原用户的使用习惯 | 复用与修改范围、默认行为和兼容性、引入的使用成本；验证收益及原能力回归 |
| 缺陷修复 | 预期的依据、复现条件、现象与根因的区别、影响范围 | 能证明旧行为错误和修复有效的案例、相邻场景回归；证据不足时先定位，不凭报错猜根因 |
| 重构或架构调整 | 当前耦合造成的具体问题，为何局部修正不够 | 职责依赖、对外行为保持、迁移与回退；验证原行为和目标结构，不用代码量证明价值 |
| 性能或稳定性 | 当前基线、目标负载、测量条件、瓶颈或故障模型 | 可测指标与代价、压力边界、退化和恢复；明确数据、环境与对比方法，不虚构阈值 |
| 安全 | 需保护的资产、参与方与信任边界、现实威胁和权限 | 防护与失败行为、可用性代价、剩余风险；验证有效防护及合法使用，敏感操作另遵守授权 |
| 项目接入或系统集成 | 双方实际接口和版本、配置差异、所有权及依赖条件 | 契约映射、数据一致性、超时重试与幂等、失败恢复；验证跨系统完整路径，模拟不能替代真实联调 |

例如“批量导入并提升吞吐”同时涉及新增能力、性能和可能的系统集成：先解释完整导入行为和失败处置，再确定可测吞吐目标，不拆成互不衔接的三份方案。
