# TapData 工位 Docker 开发环境

数据分类与生成、归档、恢复、清理责任统一遵循[数据生命周期开发规范](../../../docs/development-data-lifecycle.md)。本文项目操作仍以当前实现为准；目标两个清理操作及源码删除见[工位目标合同](../../../docs/architecture/single-task-station.md#任务生命周期目标合同)，不能用现有环境卸载或 purge 冒充已实现。

本环境用于研发本地测试和联调。现有 `tapdata-test-env` Skill、脚本、配置及运行目录标识继续兼容，用户界面与指引统一称为“开发环境”。

本指引负责命名环境配置、完整 Launcher 装配和本地 Docker 生命周期，由 [tapdata-test-env](../skills/tapdata-test-env/SKILL.md) 使用。源码构建方法仍以[构建测试指引](build-test-and-local-run.md)和当前工位分支为准；工位身份与任务退出以[工位合同](../../../docs/architecture/single-task-station.md)为准。本能力不引入环境池；配置布局以工位合同为准，版本切换使用[当前升级指引](../../../docs/usage/update-and-rollback.md#目标设计与当前实现)。与任务退出、恢复及构建的职责遵循[生命周期协作规范](../../../docs/maintenance-guide.md#生命周期协作规范)，本页只定义项目操作；资源收尾职责收敛尚未实现，不代表已有统一清理接口。

## 空闲工位连接外部 TM 的目标设计

本节是空闲工位部署 FE 并连接既有自建 TM 的权威设计。环境入口支持下述外部模式；旧版本脚本不接受新增字段，须核验工位绑定版本。后文至少一个本地 TM 和数据库保留交互仅适用于未配置 external_tm_url 的模式；不能修改本地状态绕过校验。实现验收和真实环境验收分别记录在 Jira，本文只维护稳定行为与验收合同。

使用现有入口准备源码及外部模式草稿，秘密文件与内部 preparation 仍按后文流程填写、检查及配置：

```sh
python3 <product-root>/projects/tapdata/scripts/test_environment.py prepare-source --station <station>
python3 <product-root>/projects/tapdata/scripts/test_environment.py prepare-inputs --station <station> --env <name> --external-tm-url <HTTP服务根地址>
```

prepare-source 仅支持本场景的 develop 工程，返回逐仓分支和 SHA，不创建 run；失败后回读已经准备的源码再重试。已有草稿目标不同会拒绝覆盖，修改普通输入仍由 Agent 核验后编辑。prepare-inputs 生成两个 FE 节点；实际部署仍使用 configure/deploy/update/status/uninstall。配置需要新增内部 fe_heartbeat 映射，参考 preparation 模板并核对目标分支的 Workers 身份、类型、心跳和停止/删除字段；旧本地 TM preparation 无此字段继续可用。

### 范围与源码准备

已绑定 TapData 且无当前任务、无未完成工位操作的工位可准备开发环境，不要求先接管业务任务或创建虚假 run。同一工位仍只有一个活动环境；多个 FE 是同一 Compose 项目的节点。双 FE 场景采用 node1、node2，均只选择 FE，共享同一次源码构建和制品摘要，各自具有独立 UUID、配置与工作目录。不启动本地 TM、Web 或 APIServer，不生成其宿主端口映射。

源码准备复用现有工程 Profile、仓库目录、可信 origin、分支解析与源码池；主仓选择 develop，依赖仓按项目映射解析，不能强制所有辅助仓均存在 develop。已准备的干净开发分支可沿[空闲源码刷新](../../../docs/usage/station-materials.md#空闲工位源码刷新)快进；其它分支、dirty、ignored 生成物、本地独有提交或分叉保留并报告，不能 reset、stash 或覆盖成果。缺失仓库通过现有源码池与独立克隆原语准备，不直接调用依赖活动任务的接管流程，不将 source-update 当作克隆入口。临时克隆在 `runtime/tapdata-source-preparation-*` 内先校验后发布；进程中断残留不阻断重新准备；任务清理核验临时 Git 的独立性，纳入明确处置范围；外部关联仓库保留并报告，接管前按现有保全流程处理残留并核验 runtime 为空，不能据名称删除 source 中的未知目录。部分成功按实际 Git 身份和 SHA 回读续办，不增加任务基线或永久准备状态机。源码准备错误返回脱敏的类别及恢复提示，不输出 Git 原始错误或远端凭据。

源码准备和构建先核验没有其它源码写入者，复用工位锁协调接管、源码变更及运行区发布，遵守既有产品租约与锁顺序；项目配置锁不能代替工位互斥。已存在环境时使用现有更新/切换路径，不并发争写源码生成目录。构建前后核验源码指纹，记录各仓实际 SHA、来源引用与制品摘要；远端后续前进不改变正在运行的制品，下次明确更新才重新准备。

### 外部 TM 配置与协议

运行配置 schema 2 增加可选的 external_tm_url，缺省保持现有本地 TM 模式；旧 epoch 的 schema 1/2 配置仅从备份转换为草稿，不直接加载。提供该字段时只允许 1～3 个 FE-only 节点，拒绝混合本地 TM/APIServer；地址必须是无凭据、查询参数和 fragment 的 HTTP(S) 服务根地址，本期根路径为空或 `/`，拒绝带 `/api` 或其它路径，避免重复拼接。普通配置保存服务根，生成配置统一追加 `/api/`。外部模式不生成对本地 TM 的 Compose depends_on，TM/API 映射为 null。

继续使用原生 `tapdata start backend --workDir <节点工作目录>`。有效配置中的 tapdata.conf.backendUrl 经 Launcher 的 backend_url 环境变量传入 FE；配置中的 cloud.baseURLs 保持同一目标，避免两个入口指向不同 TM。不使用无参数交互初始化，不改用 Cloud token 流程。Launcher 非 Cloud 路径会访问配置的 Mongo 获取 Access Code，故必须提供目标 TM 对应的 Mongo 连接及适用认证；不能仅凭 TM URL 推导数据库地址，也不能用另一空库替代。复用受控秘密文件与目标分支原生认证，不把凭据写入普通配置、argv 或公开回执。

目标 TM 的版本、产品模式、许可、可容纳 FE 数量以及节点加入后可能参与现有任务调度，均属于部署前置核验。部署意图已覆盖的影响无需重复确认；未知兼容性或超出授权的调度影响只暂停启动，继续独立构建与准备。脚本预检验证容器到 TM HTTP 和 Mongo 及副本成员的连接，HTTP 401/403 仅表示服务可达；Agent 按目标版本核验 WebSocket、认证、版本和许可，启动后的 Launcher 与 FE 持续心跳提供对应注册链路证据，不以宿主机端口可达替代。外部模式沿用已有数据库，不进入询问清库或 --reuse-mongo 的流程，不清库、不执行 TM 初始化迁移、不调整共享模式或权限；这不表示 FE 注册、心跳和正常业务行为没有写入。

### 装配、状态与恢复

复用完整 Launcher 包和现有装配检查，包括 TM Jar、WebUI、连接器及按产品模式所需的许可证；包内存在不等于启动这些组件。本期不优化最小包，不修改业务 Launcher。FE 启动需要 Engine Jar、Java、有效配置和日志配置，Launcher/探测使用相应 Linux Node 及已有模块；tm.jar 的存在参与原生类型判定，因此不能仅按所选进程删除附带文件。包管理器及目标架构依赖沿现有构建指引，不另引入第三方组件。

状态按所选组件逐层核验：容器、Launcher、FE、目标 TM 中的本次身份与持续心跳、许可证。原生整体 status 可能将未运行 TM 解释为未启动，不能直接作为 FE-only 失败或成功结论。目标分支决定 Launcher 与 FE 的记录字段，二者分别取证；外部模式 status 在首个样本有效时等待 21 秒（生成的 Launcher reportInterval 为 20 秒）读取第二次，证明时间戳前进并满足新鲜度要求。重复身份、停止或删除状态均不能通过。ready 表示组件及心跳就绪，不代表许可、业务或完整认证验收；这些仍需 Agent 按实际应用补证。旧节点和仅 Launcher 的记录不得计为 FE。未测试业务同步、容量或 UI 登录时明确保持待验证。

更新沿用节点身份，先完成构建、配置和连接预检再停止原环境；构建/预检失败保持原环境，切换后启动失败保留新旧构建记录和诊断，不承诺自动恢复已停止容器或回退数据库。写入结果未知先回读原现场，不能用重复部署制造新身份。只停止和清理本工位标签、Compose 项目与运行记录共同确认的资源，不自动删除远端 Worker 记录；卸载后回读其心跳停止/离线，残留记录如实报告。原生日志可能含认证信息，私有保留，对外仅提供脱敏结果。

### 与后续任务的交接

空闲表示没有业务任务，不表示 runtime 没有写入者。保留[工位合同](../../../docs/architecture/single-task-station.md)及接管前 runtime 为空的条件：运行中的环境不能自动继承为新任务，也不能静默删除。后续接管先识别活动环境并说明停止影响，复用仍有效的退出授权；未获停止授权则保留环境并暂停接管。

沿环境卸载保全必要诊断及构建依据，停止并回读本工位容器和网络，再按[清理与退出](../../../docs/usage/task-authorization.md#清理与退出)预检并执行任务清理。诊断仍在 runtime 时，先按现有材料保全规则保存需要保留的证据，再清理；未知对象保留。不能仅执行 uninstall 后忽略诊断残留，也不能把卸载成功当作清理完成。任务清理会删除 source，Git 成果必须先保全或明确放弃；持久配置保留，后续任务重新准备源码，不继承旧验收。停止、保全或清理失败时保留原现场，不创建新任务；完成后重新核验全部原接管条件。

外部 TM 模式不增加任务类型、环境池或第二套运行目录。当前配置路径与引用语义采用 epoch 33；旧配置先备份隔离，再按需转换，不承诺跨 epoch 直接读取。

### 可执行验收合同

| 场景与输入 | 预期结果及验证方法 |
|---|---|
| 无源码或已有干净源码的空闲工位 | 复用项目解析准备工程，记录实际 SHA；两个 FE 共用一份制品。检查仓库身份、构建记录和容器内实际文件摘要 |
| 脏仓、分叉、来源不符、未完成操作、并发接管 | 保留成果，拒绝受影响准备/发布；不创建虚假任务或覆盖源码。失败恢复核对已完成仓库，竞争回归证明不越过原接管条件 |
| 两个 FE 连接授权外部 TM | 同一 Compose 中恰好两个 FE、独立身份、正确 API 地址；无本地 TM/APIServer 进程及映射。核对实际进程、有效配置和目标 TM 记录 |
| 持续心跳与许可 | Launcher 与 FE 分别取证；两个本次 FE 连续样本时间前进、正常许可有效。旧 Worker 数量、端口存活和降级许可不能替代 |
| TM/Mongo/副本成员不可达、认证或版本/许可不适用 | 明确失败层，保留原环境与私有诊断，不清库、不关闭认证或许可，不将未知结果标为成功 |
| 错误架构、构建期间源码变化、部分启动失败 | 前两者在停止旧环境前拒绝；启动失败保留可核查现场、源码/制品依据和恢复入口，不重复生成节点 |
| 更新、卸载、再次接管 | 更新保持节点身份并加载新制品；卸载仅清本工位资源，远端记录心跳停止。保全并清理 runtime 后按原合同接管，停止失败不产生新 run |
| 兼容回归 | 旧 schema 1/2 经备份转换为草稿；本地 TM、多节点、配置切换与现有清理保持运行含义；同 epoch 状态可恢复 |

自动化使用受控夹具验证配置、生成、错误路径和生命周期互斥；真实双 FE 接入使用实际源码、完整 Linux 制品、授权目标 TM/Mongo，单独记录版本、节点身份、制品摘要和连续心跳证据。正式候选按仓库既有影响选择器验收，模拟通过不替代真实部署结果。

## 首次部署输入与配置命名

首次部署和新增命名配置按“复用已知信息 → 集中收集独立输入并填写秘密文件 → 配置规范检查 → 构建与部署预检 → 自动部署”进入。配置名、目标架构、产品模式、节点与特殊端口/资源要求没有先后依赖，应同轮展示默认值与缺项，只让用户补充或更正；仅当路径依赖尚未确定的配置名、产品模式决定是否需要许可证，或数据库预检发现已有集合时，追加相应交互。用户只需要运行意图，构建准备由 [项目开发指引](tapdata-development.md#docker-开发环境的构建准备)负责；已有配置或事实直接复用。

| 输入 | Agent 的引导与默认值 |
|---|---|
| 配置名 | 未命名时建议 `local`；用稳定用途命名，允许用户明确命名，不随架构或工位变化改名 |
| 架构 | 明确选择 `linux/amd64` 或 `linux/arm64`，不从宿主机推导 |
| 产品模式 | 核实部署意图，例如本地企业版 DAAS；内部 Profile 由项目指引推导 |
| 节点组件 | 本地模式默认 node1 的 TM+FE，1～3 个节点且至少一个 TM；外部模式默认两个 FE；APIServer 仅本地模式显式选中时部署 |
| MongoDB | 先创建 Mongo URI 秘密文件并给出绝对路径，由用户本地填写；已有受控文件直接复用，核对容器可达、认证、副本集和数据库用途 |
| 许可证 | 每个环境仅一份 license.txt，所有节点共享；先创建权限 0600 的文件并给出绝对路径，由用户填写；存在或非空不代表授权有效，启动后验证 |
| 端口与资源 | 默认 node1 TM 13030/API 13080，node2 23030/23080，node3 33030/33080；未选组件为 null，冲突时选择空闲端口并告知；默认 Java 堆见模板 |

通过 `prepare-inputs --env <name>` 从 [运行配置模板](../templates/station/test-env.json) 生成用户可编辑草稿及秘密文件，不依赖 Docker、构建或 preparation。返回输入项、已有默认值、缺项与绝对文件路径；产品模式从会话复用，脚本不新增模式台账。Agent 填入名称、架构和已知值，只让用户补缺项，可用自然语言反馈而不要求手工编辑 JSON。产品模式与登录验收目标在会话/Jira 记录，不另设执行清单。每工位可以保存多份配置，但只有一个活动环境；新增配置不会启动第二套环境，也不代表切换源码分支。

### 旧配置备份来源

下表仅用于识别备份中的旧材料，不是新版运行输入路径；`<name>` 是用户配置名，不是 station_id。新版目录见下一节。

| 对象 | 统一位置或名称 |
|---|---|
| 用户运行配置 | `config/tapdata-test-env/<name>.json`，schema_version 2，字段见模板 |
| 输入草稿 | `config/tapdata-test-env/drafts/<name>.json`；沿用 schema 2，未完成时不列为已保存环境，不作为部署输入自动加载 |
| Agent 项目准备 | `config/tapdata-test-env/preparation/<name>.json`，schema_version 1，用户不填写 |
| Mongo 秘密文件 | `config/secrets/tapdata-test-env/<name>/mongodb-uri`；mongo_uri_file 填 `tapdata-test-env/<name>/mongodb-uri` |
| 许可证秘密文件 | `config/secrets/tapdata-test-env/<name>/license.txt`；ports 中 license 填 `secrets/tapdata-test-env/<name>/license.txt` |
| 节点 | 新配置统一 `node1`、`node2`、`node3`；nodes 与 ports 的键一致 |
| 单一运行现场 | `runtime/tapdata-test-env/`，全部节点使用 `ao-tapdata-<station_id>` Compose 项目 |

新配置所有节点的 license 引用均指向同一份 `license.txt`；确认产品模式无需许可证时统一为空字符串，不要求用户逐节点提供。运行配置不含 build/assets、制品路径或监控实现字段；旧 schema 1/2 仅从备份中提取输入，不直接用于部署。新配置和项目准备通过 configure 保存，普通配置保存不改 `.agenticops/`。只修改已有运行配置时可复用对应 preparation；切换源码或架构需 Agent 重新核验它，不要求用户同步技术字段。

TM、FE、APIServer 分别映射 Launcher 的 `start frontend`、`start backend`、`start apiserver`，每次附带独立 `--workDir`。本地模式中无 TM 节点等待 TM 容器健康；节点用 Compose DNS 地址通信，内部 TM 3030/API 3080，宿主映射只绑定 127.0.0.1。每个节点角色、端口及资源必须与运行配置一致。

### 按环境聚合的项目配置映射

通用目录、草稿保存、共享引用、秘密与清理合同以[工位合同](../../../docs/architecture/single-task-station.md#配置按环境聚合)为唯一来源。本节定义 TapData 文件映射；prepare-inputs 在配置缺项时查找备份，configure 在工位锁内发布完整配置组合。临时发布目录中断后由下次受管调用恢复，不生成长期版本库。

| 对象 | 目标位置（相对工位） | 项目职责 |
|---|---|---|
| 运行输入 | `config/environments/<name>/config.json` | 节点角色、端口、镜像、平台、Java 参数及秘密引用 |
| 项目准备 | `config/environments/<name>/preparation.json` | Agent 从实际源码核验 build/assets、驱动与 TM/FE 心跳字段 |
| 输入草稿 | `config/environments/<name>/drafts/` | 保持本环境对应文件结构；未采纳秘密放其 secrets 子目录 |
| 组件输入 | `config/environments/<name>/components/tm.yml`、`fe.yml` | 归并原根层组件配置；按部署方式需要使用，不强制 Docker 环境额外生成 |
| 测试输入 | `config/environments/<name>/testing/` | 原 config/taptest 的环境配置与数据源定义按实际目标环境归属 |
| 环境秘密 | `config/environments/<name>/secrets/` | mongodb-uri、license.txt、admin-password、fe-access-code 及实际测试凭据按需保存 |
| 共享输入与秘密 | `config/shared/components/`、`testing/`、`secrets/` | 只收纳明确跨环境共用的对象，环境显式引用 |
| 旧配置备份 | `config/backups/<backup-id>/` | 保留不兼容旧输入及秘密的原相对结构，不作为运行输入 |
| 活动现场 | `runtime/tapdata-test-env/` | 沿用单 Compose 项目与当前现场，不按环境复制运行目录 |

同一环境的节点按实际许可要求引用同一份许可证；确实跨环境共用时可显式引用 shared/secrets 下的文件，不强制每个环境复制一份。Mongo URI、许可证和管理员凭据的文件引用都遵循 config 根基准，消除当前 mongo_uri_file 与 ports 中 license 的不同基准；例如环境 Mongo 引用为 environments/dev/secrets/mongodb-uri。运行输入仍为 schema 2、preparation 为 schema 1，由 epoch 33 明确新的引用基准；旧 epoch 文件只进入备份转换。外部 TM 环境仍需核验对应 Mongo 与权限，环境名不推导源码分支、产品模式或凭据。

旧路径覆盖当前命名环境布局、config/tm.yml、config/fe.yml、config/secrets 下的散放文件及 config/taptest。不兼容材料先按工位合同备份隔离，新环境不自动加载旧路径。转换的[触发时机与处理顺序](../../../docs/architecture/single-task-station.md#转换触发时机与处理顺序)统一由工位合同维护。TapData 匹配备份时核对名称、TM 地址、Mongo 目标库、组件和秘密引用，不自动把散放文件归到默认环境或判为共享。旧 schema 1 的 build/assets 与探测字段分离为 preparation 候选，并由 Agent 对当前源码重新核验；schema 2 及独立 preparation 同样不能直接冒充当前有效配方。旧 TapTest 内嵌凭据转为草稿秘密和新引用，实际原生输入仍按消费者支持生成。无法确认或转换的材料保留在备份。备份、同名冲突、兼容判断及验收沿工位合同，不在项目指引另建迁移器或计划。

## 功能依赖与兼容接续

本环境功能拥有运行配置（schema 2）、构建 preparation（schema 1）及活动环境记录；字段要求由 test_environment.py 的 validate/combine_config 校验维护，模板只提供草稿。结构版本随需求变化，不要求与应用 epoch 相同。路径、秘密、备份和目录发布复用 environment_config 接口，不由清理功能解释配置内容。

Agent 优先从当前项目源码、已有配置和已核实环境获取字段含义、组件入口、构建方法及探测要求，向研发说明差异和缺项后修补草稿；有效正式配置直接复用。正式配置不符合当前字段合同时，prepare-inputs 保留原件并提供草稿，不因旧版本号阻断草稿准备，也不自动认定旧语义等同当前版本。损坏 JSON 或未知来源仍须保全核实。确认后的草稿沿 check-inputs/configure 重新检查，成功不等于连接、构建或部署通过。

构建与部署继续复用下文现役入口，不新增原生成果导入框架。辅助构建失败时，Agent 可在授权范围内按当前源码完成编译，将已核实产物保留在受管 source 或本轮 build 区域；经研发确认后调整 preparation 的 build 为实际必要的准备/产物检查步骤，assets 指向真实产物，再由原 build/deploy 入口执行完整装配、内容/架构检查、Java/Node 与数据库预检。不能把空命令当成功证据，也不能手改 build-record.json 的 validated 或 active.json。任意外部目录和缺少来源的旧产物不直接采用；业务验证仍独立执行。该接力可复用既有能力，真实 TapData 编译与部署通过仍需单独取证。

## 配置准备与预检

`prepare-inputs` 先复用完整的新配置或草稿，缺项时才查找备份并填补可确定的输入；秘密文件权限为 0600，重复调用保留已填内容。用户可修改草稿或用自然语言反馈普通输入，由 Agent 写入；秘密只在本地文件填写，不进入聊天、命令参数或日志。草稿中断后继续复用，配置操作本身不修改工位状态或 epoch。

用户填写完成后必须运行 `check-inputs --config <草稿绝对路径>`：复用运行配置校验，检查字段、架构、1～3 个节点、本地模式至少一个 TM（外部模式仅 FE）、组件与端口对应、端口范围和重复、Java 参数结构、单份许可证引用、秘密文件受控路径/普通文件/权限/非空，以及 Mongo URI 基本格式、目标数据库和容器地址。失败只纠正返回的缺项或错误，再检查；不覆盖用户秘密文件。产品模式与是否需要许可证由 Agent 对照实际源码核实；不要求用户填写内部 Profile。通过仅表示静态配置合规，Mongo 认证、网络、副本集、宿主端口实际占用和许可证有效性仍由后续预检与启动验证，不能称为环境可用。

用户配置的 schema_version 为 2；节点、镜像、平台、Mongo 秘密路径、ports 和 java 是运行输入。Agent 依据[项目开发指引](tapdata-development.md#docker-开发环境的构建准备)生成独立 preparation，生命周期脚本合并后复用已有执行合同；旧完整 schema 1 不能直接保存或部署。`configure --env <name> --config <已检查的草稿.json> --preparation <preparation.json>` 先验证两份输入，普通配置错误不覆盖已保存配置或停止当前环境。只改运行配置时可省略 --preparation，复用已保存准备文件。

部署前核对 Docker CLI、Compose 与 daemon、秘密文件权限及端口。Mongo URI 的 localhost/127.0.0.1 不能代表宿主机，使用用户提供的容器可达地址；不猜测替换 URI。Mongo 的权限、TLS 与副本集必须由目标应用支持，不自动创建外部数据库或生成 TLS 材料。源码与目标 Linux 制品、模块加载、Java/Node 执行和副本成员可达性由项目准备及只读容器预检验证；准备失败继续不依赖缺项的工作并保留原环境。

本地 TM 模式部署前只读检查目标库的已有集合（Mongo 的表），输出明确库名与集合数，不读取业务记录。`inspect-mongo --env <name>` 复用当前 Linux 制品；无活动现场时由 Agent 在项目准备完成后指定受管目录 `--bundle builds/<build-id>/bundle`。首次部署或切换非空库未取得保留决定时，deploy 在停止原环境前拒绝继续；用户明确保留后才传 --reuse-mongo。正常 update 保留原库，不把应用更新当作清库授权。预检因权限无法列集合时待核验，不把查询失败当成空库。

发现旧表时先询问保留还是清理，说明历史模式、权限、节点等记录可能影响验证。清理只能由用户审核后复制命令执行，或由用户明确输入对应命令并要求 Agent 代执行；选择“需要清理”本身不授权 Agent 主动执行。Agent 提供的命令必须绑定已回读的具体目标库，并在命令内核对实际数据库名称，用秘密文件引用读取连接，不能展开 URI 或密码、清理整个 Mongo 服务或其它数据库。用户执行后再只读回查，不以其说“执行过”代替空库事实；完成清理后无需 --reuse-mongo。许可证可能绑定现有 sid/机器信息，清库会删除数据库授权与身份记录，须在命令说明中指出并确认现有许可证能用于重新初始化。

启动后核验实际产品模式、Settings、版本、许可证、登录及菜单。已有数据库模式与部署意图不同，先说明影响并取得决定，备份受影响设置；不删除迁移记录、重置权限或关闭许可证检查。容器健康不代表业务验收完成。

## 部署排障与分层验收

编译、依赖和装配异常先按[编译与装配易错点](tapdata-development.md#编译与装配易错点)定位；部署继续使用本指引的生命周期入口。下列检查按实际源码、命名配置和当前节点身份取证，只读取必要字段，不把工位的临时排障脚本、整份日志或数据库记录复制为通用配方。

| 现象或阶段 | 核验与处理 | 不能据此推断 |
|---|---|---|
| Docker CLI 存在但 daemon 访问失败 | 区分 daemon 未运行、连接上下文和当前执行权限；在已授权方式下重新核验后继续。 | 工具已安装不代表可部署；不能因此跳过容器预检。 |
| Mongo 返回认证错误 18 | 一次集中核对实际认证库、账号、密码和 URI 特殊字符编码；用户修改既有秘密文件后重验。区分认证失败、连接失败与副本集公布地址不可达，不展示 URI，不自行替换主机、认证库或重置密码。 | 字段非空或静态格式检查通过不代表认证成功；认证失败也不能视为空库。 |
| Launcher 健康、注册与心跳 | 将当前节点 UUID 与实际监控记录对应；按源码更新周期至少取两次样本，确认时间戳前进且满足既有新鲜度要求。 | Launcher 存活不代表 FE 已向 TM 注册，更不代表业务同步成功。 |
| FE 注册与持续心跳 | 核对当前运行中每个 FE 的 TM Worker 记录、身份、停止/删除状态及心跳；结合实际进程和配置检查数量，排除旧环境遗留记录。集合及字段以本分支源码为准。 | 不能把 TM-only 节点的 Launcher 算作一个 FE，也不能只按全库 Worker 数量验收。 |
| 许可证文件存在或日志出现 valid | 核验共享文件实际加载、正常许可校验、期限与 FE 数量限制，以及当前 FE 的许可绑定。区分正常 valid、数据库不可用时的 fallback 和关闭 checkLicense；对时间敏感的状态连续回读。 | 非空、HTTP 首页成功、降级通过或禁用校验均不能证明正常许可验收通过。 |
| 许可证接口返回 401 | 先核实是否需要登录；可用当前源码对应的启动日志与必要持久化字段补充许可证据，单独标注接口未验收。后续确需管理接口时，先创建或复用权限 0600 的 `config/environments/<name>/secrets/admin-password`，给出绝对路径让用户填写；已有文件不覆盖，不在聊天索取密码。 | 管理员密码不是 Mongo 密码；401 本身不证明许可证失效，也不能据此关闭认证。 |
| 初始化迁移告警 | 绑定实际脚本、错误码、查询条件和所影响功能，做最小只读影响核验。例如某些分支的 `init/idaas/4.24-2.json` 删除旧 APIServer Worker 命令缺少 `deletes[].limit`，可出现 Mongo 40414；需核对当前分支及是否存在匹配记录。 | 某次匹配数为零只说明该次未发现目标记录，不代表缺陷消失；不能补写迁移成功状态、自动删记录或宣称所有业务验收通过。 |

旧 APIServer 告警存在匹配记录、阻断后续初始化或影响当前场景时，保留对应验收缺口，在现有任务中记录影响与后续修复需求；无匹配记录且请求的检查通过时可以报告这些具体结果，同时披露告警，不扩大成完整应用通过。真实缺陷修复另按任务范围处理，不为完成部署临时改业务源码。

清库授权继续遵循上一节的精确命令与目标库合同。没有近期心跳不能证明没有其它使用者，也不能替代停写核验、数据保全或清理授权；部署重试不自动重复清库。只移除已核验无引用且在用户清理范围内的配置或占位文件，保留使用中的共享许可证、Mongo 秘密、preparation 与必要构建证据。

结果分别报告构建/装配、容器与组件、Launcher、FE、许可证、UI 登录和业务验证。Web 首页可访问与 UI 已登录是不同结果；未进行登录、菜单、业务同步或容量实验时保持待验证，不把环境部署完成当作研发任务完成。

## 操作、恢复与卸载

统一入口为 Product Root 的 `projects/tapdata/scripts/test_environment.py`，参数 `--station <station>`。`configure --env <name> --config <json>` 保存运行配置与 Agent 准备但不应用；`list` 回读配置清单和 Docker 实际状态；`deploy` 多配置时需 `--env`，单配置可省略；`update/status/uninstall` 默认针对活动环境。配置或秘密文件变化需 update，不热加载。源码修改后要加载新制品也使用 update；对同名活动环境重复 deploy 只回读现有环境，不重建源码。

不同配置的部署需用户明确切换意图，对应 `deploy --env <name> --switch`。目标构建、架构、Mongo和许可证文件预检成功后才停止旧环境。更新保留同名节点身份；切换清理旧节点现场并生成新身份，两份配置和外部数据库保留。上线失败保留现场和新旧构建记录，不自动回退数据库；用 status 回读并修复后 update，或明确卸载。中断或 Docker 写入结果不明时先回读，归属不明或未登记资源停止自动删除。

所有节点属于同一个 Compose 项目 `ao-tapdata-<station_id>`，定义保存在 `runtime/tapdata-test-env/compose.json`；节点是其中的 services，不按节点分别执行 docker run 或生成独立项目。脚本统一传 `docker compose -p <project> -f <compose-file>`，更新和切换沿用同一项目，工位之间以 station_id 隔离。Docker Desktop 中按该项目查看整组。可用同一组参数执行只读 `ps --all` 核验分组；部署和删除优先使用生命周期入口，避免绕过归属、构建及诊断检查。

卸载先保留私有诊断，再回读确认受管容器和网络已删除，最后清理当前运行目录。不执行 Docker prune、不删除镜像、不删除外部数据库；诊断留在 `runtime/tapdata-test-env-diagnostics/`，配置和源码保留。环境卸载与任务退出按实际对象和结果衔接，任务清理已有 Docker 收尾时不要求先重复手工卸载。当前环境入口仍读取工位绑定、操作与运行记录，损坏材料可能使卸载失败；最小依赖收尾是开发目标，不能假定已覆盖所有异常。此时保留现场，由 AI 核实资源并在有效范围内使用原生工具收尾，再按原操作复查，不重新部署来满足卸载条件。停止或删除失败时保留受影响运行目录并报告残留；是否已释放任务及能否再次接管按工位合同回读，不能将资源失败一概等同于任务仍占用。需要保留的诊断在 runtime 清理前独立保存，归档引用不代表已复制诊断正文；不能仅删除本地目录就认定 Docker 资源已回收。

## 验收

自动测试核对集中输入准备、单份共享许可证、填写后规范检查、重复初始化保全、空文件和路径/权限拒绝、多配置选择、单环境约束、组件角色与端口生成、失败预检保留原环境、更新身份保留、切换身份更新、资源归属、脱敏和卸载保留配置/外部数据。安装回归确认新增 Skill 按项目机制接线，旧工位初始化、刷新、清理继续可用。

真实验收必须使用实际工位源码、完整 Linux 产物及授权 MongoDB：验证单节点、三节点（含 TM-only/FE-only）、Launcher 注册和持续心跳、停止节点后的离线、更新加载新制品、两份配置顺序切换和卸载。构建成功、模拟测试或端口存活都不能宣称完整应用验收通过；缺少真实环境时列为待核验。

### 业务入口与已验证候选

准备文件的 build 只调用[业务构建入口](build-test-and-local-run.md#业务构建入口)。argv 中 `${TAPDATA_TEST_ENV_BUILD_DIR}` 由适配器作为普通参数替换，不使用 shell 二次展开；将业务输出指向该目录下的 application。assets 使用 `{"source":"@build/application/bundle","target":"."}` 消费其完整包，必须通过相邻 build-manifest.json 的完整标记与逐文件摘要核验。当前候选仍执行 Linux 架构、Java/Node 和容器连接检查。

部署前已存在且与源码、配方和制品匹配的完整候选，先调用原业务入口核验工具链及复用条件，再重做连接预检，避免重复全量编译。旧的通用步骤配方没有工具链复用合同，继续执行原构建；不能根据旧目录存在就假定可复用。源码构建入口不存在时先在业务仓库适配，不在 AgenticOps 中再维护第二套业务编译命令。

已有宿主机 Node 和 Launcher Mongo 驱动时，在完整编译之前只读核验 Mongo 认证、目标数据库及外部 TM 可达性；缺少独立探测依赖时仍保留构建后的容器检查。宿主机网络失败可能由容器专用域名或路由导致，记为待容器核验；已确认认证失败或需决定的目标数据库内容则在构建前停止。宿主机检查不能替代容器网络检查。目标版本、许可及 FE 容量仍由 Agent 按实际 TM 的原生只读资料在部署前核实，不把文件存在、HTTP 可达或编译成功当作许可验收。
