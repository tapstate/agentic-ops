# 公司级硬规定

规则类别：公司规则。

本文件只记录 TapData 跨项目硬规定。具体项目的语言例外、分支例外、工具入口和验证差异必须写入 `install-resources/basic/projects/<project>/` 或项目工作空间规则，不得写入公司规则。

规则冲突时按 `项目规则 > AIAgent 规则 > 公司规则 > 个人规则` 执行。

## 事实源边界

- Jira 是任务、负责人、迭代、状态、评论和任务证据的事实源。
- Git 仓库是代码、测试、提交和分支的事实源。
- GitHub Pull Request 和 CI 是代码审查、审查评论、CI 结果和合入记录的事实源。
- AIAgent 不得用本地日志、聊天上下文或推测替代事实源。

## 人工门禁

- 真实 Jira 写入、Git push、创建或更新 Pull Request、合并、发布、范围变更和线上风险相关动作必须先获得研发工程师确认。
- AIAgent 可以准备计划、证据和命令，但不得绕过人工确认执行高风险副作用。

## 人机职责边界

- AgenticOps 不追求定义所有实施细节；公司和项目标准应聚焦规范、原则、硬要求和职责边界。
- 人负责把控关键节点，明确目标与边界，评估风险，并做出项目决策。
- AIAgent 在既定规范和人工决策范围内，负责分析、设计、编码、测试、文档、证据整理和持续推进。
- AIAgent 可以给出方案、建议、风险提示和补卡草稿，但不得替代研发工程师确认方向、范围、风险等级、目标分支、验收边界或最终项目决策。
- 当规范不足以支持继续执行时，AIAgent 必须反馈缺口和建议，等待人工决策后再继续。

## 交互语言

- AIAgent 面向研发工程师、流程负责人、审阅者或 Jira 参与者的自然语言交互必须使用中文。
- Jira 中人可见的摘要、标题、描述、评论、工作日志、证据正文、阻塞说明、补卡说明和任务审计记录必须使用中文。
- Jira 字段名、状态名、`transition` 名称、`issue_key`、命令、配置字段、错误码、代码标识和日志关键字可以保留原始英文或缩写。
- 不得把英文 Jira 字段值或命令输出原样贴给研发工程师作为结论；必须用中文解释影响、风险和需要人工处理的动作。

## Git 提交

- TapData 公司仓库创建工作分支时，分支名至少必须包含用户名、Jira 任务编号和检出分支。
- 检出分支为 `release-vX.Y.Z` 时，工作分支名中只保留 `vX.Y.Z`，不得保留 `release-` 前缀。
- 推荐工作分支格式为 `<username>/<jira-key>/<source-branch>`，例如 `harsen/TAP-1234/develop`、`harsen/TAP-1234/v3.8.0`。
- 无法确认用户名、Jira 任务编号或检出分支时，必须停止并请求研发工程师补齐，不得创建不可追踪分支。
- Git 提交必须围绕当前 Jira 卡片或当前标准资产变更，一个提交只包含一个逻辑变更。
- TapData 公司规范默认使用英文提交标题和英文提交描述。
- `type`、`scope`、Jira key、命令和配置字段作为结构化标识可以保留英文。
- TapData 公司代码提交必须绑定 Jira 任务卡片；`tag` 指 Jira 任务编号，例如 `TAP-1234`。
- 提交格式为 `<type>(<scope>): <tag> <subject>`，不得省略 `<tag>`。
- 允许的 `type` 为 `Feat`、`Fix`、`Docs`、`Style`、`Refactor`、`Test`、`Chore`。
- Jira 任务编号必须能从分支名、用户指令、Jira 卡片或任务上下文中确认；无法确认时必须停止并请求研发工程师补齐，不得创建无 Jira 绑定的代码提交。
- 非平凡提交必须包含 body，说明问题、处理方式、验证结果和风险；不得在提交信息中粘贴完整 Jira 描述、敏感日志或凭证。

## Git 推送与 Jira 反馈

- 执行已获研发工程师确认的 Git 推送时，如果能从任务上下文、分支名或提交信息可靠确认对应 Jira 编号，推送成功后必须在该 Jira 卡片追加中文变更总结。
- 变更总结至少包含推送分支、提交、变更摘要、验证结果和残留风险；不得写入 secrets、tokens、credentials、private keys 或原始敏感日志。
- Git 推送成功但 Jira 评论写入失败时，必须明确反馈“代码已推送但 Jira 回写未完成”，并保留可恢复的评论内容；网络或 Jira 服务恢复后只重试评论，不得重复推送。
- Jira 评论仍属于真实 Jira 写入，必须遵守所有权、策略、操作契约和人工确认门禁。

## 保密

- 不得提交 secrets、tokens、credentials、private keys 或原始敏感日志。
- 需要展示问题证据时，应优先脱敏并保留可审查的最小上下文。

## 审查职责

- AIAgent 不能替代代码审查人、QA、安全、运维或流程负责人的专业审查。
- 审查意见必须按事实源回读，不得只依据聊天摘要判断已经解决。

## 规范沉淀

- 临场经验必须先形成改进建议，再经人工确认后进入标准资产。
- 项目层可以补充项目差异；覆盖公司硬规则时必须显式记录覆盖原因和审计依据。
- 不成熟、边界不清或风险不稳定的做法不得固化为默认规则。
